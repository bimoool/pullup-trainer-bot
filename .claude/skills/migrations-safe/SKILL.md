# Миграции без инцидентов

## Порядок деплоя — не менять

Сборка образа → **миграции** → подъём контейнеров.

Обратный порядок уже ронял прод: новые колонки при старом коде дали
`UndefinedColumnError` и положили Mini App. `deploy-run.sh` выполняет
`alembic upgrade head` между `build` и `up -d` именно поэтому.

## Только аддитивные миграции

Пока прод и новая схема живут рядом (волны 0–7), любая ревизия должна быть
совместима со **старым** кодом, который продолжает работать:

- добавлять колонки только `nullable=True` или со значением по умолчанию;
- не удалять и не переименовывать то, что читает работающий код, — сначала
  перестать читать, задеплоить, и только следующей ревизией удалять;
- не менять тип колонки на месте — новая колонка, перенос, удаление старой
  отдельным шагом.

## Разовые скрипты в контейнере

`scripts/` копируется в образ, так что скрипт запускается напрямую:

```bash
docker exec <контейнер> python scripts/<имя>.py --dry-run
docker exec <контейнер> python scripts/<имя>.py
```

У скриптов миграции данных обязателен `--dry-run`, и он обязан быть
по-настоящему сухим. Идемпотентность по пользователю: повторный прогон не
должен ломать уже перенесённых. Если нужен именно повторный перенос —
отдельный явный флаг (`--truncate`), несовместимый с `--dry-run`.

## Проверка

Миграция проверяется на staging (своя база, свой бот) до прода. Тестовый набор
сам накатывает `alembic upgrade head` на чистую базу — если ревизия ломает
накат с нуля, это видно сразу в `pytest`.
