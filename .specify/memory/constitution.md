# pullup-trainer-bot Constitution

## Core Principles

### I. Чистая архитектура domain/ (NON-NEGOTIABLE)

`app/domain/` MUST содержать только чистую бизнес-логику — прогрессию,
аномалии, ачивки, правила готовности к тренировке, отчёты. Ни один файл
в этой директории не MAY импортировать `aiogram` или `sqlalchemy`;
соответствие проверяется буквально (`grep -rl "aiogram\|sqlalchemy"
app/domain/` MUST быть пуст). Функции — чистые (без побочных эффектов и
скрытых зависимостей от сессии БД/бота), датаклассы — `frozen=True`,
деньги и вес — `Decimal`, никогда не `float`. Домен покрыт unit-тестами в
`tests/test_*.py` без поднятия Postgres.

Слои выше домена соблюдают строгое разделение ответственности:
`app/db/repositories/` — единственное место, трогающее SQLAlchemy-сессию,
один репозиторий на агрегат (`WorkoutRepository`, `UserRepository`, ...),
конвертирующий ORM ↔ доменные датаклассы; интеграционные тесты —
`tests/test_repositories/` на реальном Postgres. `app/services/` —
оркестрация поверх репозиториев (запись через репозиторий, событие в
`EventRepository`, начисление монет, проверка ачивок), тесты —
`tests/test_services/`, реальный Postgres. `app/bot/handlers/` — тонкий
слой aiogram: сбор ввода, FSM-состояние, вызов сервиса, форматирование
ответа — и ничего из бизнес-логики прогрессии/начислений; тесты —
`tests/test_bot/` через реальный `Dispatcher.feed_update`, не моки
хендлеров.

Rationale: изоляция домена — единственная причина, по которой формулу
прогрессии и правила готовности можно проверять unit-тестами без
инфраструктуры и без риска, что правка хендлера незаметно поменяет
бизнес-логику. Нарушение этой границы исторически превращалось в баги,
которые проявлялись только в проде (см. Принцип VI).

### II. План перед кодом для архитектурно значимых изменений

Нетривиальные изменения формулы прогрессии (шаг роста, пороги, переходы
снаряда) или схемы БД (новые колонки/таблицы) MUST начинаться с плана
с конкретными расчётами на реальных числовых примерах — не абстрактными
формулами — и получать явное согласование прежде, чем код будет написан.
Тесты пишутся на каждый пример из плана с точными ожидаемыми значениями.

Rationale: ручной расчёт по плану, сверенный с тем, что реально считает
код, почти всегда ловит расхождение между тем, что казалось очевидным на
бумаге, и фактическим поведением реализации (см. Принцип IV) — раньше,
чем это стало бы регрессией у реальных пользователей.

### III. Безопасность токенов и секретов

Токены, пароли и любые секреты MUST NOT появляться в коде, коммитах или
истории git — только в `.env` (локально) или GitHub Secrets (CI/CD),
прочитанные через `app.config.settings`. Деплой-образ не содержит `.git`
и не имеет `git`/`gh`; любая функция, которой нужна история коммитов или
GitHub API (например, автосбор изменений для еженедельного отчёта),
MUST использовать собственный токен проекта из `.env`, а не личный
`gh`-доступ разработчика — тот допустим только для исследования и
прототипирования самим разработчиком (или Claude), не для автономного
процесса бота.

Rationale: образ без `.git`/`gh` — не случайность инфраструктуры, а
осознанная граница: код, который полагается на локальные dev-инструменты,
не может работать в проде, где их физически нет.

### IV. Доказанное тестовое покрытие

Зелёный тест сразу после фикса ничего не доказывает сам по себе — он мог
быть зелёным и без фикса. Для нетривиальных исправлений баг MUST быть
пойман тестом, который: временно откатывают вместе с исправлением, видят
падение именно этого теста, затем возвращают исправление и видят зелёный
результат. Тот же принцип действует при разработке по плану (Принцип II):
тест пишется до реализации, ожидаемое значение сначала считается вручную
по плану, а затем сверяется с тем, что выдаёт код.

Rationale: только демонстрация факта, что тест падает без фикса и
проходит с ним, отличает тест, который реально защищает от регрессии, от
теста со слабым условием или неверной фикстурой (см. исторический баг
`callback.message.from_user` в `docs/incidents.md`).

### V. Архивировать, не удалять

Любой «сброс» или удаление исторических пользовательских данных
(тренировки, блоки, снаряжение, базовые показатели) MUST переносить
данные в архивную таблицу (`*_archive_v1`, `*_archive_admin_reset`), а
не выполнять `DELETE`. Перед удалением enum-значения из БД MUST сначала
вручную проверить, нет ли исторических строк с этим значением; если
есть — значение остаётся в определении enum как «исторический, не
используется», с комментарием рядом.

Rationale: тренировочная история — это то, ради чего существует продукт;
необратимая потеря прогресса пользователя недопустима даже ради чистоты
схемы.

### VI. Явная обработка ошибок, не общий catch-all в проде

Хендлер, который может упасть предсказуемо, MUST ловить и обрабатывать
эту ошибку сам — не полагаться на глобальный catch-all диспетчера
(логирование + уведомление админа) как способ скрыть баг. `state.clear()`
MUST выполняться до записи в БД в `_finalize_workout`, не после (иначе
двойной тап создаёт гонку). В любом хендлере, где `message` может прийти
из `CallbackQuery`, `telegram_id` MUST браться только из
`callback.from_user.id` (или явного параметра, прокинутого от него),
никогда из `message.from_user.id` — в реальном Telegram сообщение с
inline-кнопкой отправлено ботом, и `message.from_user` всегда бот, не
нажавший.

Rationale: конкретный класс бага (`callback.message.from_user`) терял
тренировку молча, без сообщения об ошибке, потому что ошибка
проглатывалась после `state.clear()` — глобальный catch-all существует
как страховка для непредвиденного, а не как основной путь обработки
предсказуемых случаев.

### VII. Деплой-дисциплина

Миграции, меняющие схему `workouts`, `blocks`, `workout_sets`,
`baselines` или `equipment_items`, MUST быть проверены локально против
непустых таблиц (dev-БД из docker-compose, не только чистая тестовая
БД) прежде, чем `alembic upgrade head` выполняется на проде — и MUST
проверить, нужно ли то же изменение в соответствующей
`*_archive_admin_reset`-таблице (эти таблицы созданы через `CREATE TABLE
... LIKE`, который фиксирует структуру только на момент создания и не
следует за последующими `ALTER TABLE` исходной таблицы). После деплоя
MUST быть выполнена проверка на реальных данных (прямой SQL-запрос или
реальный проход через бота/сервисный слой) — отсутствие ошибок в логах
чистого старта подтверждает только то, что процесс не упал, не то, что
фича работает. Деплой на прод-сервер выполняется явно (`git push` +
ручные SSH-команды или workflow_dispatch), не автодеплоем на каждый push
в main.

Rationale: реальный инцидент (ревизия формулы прогрессии, миграция
`e2c7a4f19d3b`) показал, что баг рассинхронизации архивной таблицы
проявляется только на непустой БД — на пустой `pullup_test` он остался
бы незамеченным до первого реального «Полного сброса» в проде.

## Технологический стек и инфраструктура

Стек фиксирован: Python 3.12, aiogram 3 (long polling, без вебхука),
PostgreSQL 16, SQLAlchemy 2 (async), Alembic, APScheduler, Redis
(FSM-хранилище), gspread, openpyxl; веб-слой Mini App — FastAPI
(`app/web/`) поверх тех же repositories/services/domain, что и бот, без
дублирования логики. Смена любого элемента этого стека — архитектурно
значимое изменение по Принципу II.

VPS `192.241.141.47` разделён с другим проектом (`reeltrack-bot`) — все
`docker compose`-команды MUST выполняться из `/root/pullup-trainer-bot`
без `-p` или глобальных флагов, способных задеть контейнеры соседнего
проекта; порты сервисов этого проекта публикуются только на
`127.0.0.1` или через эфемерный порт (`docker compose port db 5432`),
никогда не занимая порты, которые может использовать `reeltrack-*`.

Фоновые задачи (синк Google Sheets, опрос Robokassa, еженедельные
отчёты) реализуются через APScheduler (`app/workers/`), не через
вебхуки — у бота нет домена/HTTPS для приёма входящих колбэков.
`app.bot.parsing.MAX_REPS` — единственный источник верхнего предела
числа повторений; локальные копии числовых лимитов в отдельных
хендлерах запрещены.

## Рабочий процесс и живая документация

Тесты (`tests/conftest.py`) сами поднимают `db` из docker-compose и
создают отдельную БД `pullup_test`, миграции применяются автоматически.
Перед мержем MUST быть выполнено: `pytest` (весь набор) и
`ruff check app/ tests/`. `settings.is_admin(telegram_id)` — единственный
разрешённый обход продуктовых ограничений (мин. отдых между тренировками,
принудительный выбор снаряда, «Полный сброс», тестовый платёж 1₽) для
проверки вживую; домен (`app/domain/rules.py` и т.п.) об этом обходе не
знает и не меняется — обход существует только в вызывающем bot/repository
слое.

`CLAUDE.md` — живой документ проекта: после значимой новой фичи или
явно установленного нового соглашения он MUST обновляться (добавление
или правка соответствующей записи), не дожидаясь отдельной просьбы.
Записи формулируются по фактическому состоянию кода/истории на момент
правки, не по памяти о более раннем состоянии проекта. Числовые
константы продуктовых решений (не научных фактов — потолок повторений,
шаг прогрессии, стартовый вес) MUST быть явно зафиксированы в докстринге
там, где вводятся, с указанием, что это осознанный выбор, а не выведенная
величина.

## Governance

Эта конституция имеет приоритет над остальными практиками разработки в
проекте; при конфликте с `CLAUDE.md` или обсуждением в PR побеждает
конституция, а `CLAUDE.md` затем обновляется, чтобы устранить конфликт.

Поправки вносятся правкой этого файла и требуют: (1) явного описания
причины изменения (новый инцидент, устоявшееся соглашение, продуктовое
решение), (2) обновления Sync Impact Report в комментарии в начале файла,
(3) версионирования по семантическим правилам ниже. Любой PR, меняющий
архитектуру, схему БД или процесс деплоя, MUST быть сверен с
соответствующим принципом; отклонение от принципа MUST быть явно
обосновано в описании PR, а не молчаливо.

Версионирование конституции — семантическое:
- **MAJOR** — несовместимое назад удаление или переопределение принципа.
- **MINOR** — добавление нового принципа или существенное расширение
  существующего руководства.
- **PATCH** — уточнение формулировок, исправление опечаток, не меняющее
  смысл требований.
