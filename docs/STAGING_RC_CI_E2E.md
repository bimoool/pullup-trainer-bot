## Что утверждает падение

`order` — порядок ответов страницы `back`. Падение значит: **к моменту проверки страница получила два `GET /active` и ни одного
запроса досылки очереди** (ни `events:fail`, ни `events:ok`). То есть проекция дедлайнов прочитана при нулевой попытке
досылки. Сама проверка корректна (в зелёных прогонах `order[0] === "events:fail"`, затем `events:ok`, и только потом `active`).

## Классификация: ошибка наблюдения теста или реальное нарушение drain-before-projection?

Установлено **по коду и экспериментом**:

1. **Ворота стоят правильно.** `startEngineReconciliation` вызывается в `App.tsx` до первого экрана и синхронно ставит
   `holdEngineReconciliation(run)`; `fetchActiveLiveSession` и два чтения списка сессий ждут `awaitEngineReconciliation()`
   (`apiV2.ts:812,1001,1021`). Сбой сети (`httpStatus === null`), 5xx, 408, 429 — transient: очередь цела, повтор с
   задержкой, ворота держатся (`isTransient`).
2. **Но есть путь, где ворота открываются без единой попытки досылки.** `drainEngineQueues`:
   ```ts
   try { queues = await loadAllQueues(store); } catch { return { pending: false }; }  // «хранилище недоступно — досылать нечего»
   ```
   Если чтение IndexedDB при холодном старте упало, сверка считается завершённой, ворота снимаются, `GET /active` проецирует
   дедлайн, а сохранённое действие пользователя остаётся в IndexedDB неотправленным. Эта ветка есть с `60ce46d` (#306 B1), т.е.
   **в BASE**, а не внесена #322/#323; unit-тестов на неё нет.
3. **Эксперимент** (`docs/rehearsal/diag/idb-read-failure.ts.txt`: поток теста №10, но чтение IndexedDB в первые 2,5 с жизни
   страницы `back` падает): 4 из 4 прогонов дали `order = ["active","active"]` без единого запроса досылки за 12 с — **точно
   сигнатура CI**; очередь осталась в IndexedDB (`queues = 1`); в 3 из 4 серверная проекция записала подход целью 15 вместо
   измеренного «Стопа» (журнал `session_events`: `deadline` без `stop`). Один прогон показал `value = 3` при тех же признаках
   неотправленной очереди — механизм этого расхождения я не объяснил (в более раннем прогоне с окном наблюдения 4 с «Стоп» позже всё же оказался на сервере — досылка могла уйти уже после окна; журнал событий не фиксирует время запроса).
4. **Альтернатива «потерянная запись очереди» (UI обновляется раньше `await saveQueue`) не подтвердилась:** `enqueue` в
   `LiveEngineScreen.tsx` действительно делает `setQueue` до записи в IndexedDB, а хелпер тестов 10–12 (в отличие от теста 8)
   не проверяет `storedEngineQueues` перед `page.close()`. Но проба «закрыть страницу сразу после тапа «Стоп» (офлайн)»
   (`docs/rehearsal/diag/stop-close-durability.ts.txt`, под CPU-нагрузкой) сохранила очередь **20 из 20** раз (10 «сразу»,
   10 «после смены фазы»).
5. **Артефакт порядка событий Playwright** маловероятен: в том же прогоне CI тесты 11–13 с теми же слушателями и
   `route.abort`/502 прошли.

## Вывод

* Это **не** доказанная «ошибка наблюдения теста»: проверка корректно ловит состояние «проекция прочитана при нуле попыток
  досылки», и это состояние **достижимо в коде** (п. 2) и воспроизводится инъекцией (п. 3).
* **Не доказано**, что CI-падение вызвано именно сбоем чтения IndexedDB: трасса/сетевой лог не получены, другой механизм с той же
  сигнатурой я не нашёл, но и не исключил.
* Следствие для готовности: пока причина не подтверждена трассой (или не исправлена ветка `catch` в `drainEngineQueues`),
  считать это **возможным реальным дефектом**, а красный CI — блокером. Базовая ветка тоже красная в CI (run 233 на
  BASE `6080159`; зелёный только run 237 на #323), что согласуется с «дефект в BASE», но тоже не доказано — имена упавших тестов
  в тех прогонах мне не доступны.

## Фикс ветки `catch` (сбой чтения IndexedDB ≠ «очередей нет»)

Применён после подтверждения дефекта (п. 2–3): `drainEngineQueues` при ошибке `loadAllQueues` возвращает
`{ pending: true, storeUnreadable: true }`, а не `{ pending: false }`.

* **Ворота держатся**, пока чтение не удастся; сверка повторяет его с теми же ограниченными паузами, что и сетевой
  сбой (`RECONCILE_RETRY_DELAYS_MS`: 1, 2, 4, 8, 15, 15… с, без опроса). После удачного чтения — досылка, и только
  потом `GET /active`/список сессий. Очередь во время сбоя не удаляется и не перезаписывается.
* **Не блокирует навсегда молча:** App показывает `engine-store-error` («Не удалось прочитать сохранённые на
  устройстве данные тренировки… пробуем снова») с кнопкой «Повторить» (`wakeEngineReconciliation`); `online` и
  возврат на экран тоже будят повтор. Баннер исчезает сам после удачного чтения. Остальное приложение работает —
  ждут только чтения с проекцией.
* **Решение по пределу повторов:** ворота после N неудач **не** открываются — это вернуло бы ровно этот дефект
  (цель вместо измеренного). Постоянно нечитаемое хранилище = видимая ошибка + повтор каждые 15 с, а не тихая
  подмена результата.
* idb-keyval 6.3.0 сбрасывает закешированное соединение при неудачном `open` (`dbp = undefined`), поэтому повтор
  действительно открывает IndexedDB заново — проверено E2E №17–18 (восстановление при живой странице).

Тесты: `tests/liveEngineClient.test.ts` — блок «Сбой чтения IndexedDB при сверке» (управляемый `faultyStore` +
сервер на настоящем движке: нет проекции до чтения, восстановление → записано 3, не 15; повторные сбои без
busy-loop и один цикл на пачку стартов; потерянный ответ + сбой чтения → тот же `client_event_id`, один лог;
«перезагрузка» во время сбоя — очередь цела). E2E `live-engine-v2.spec.ts` №17 (автоповтор после восстановления) и
№18 (перезагрузка во время сбоя, «Повторить», одна досылка) с инъекцией сбоя `indexedDB.open` в странице.
Откат одной строки `catch` → 6 unit-тестов красные (в т.ч. «записано 3, не 15»); E2E №17–18 красные на
поведенческой проверке с **сигнатурой CI №10** — `order = ["active","active"]` без единого запроса досылки, а в
`session_events` обеих сессий `deadline` без `stop` (цель вместо измеренного). С фиксом: №8–12, 17, 18 — 5 прогонов
по 7/7 локально (Chromium 141, Playwright 1.63), unit 325/325.

**CI №10 этим не объяснён:** фикс закрывает воспроизводимый путь с той же сигнатурой, но то, что CI-падение
вызвано именно сбоем IndexedDB, по-прежнему не подтверждено трассой (см. «Что нужно, чтобы закрыть», п. 1–2).
