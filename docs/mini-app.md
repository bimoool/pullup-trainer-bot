# Mini App

Перенесено из `CLAUDE.md` без изменения содержания (issue #174) — только
заголовки/порядок. Включает всю историю разработки Mini App: initData,
навигацию, экраны, черновик живой тренировки, лидерборд, ГТО/WSF-разряды,
удаление/редактирование истории на веб-слое, E2E-тестировщик и известный
класс UI-бага с невидимыми полями ввода.

## Mini App: Этап 0 (issue #15)

Домен `app.bimoool.com` подтверждён (2026-08-31) — A-запись резолвится в
`192.241.141.47`, этот VPS. Веб-слой: `app/web/` (FastAPI, тонкий слой
поверх тех же `repositories`/`services`/`domain`, что и бот — не дублирует
логику), `webapp-frontend/` (React + Vite, вне пакета `app`, собирается в
статику и отдаётся тем же FastAPI-процессом одним origin'ом, без CORS),
`Dockerfile.web` + сервис `web` в `docker-compose.yml` (свой контейнер,
свой образ, зависит только от `db`, порт публикуется только на
`127.0.0.1` — физически не может задеть `reeltrack-*` на этом же VPS, см.
шапку файла).

**Готовые библиотеки, не самописный HMAC** (issue #15, коммент от
2026-08-31, референс `taiga-labs/telegram-miniapp-template`):
- Бэкенд — `init-data-py` (`app/web/auth.py::get_validated_init_data`,
  FastAPI-зависимость): выбран, а не `telegram-webapps-authentication`,
  потому что не навязывает свою обвязку над Depends/Header — тонкий слой
  интеграции пишется по тому же принципу, что и остальной проект (бот не
  использует чужой HTTP-клиент для Robokassa как чёрный ящик, см.
  `app/services/robokassa.py`, — берёт готовую проверку подписи и
  оборачивает сам).
- Фронтенд — `@telegram-apps/sdk` (`retrieveLaunchParams().initDataRaw`
  для сырой initData, `init()` на старте) — не `@twa-dev/sdk` (устаревший)
  и не самописная обвязка над `window.Telegram.WebApp`.

**Важная оговорка о проверке.** Обе интеграции написаны без доступа к
npm/PyPI из песочницы Claude (сетевой доступ недоступен, тот же класс
ограничения, что SSH к серверу, см. ниже) — по памяти о публичном API
этих библиотек, не сверено установкой пакета. `tests/test_web/test_auth.py`
специально строит initData САМ, по официальному алгоритму Telegram
(HMAC-SHA256, независимо от внутреннего устройства `init-data-py`), и
подписывает реальным `bot_token` — если имена классов/методов
(`InitData.parse`/`.validate(token, lifetime=...)`/`.user.id`/
`.user.first_name`) в реальности отличаются от использованных здесь, эти
тесты первыми покажут расхождение при первом `pytest`/`docker compose
build web` с доступом к сети. Не мержить/деплоить, не прогнав их хотя бы
раз с реальными пакетами.

**Обновление (issue #23, 2026-09-01): доступ к npm из песочницы Claude
иногда всё же есть** — оговорка выше про полное отсутствие сетевого
доступа не универсальна, зависит от конкретного запуска/окружения.
Когда доступ есть — им стоит воспользоваться (`npm install` в
`webapp-frontend/`, закоммитить получившийся `package-lock.json`, если
его ещё нет, прогнать `npx tsc -b && npx vite build` перед выводами о
типах/сборке), не полагаться на память о публичном API по умолчанию.
Так был найден реальный баг: `@telegram-apps/sdk`'s `retrieveLaunchParams()`
(пакет `@telegram-apps/bridge` под капотом) читает launch params
**только из URL** (`location.href` → `performance` navigation entry →
`sessionStorage`), никогда не обращается к `window.Telegram.WebApp.initData`
(мост старого `telegram-web-app.js`, подключённого в `index.html`).
На живом Telegram Desktop `tgWebAppData` иногда не попадает в URL, хотя
кнопка Mini App правильная (`KeyboardButton(web_app=WebAppInfo(...))`,
не обычная `url=`-ссылка — тип кнопки был не при чём) — фронтенд получал
пустой `initDataRaw` и ошибочно писал "открыто не из Telegram?".
`webapp-frontend/src/App.tsx` теперь фолбэчится на
`window.Telegram.WebApp.initData`, если `retrieveLaunchParams()` пуст
или бросает исключение — тот же initData, другой источник, независимый
от URL-парсинга. Не проверено на живом Desktop-клиенте (сеть до npm ≠
доступ к реальному Telegram-клиенту, это два разных класса ограничения
песочницы) — если фолбэк не поможет, следующий кандидат — точка входа
через постоянную Menu Button (`set_chat_menu_button`/`MenuButtonWebApp`)
вместо `KeyboardButton`, у неё более стабильная кросс-клиентская
поддержка initData по опыту сообщества `@telegram-apps/sdk`.

**Обновление (issue #28, 2026-09-02): фикс #23 не помог, кнопка всё же
не при чём.** После деплоя фолбэка на `window.Telegram.WebApp.initData`
ошибка "initDataRaw is empty" повторилась и на Desktop, и (чёрный экран)
на мобильном. Автор issue заподозрил, что кнопка на самом деле обычная
`url=`-ссылка, а не `web_app=WebAppInfo(...)` — проверено буквально по
коду (`app/bot/keyboards.py`, `bottom_menu_keyboard`): это
`KeyboardButton(text=BOTTOM_MENU_MINI_APP, web_app=WebAppInfo(url=...))`,
настоящая Web App-кнопка, не ссылка. Довод "то же самое в обычном
браузере" не доказывает обратного — вне Telegram initData не появится
никогда ни при каком типе кнопки, это ожидаемо, а не диагностика. Заголовок
открывшегося окна ("Pull-Up Trainer" — имя бота, не `<title>` из
`index.html`, там `pullup-trainer-bot`) — обратное косвенное
подтверждение: это хром именно Telegram Web App, не встроенный браузер по
`url=`-ссылке (тот показывал бы домен/HTML-title). Причина ошибки — в
чём-то другом в цепочке initData внутри самого Telegram-клиента, не
доказано, что именно. `webapp-frontend/src/App.tsx` теперь при пустом
`initDataRaw` формирует сообщение об ошибке с диагностикой (был ли брошен
`retrieveLaunchParams()`, есть ли вообще `window.Telegram.WebApp`, его
`version`/`platform`, `location.href`) — следующий репорт от пользователя
принесёт из этого текста данные, которых сейчас не хватает, чтобы отличить
конкретную причину (скрипт `telegram-web-app.js` не догрузился, `MINI_APP_URL`
на проде не тот/не передеплоен, потеря `#tgWebAppData=...` при 30x-редиректе
до финальной страницы, версия клиента слишком старая для Bot API 6.1+ и
т.п.) вместо одной и той же неинформативной фразы. Не проверено на живом
клиенте (тот же класс ограничения песочницы, что и выше) — следующий шаг
после деплоя ждёт свежий текст ошибки от автора issue, не гадание вслепую.

**Обновление (issue #30, 2026-09-02): найдена настоящая первопричина —
не баг, задокументированное поведение Telegram.** Автор issue нашёл в
официальной документации (`docs.telegram-mini-apps.com/platform/init-data`):
initData гарантированно пустая, если Mini App запущена через keyboard
button (тем способом и открывалась она всё это время,
`KeyboardButton(web_app=WebAppInfo(...))` в нижнем меню) или в
inline-режиме — подтверждено также открытым багом на bugs.telegram.org
про то же поведение на macOS Desktop. Диагностика из #28
(`window.Telegram.WebApp` существует, `retrieveLaunchParams()` не бросает
исключение, просто возвращает пустоту) — ровно то, что предсказывает этот
документированный кейс, не расхождение SDK с реальностью. **Единственный
способ запуска, для которого Telegram официально гарантирует непустую
initData — menu button** (значок слева от поля ввода,
`MenuButtonWebApp`/`bot.set_chat_menu_button`), не keyboard button.
Фикс: `app/main.py::configure_menu_button` вызывается при старте
(`run_polling`, после `set_my_commands`) и ставит `MenuButtonWebApp` (если
`MINI_APP_URL` задан) или явно откатывает на `MenuButtonDefault` (если нет)
— тот же принцип условной видимости, что у прежней кнопки. Кнопка Mini App
в нижней клавиатуре (`BOTTOM_MENU_MINI_APP` в `app/bot/keyboards.py`)
убрана целиком, не оставлена как запасной путь — она гарантированно
воспроизводила бы тот же баг при каждом тапе, оставлять её значило бы
сохранять документированно сломанную точку входа. Не проверено на живом
клиенте (тот же класс ограничения песочницы) — если чёрный экран на
мобильном (issue #28) переживёт получение валидной initData через menu
button, это отдельный баг ErrorBoundary/загрузки скрипта, не initData.

**Что требует доступа к серверу (не проверяемо из песочницы Claude):**
1. Host-level nginx на сервере подтверждённо не установлен (issue #21:
   `which nginx` пусто, `/etc/nginx/sites-available/` не существует) —
   значит `reeltrack-bot` его тоже не использует. Установка (`apt install
   nginx`) и включение конфига из пункта 4 — руками на сервере.
2. Свободны ли порты 80/443, не заняты ли чем-то от `reeltrack-bot`.
3. `certbot`/Let's Encrypt на `app.bimoool.com` — получить сертификат,
   настроить автопродление. `certbot --nginx -d app.bimoool.com` сам
   допишет `listen 443 ssl`/редирект в конфиг из пункта 4, отдельный файл
   под 443 не нужен.
4. Reverse proxy `app.bimoool.com` → `127.0.0.1:${MINI_APP_PORT:-8001}`
   (порт сервиса `web`, см. `docker-compose.yml`; дефолт 8001, не 8000 —
   на проде порт 8000 подтверждённо занят чужим живым процессом, issue #19).
   Готовый конфиг — `deploy/nginx/app.bimoool.com.conf` (issue #21,
   версионируется как `deploy/deploy-run.sh`, применяется на сервере
   вручную командами в шапке файла: скопировать в
   `/etc/nginx/sites-available/`, симлинк в `sites-enabled/`, `nginx -t`,
   `systemctl reload nginx`). Самостоятельный файл на отдельный
   `server_name` — не трогает конфиг `reeltrack-bot`, если тот тоже
   окажется под host-level nginx на этом VPS.
5. Заполнить `MINI_APP_URL=https://app.bimoool.com` в `.env` на сервере —
   до этого кнопка "🚀 Личный кабинет" в нижнем меню бота скрыта
   (`app/bot/keyboards.py::bottom_menu_keyboard`).
6. `docker compose build web && docker compose up -d web` (из
   `/root/pullup-trainer-bot`, без `-p`/глобальных флагов — см. шапку
   файла) и живая проверка: открыть Mini App из бота, увидеть
   "Привет, {имя}" с реальным статусом готовности к тренировке.
7. `webapp-frontend/package-lock.json` уже закоммичен (после первого
   успешного `npm install`/`docker compose build web` с доступом к
   npm-реестру) — при добавлении новых зависимостей в
   `webapp-frontend/package.json` перегенерировать `npm install` и
   закоммитить обновлённый лок туда же, не оставлять package.json без
   него снова.

**Обновление (issue #61): черновик живой тренировки на сервере —
исправление принятого в issue #59 решения держать промежуточные подходы
только в памяти браузера.** На живом использовании подтвердилось, что
закрытие Telegram посреди тренировки в реальном времени (issue #59, режим
"подход → таймер → ввод → ...") — обычное прерывание (звонок, свайп
приложения), а не редкий edge case: старое поведение при обнаружении
активного `ActiveTimer` без данных в памяти намеренно всё сбрасывало
("начни заново"), что на практике означало полную потерю тренировки.

Схема — отдельная таблица `WorkoutDraft`/`workout_drafts`
(`app/db/models.py`, миграция `f1a2b3c4d5e6`), не поле в `ActiveTimer`:
у них независимые жизненные циклы (черновик живёт весь поток тренировки,
таймер — только во время конкретного отдыха, и не всегда синхронно
удаляется при продолжении, см. докстринг `ActiveTimer`) — совмещать в
одной строке было бы источником рассинхрона. Один черновик на
пользователя (unique `user_id`), без snapshot плана (`target`/`work_sets`/
`equipment`) — при восстановлении план перезапрашивается тем же
`GET /api/workout/plan`, что и обычный старт (пока черновик не сдан,
прогрессия не менялась, план детерминирован). `step_index` — единственный
источник позиции в потоке шагов, сами шаги (`buildSteps` в
`LiveWorkoutScreen.tsx`) пересобираются на фронтенде из `work_sets_a/b`
плана, не хранятся в БД.

API — `PUT/GET/DELETE /api/workout/draft` (`app/web/routes.py`,
`WorkoutDraftRepository` — тот же CRUD-без-сервисного-слоя паттерн, что
`ActiveTimerRepository`). `PUT` апсертит целиком (весь накопленный массив
подходов, не один подход за раз) — вызывается после каждого завершённого

сохранение не удалось, показывается ошибка и переход на следующий шаг не
происходит — иначе только что введённый подход потерялся бы молча при
следующем закрытии Telegram. `submit_workout` удаляет черновик сам при
успешной записи (`status == "ok"`), в той же обработке, что и запись
`blocks`/`workouts` — не полагается на отдельный `DELETE` с клиента после
успеха (сеть могла оборваться уже после успешного submit).

произвольная середина шкалы). Ловушка, пойманная до коммита (тот же класс,
что и `user.sound_volume_percent or DEFAULT...` был бы для этого поля): 0 —
валидное значение ("выключить звук"), но falsy в Python — резолвинг обязан
проверять `is not None`, а не truthiness, в отличие от трёх полей длительности
выше (там 0 не бывает, `ge=1` в схеме). По той же причине `TimerPreferencesUpdateRequest`
хранит `duration_seconds`/`sound_volume_percent` как независимые опциональные
поля с `@model_validator` "ровно одно из двух", не общее "значение" —
семантика "0 отдыха" и "0% громкости" разная (первое невалидно, второе
валидно).

Сама по себе регулировка не решала бы жалобу "тихо" при дефолте 100%, если
бы 100% звучали как раньше — поэтому заодно подняты базовые `peakGain` в
`webapp-frontend/src/sound.ts` (`scheduleBeep`) с исходных 0.3/0.2/0.2
(issue #63) до 0.5/0.35/0.35 при 100% громкости, и сама громкость — просто
множитель поверх них. Громкость 0% — отдельная ветка `scheduleBeep`,
возвращающая до планирования осциллятора, а не `peakGain=0`, спущенный в
`exponentialRampToValueAtTime` — Web Audio API не принимает 0 как цель
экспоненциальной рампы (`RangeError`), тот же класс API-ограничения, что уже
учтён в `gain.gain.setValueAtTime(0.0001, ...)` (issue #59) для старта/конца
самого бипа.

Источник правды громкости на фронтенде — module-level переменная в
`sound.ts` (`getSoundVolumePercent`/`setSoundVolumePercent`), не React state
внутри `TimerScreen.tsx`: `TimerScreen` пересоздаётся с новым `key={stepIndex}`
на каждом шаге тренировки (issue #59), обычный state потерял бы
несохранённое изменение громкости при переходе к следующему отдыху. Сидируется
один раз за сессию тренировки в `LiveWorkoutScreen.tsx` сразу после

нативный `<input type="range">` и не компонент из `@telegram-apps/telegram-ui`
(в проекте до этой правки такого использования не было, поэтому неоткуда
было подтвердить его наличие в установленной версии без npm-доступа в этом
запуске — см. оговорку выше про непостоянство сетевого доступа из песочницы

показывал «🔁 Внести пропущенную тренировку»/«➕ Внести свободные

**Фронтенд** — `NO_EQUIPMENT_YET_STATUSES` (`WorkoutScreen.tsx`) прячет обе

уже назначен с прошлой тренировки, кнопки (и факультатив, issue #94)
корректны и не тронуты.

**Бэкенд** — `_resolve_backdate_context` до этого issue сознательно
игнорировал `equipment_setup_required` (issue #52: «бэкдейт про прошлое,

не про то, из чего физически выбирать снаряд.

`GET /free-workout/plan` не тронут — там снаряд никогда не наследуется
автоматически (пользователь всегда выбирает тип/резину/вес явным полем

не `band`), фиктивного снаряжения там в принципе неоткуда взяться.


## E2E-тестировщик Mini App: Playwright + синтетический initData (issue #126)

**Реальный браузерный рендер, не HTTP-моки — дополняет `pytest`, не
заменяет.** `tests/test_web/` проверяет логику API (что вернул JSON), но
не может по конструкции поймать баг вида "кнопка показана, хотя не
должна быть" (именно так был найден issue #123) или необработанное
исключение внутри React — для этого нужен настоящий браузер. Архитектура
initData (обычный HMAC на `BOT_TOKEN`, см. `app/web/auth.py`) делает это
дешёвым: не нужен ни реальный Telegram, ни Telethon-юзербот (в отличие от
полноценного E2E самого бота — по словам автора issue, тот путь отложен
как слишком тяжёлый: живой номер телефона там синтетическими данными не
заменить).

**Структура — `webapp-frontend/e2e/`, отдельный `package.json`/
`tsconfig.json` от `webapp-frontend/`, не общий.** Изоляция намеренная:
`@playwright/test` — devDependency только этого набора, не тянется в
основной фронтенд-бандл/его `package-lock.json`. `fixtures/initData.ts` —
TS-порт `_sign`/`_build_init_data` из `tests/test_web/test_auth.py`, не
второй источник правды: алгоритм сверен не по докстрингу, а прямым чтением
исходника установленной в проекте версии (`init-data-py==0.2.7`, максимум,
удовлетворяющий `>=0.2.7,<1` из `pyproject.toml`) — в частности,
`InitData.calculate_hash()` делает `data_check_string.replace("/", "\\/")`
перед подписью, что в самом `test_auth.py` не покрыто (там нет `/` ни в
одном тестовом значении), но TS-версия это учитывает на будущее.
`fixtures/telegramMock.ts` кладёт initData через `page.addInitScript` в
`window.Telegram.WebApp.initData` — тот же фолбэк-путь кода, что
`App.tsx` использует для реального Telegram Desktop (issue #23/#28), не
подмена `fetch`/API мимо продакшен-логики. `scripts/e2e_seed.py` сидирует
сценарии тем же кодом (`repositories`/`services`), что уже используют
интеграционные `pytest`-фикстуры (`_make_returning_user` в
`tests/test_web/test_workout.py` — сценарий `ready` дословно повторяет тот
же рецепт) — не отдельный сервисный слой заново.

**Первая итерация — 3 сценария из 8 предложенных в issue, остальные
пять — отдельными issue.** Согласовано явно с автором issue:
`not_onboarded`, `first_workout` (обязательный — именно этот статус поймал
issue #123), `ready` (единственный с полным пользовательским путём —
заполнение формы обоих блоков и реальный `POST /api/workout/submit`, не
только рендер статичного экрана). `too_early`/`no_access`/

в `WorkoutScreen.tsx`) и `is_deload_a`/`is_heavy_b` (оба требуют более
сложного сидирования истории — серии блоков с нужной чётностью/датами) —

самого прогона (оба лежат на Azure Blob Storage, вне allowlist песочницы

требуют подтверждения, недоступного автономному запуску, поэтому сам браузер
Playwright ни разу не запускался и живого прогона трёх сценариев всё ещё нет.
Зато появившийся `node_modules` позволил прочитать реальный установленный
исходник `@telegram-apps/sdk`/`@telegram-apps/bridge`, а не полагаться на
память о публичном API — тем же приёмом, что уже раз сработал для
`init-data-py` в предыдущей сессии этого issue.

Находка: `webapp-frontend/src/main.tsx` оборачивает `@telegram-apps/sdk`'s
`init()` в try/catch и намеренно логирует через `console.error("Telegram
SDK init() failed", ...)` (issue #24 — без этого необработанное исключение
роняло рендер ДО первого `<p>Загрузка…</p>`). Чтение исходника `init()`
(`node_modules/@telegram-apps/sdk/dist/index.js`, экспорт `vu`) показало,
что он сам вызывает тот же `retrieveLaunchParams()` (через `oe()`/`Ir()`,
чтобы определить версию SDK, если её не передали явно) — тот же самый
вызов, что App.tsx уже вызывает напрямую и для которого у App.tsx есть
собственный фолбэк на `window.Telegram.WebApp.initData` (issue #23). У
`init()` в main.tsx такого фолбэка нет и не должно быть — он просто ловит
исключение и живёт дальше с дефолтной версией, это и есть весь смысл фикса
issue #24. Но `telegramMock.ts` (эта E2E-сессия) кладёт initData ТОЛЬКО в
`window.Telegram.WebApp.initData` — намеренно не вписывает launch-параметры
в URL/performance entry/sessionStorage (единственные источники, которые
читает `retrieveLaunchParams()`), поэтому `retrieveLaunchParams()`
гарантированно бросает исключение в этом наборе, `init()` гарантированно
ловит его и гарантированно логирует `console.error` — на КАЖДОМ сценарии,
не на каком-то одном. `collectConsoleErrors` (`fixtures/assertions.ts`)
слушает `page.on("console")` с типом `"error"` до первого `page.goto` и
падал на этом ожидаемом сообщении так же, как упал бы на настоящем баге —
`expect(consoleErrors).toEqual([])` был слишком строгим для этой конкретной
(ожидаемой, задокументированной) строки.

Фикс — `EXPECTED_CONSOLE_ERROR_SUBSTRINGS` в `fixtures/assertions.ts`:
`collectConsoleErrors` отфильтровывает сообщения, содержащие "Telegram SDK
init() failed", не трогая остальную логику (`pageerror`/остальные `console`
типы по-прежнему ловят реальные баги). Не исправление продакшен-кода
(`main.tsx` не тронут — поведение issue #24 там правильное и не нуждается в
изменении) — исправление самого набора, который предъявлял приложению
требование строже, чем оно само себе ставит.

**По-прежнему не проверено вживую** — это статический вывод из чтения
реального установленного исходника SDK, не подтверждение прогоном
Playwright (браузер запустить в этой сессии так и не удалось, см. выше).

**Обновление: третий реальный прогон в CI (после обоих фиксов выше) упал
иначе — все три сценария одинаково, не только `ready`, найдено чтением
`index.html`, не логами (Azure Blob для этого прогона тоже был вне
allowlist).** Единственная детальная трасса, которую автор issue смог
прочитать сам в отчёте Playwright, — `ready.spec.ts` не находит "Текущий
план"; но список упавших тестов включал и `not-onboarded.spec.ts`, у
которого нет НИКАКОЙ зависимости от плана/сценарных данных (ждёт
`getByLabel("Число подтягиваний")` сразу после открытия). Падение теста,
не зависящего от seed-данных, рядом с падением тех, что зависят, — прямой
сигнал, что причина ОБЩАЯ для самой загрузки приложения, а не в
конкретном сценарии/сидировании (то же рассуждение, что уже правильно
предложил автор issue в комментарии, приведшем к этому разбору).

Причина — `webapp-frontend/index.html` грузит настоящий
`https://telegram.org/js/telegram-web-app.js` блокирующим `<script>` в
`<head>`, БЕЗ `async`/`defer`. `page.addInitScript`
(`fixtures/telegramMock.ts`) гарантированно выполняется раньше ЛЮБОГО
скрипта страницы — но это не помогает, потому что "раньше" не то же
самое, что "последний": сам `telegram-web-app.js`, выполняясь ПОСЛЕ
addInitScript вне настоящего Telegram-клиента, тоже пишет в
`window.Telegram.WebApp` — своим собственным объектом с пустым `initData`
— целиком ПЕРЕЗАПИСЫВАЯ то, что только что положил мок, а не дополняя
его. `App.tsx` в фолбэке (issue #23) получает `telegramWebApp.initData ===
""` и уходит в ветку "initDataRaw is empty" ещё до первого запроса к
`/api/hello` — одинаково на каждом сценарии, независимо от того, что
сидировал `scripts/e2e_seed.py` под конкретный `telegram_id`. Это

## Редактирование/удаление личных резин в Mini App (issue #148)

**До этого issue список резин (`EquipmentItem`) был только `POST`/`GET`
(issue #124, PR 3) — ни переименовать, ни удалить ошибочно заведённую
резину было нельзя ни в одном интерфейсе.** `PATCH`/`DELETE
/api/equipment/band-items/{id}` (`app/web/routes.py`) закрывают это;
`EquipmentItemRepository.rename`/`.delete` — ownership-проверка (404, не
403, тем же принципом, что и остальные проверки в этом файле).

**Удаление — настоящий `DELETE`, не архивация.** Резина — личный
справочник пользователя, не история тренировок (в отличие от
`workouts`/`blocks`, которые архивируются при "🧪 Полный сбросе") — прямое
удаление здесь корректно и ожидаемо.

**Схема была устроена так, что удаление сломало бы историю — это
поправлено как часть issue, не оставлено.** `blocks.equipment_item_id`/
`elective_workouts.equipment_item_id` были FK без `ON DELETE` (то есть
Postgres по умолчанию `RESTRICT`) — `DELETE` на уже использованную резину
падал бы `IntegrityError`. Миграция `e7c2a4f9d1b3` меняет обе FK на
`ON DELETE SET NULL` и добавляет `Block.equipment_item_name`/
`ElectiveWorkout.equipment_item_name` (+ `blocks_archive_admin_reset`, по
правилу "пяти архивных таблиц" из раздела "Процедура деплоя" выше) —
снапшот названия резины НА МОМЕНТ этой конкретной тренировки, заполняется
`WorkoutRepository`/`ElectiveWorkoutRepository` при записи блока (не
задним числом при удалении — переименование резины после тренировки не
должно менять то, что показывает уже записанная история). Бэкфилл в той
же миграции — до этого issue резину нельзя было переименовать, значит
текущее `equipment_items.name` совпадает с названием на момент любой уже
существующей записи. `WorkoutDraft.block_*_actual_band_item_id` — не FK
(черновик не хранит снапшот плана вообще, issue #61), `EquipmentItemRepository.delete`
обнуляет их вручную, чтобы черновик не указывал на исчезнувший id.

**Побочный найденный баг (не потребовал доступа к проду, поймано чтением
кода `current_equipment_progress`/`_same_equipment`, `app/domain/reports.py`
+ идентичный предикат в `app/domain/recommendations.py`) — две РАЗНЫЕ
удалённые резины выглядели бы "тем же снарядом".** Сравнение "тот же
снаряд" для BAND шло по `equipment_item_id`; после того как удаление стало
возможным, `equipment_item_id` может быть `None` у двух исторически разных
резин (обе удалены) — без тай-брейка `_same_equipment` считала бы их одним
непрерывным сегментом (`None == None`), склеивая несвязанный прогресс.
Исправлено: если у обеих сторон `equipment_item_id is None`, сравнение
идёт по `equipment_item_name` (снапшот) вместо `id`; пока хотя бы один
`id` не `None` — сравнение как раньше, поведение не изменилось. Тесты —
`tests/test_reports.py::test_current_equipment_progress_deleted_band_still_merges_by_name`/
`test_current_equipment_progress_two_different_deleted_bands_do_not_merge`.

**Решение по п.4 issue (резина, которая сейчас активный унаследованный
снаряд блока) — удаление РАЗРЕШЕНО безусловно, не заблокировано.**
Рассмотренные варианты:
1. Блокировать `DELETE`, если резина используется в актуальном плане
   (`_resolve_next_state`/`resolve_next_targets` вернули бы её как
   унаследованную) — самый безопасный для пользователя вариант, но требует
   отдельного запроса "не используется ли эта резина прямо сейчас" перед
   каждым удалением и отдельного статуса ошибки в UI ("нельзя удалить,
   используется") — заметно больше кода ради узкого случая.
2. **Разрешить всегда (выбрано).** `blocks.equipment_item_id` у
   унаследованной записи станет `NULL` (та же миграция), `equipment_type`
   останется `BAND` — следующий план (`GET /api/workout/plan`) вернёт
   `equipment_a/b.item_id = null` при `type = "band"`. Mini App уже умеет
   показывать явный выбор/заведение резины для этого случая — тот же
   `BandItemSelect`, что и для первой тренировки на резине (issue #124, PR
   3), просто триггер выбора расширен: раньше обязательный выбор резины
   требовался только при `plan.is_first_workout`, теперь — также при
   `item_id === null` независимо от `is_first_workout`
   (`WorkoutScreen.tsx::handleSubmit`, `missingBand`). Если пользователь не
   тронет поле, `POST /api/workout/submit` унаследует `item_id = null` —
   сервер не подставляет несуществующий id молча (`_resolve_explicit_equipment`
   этой веткой не затронут, там валидация уже была).

Выбран вариант 2 — согласуется с тем, как проект уже устроен: бэкдейт/
факультатив/живая тренировка ни разу не блокируют действие ради
консистентности справочника, вместо этого дают пользователю выбрать
заново там, где выбор нужен (тот же принцип, что "равнозначный ввод резины
для первой тренировки", issue #124). Не проверено на живом клиенте (тот же

**Обновление: реальный прогон интеграционных тестов автором продукта нашёл
`MissingGreenlet` в `test_delete_band_item_already_used_in_workout_does_not_
break_history` — баг оказался в самом тесте, не в `WorkoutRepository`.**
Строка `user_row = await UserRepository(session).get_by_telegram_id(53044)`
шла ДО `session.expire_all()`, а `user_row.id` читался ПОСЛЕ — и поскольку
общая для теста `AsyncSession` уже держала этот `User` в identity map
(создан в начале того же теста), `get_by_telegram_id` возвращал тот же
самый Python-объект, не новый; `expire_all()` пометил его (как и всё
остальное в identity map) expired, включая PK-атрибут. Синхронное чтение
`user_row.id` при вычислении аргумента для
`WorkoutRepository(session).resolve_next_targets(user_row.id)` происходит
ДО того, как этот `await` реально запускается (Python вычисляет аргументы
вызова раньше, чем передаёт управление корутине) — то есть вне
`greenlet_spawn`-контекста, в котором `AsyncSession` обычно прячет
синхronous ORM-код. Отсюда и `MissingGreenlet` ровно на этом вызове, хотя
сам `_resolve_next_state`/`resolve_next_targets` ни при чём — все их
операции с `Block`/`Workout` идут через уже awaited `list_for_user`,
объекты которого `selectinload` полностью "освежает" по своим же column-
атрибутам даже после `expire_all()` (проверено отдельным изолированным
воспроизведением на SQLite/`aiosqlite` — тот же паттерн `expire_all()` +
`selectinload` + синхронное чтение колонки работает без ошибок; тот же
эксперимент с чтением PK-атрибута уже expired объекта как аргумент вызова
`async def`-функции воспроизвёл именно `MissingGreenlet`, байт-в-байт то
же сообщение). Фикс — `tests/test_web/test_equipment_band_items.py`:
`user_id = user.id` захватывается из уже существующей переменной `user`
ДО `session.expire_all()` (обычный python `int`, не атрибут ORM-объекта),
повторный `get_by_telegram_id` убран как не нужный вовсе. Правило на
будущее для тестов, использующих этот приём эмуляции "следующего HTTP-
запроса" (`session.expire_all()` посреди теста, см. и другие интеграционные
тесты `tests/test_web/`) — захватывать любые значения, нужные ПОСЛЕ
`expire_all()`, в обычные переменные ДО него, не читать их с ORM-объекта
после.
