# Наше приложение: офлайн-сценарии в браузере на изолированном стенде (2026-10-29)

**Граница.** Браузер (встроенный браузер Claude, viewport 375×812) + изолированный стенд SHA `e3dd640` (:8021), синтетический пользователь 800002, БД `pullup-gap2-pg`. **Это не реальный iPhone и не Telegram**: поведение Telegram WebView на iOS, фоновая выгрузка страницы, `online`/`offline`-события и wake-lock здесь не проверялись и подтверждёнными не объявляются. Продуктовый код не менялся, production не затрагивался.

**Средство.** `tools/netproxy.py` — прокси :8022 перед стендом с режимами для `/api/*`: `pass`, `drop` (закрыть соединение, на бэкенд не пересылать), `drop_response` (запрос ПРИМЕНЁН на бэкенде, клиент ответа не получает — худший случай для дублей), `delay:N`. Журнал запросов `GET /__log`. Нужен именно такой, а не отключение сети браузера: встроенный браузер не имеет переключателя «офлайн».

Тренировка: «Максимум подтягиваний» (живая сессия v2, 4 подхода), сессия id 2.

## Вывод для пользователя (факты, не оценка приоритета)
- Идемпотентность на двух уровнях (серверный `client_event_id` + клиентская очередь в IndexedDB) выдержала обрыв запроса и обрыв ответа: ни потери, ни дубля в проверенных сценариях.
- Слабое место — только состояние «страница перезагружена при обрыве»: пользователь видит сырую ошибку без кнопки и без подсказки, что данные сохранены; экран не оживает при возврате сети (S3–S4).
- Сообщения об ошибке содержат сырой текст браузера («Failed to fetch») на английском (S1, S2, S3).

## Не проверено (причина)
Реальный iPhone/Telegram (нет управляемого устройства — см. `../remaining-queue.csv` Q17); события `online`/`offline` браузера; отключение сети во время загрузки статики (проксировались только `/api/*`); офлайн на старте приложения без кэша (кэш GET через react-query не исследовался отдельно); экраны, кроме живой сессии (История, Профиль, правка записи, бэкдейт); `delay:N` не прогонялся отдельно (его эффект перекрыт `drop_response`).
