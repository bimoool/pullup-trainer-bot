# Минимизация нового сбора данных — план 5 ноября 2026

Статус: модель согласована владельцем, реализация ещё не выполнена. Production
заблокирован до пересмотра сбора данных и проверки результата. Проверка технического
кандидата PR #372 на staging сама по себе этот запрет не снимает.

Согласовано: убрать новый сбор роста; запрашивать вес перед расчётом, которому он
нужен; пол и дату рождения сделать добровольными для нормативов/сравнений;
часовой пояс выбирать без свободного ввода города. Добровольный личный дневник
остаётся. Существующие профили, заметки, история и связь аккаунта сохраняются.

## Контракт и точные примеры

1. Новый аккаунт: замер **8**, пояс **Asia/Yekaterinburg**, пол/дата не указаны.
   Завершение анкеты успешно. `weight_kg`, `height_cm`, `gender`, `birth_date` — NULL;
   новых строк `user_body_metrics` нет. Замер = 8, учётная запись одна, пробный доступ
   по действующему правилу 7 дней. Рост и вес не являются шагами анкеты.
2. Добровольные нормативы: тот же аккаунт выбирает `male`, **1996-03-15**.
   На дату **2026-11-05** возраст = **30**. Эти поля сохраняются только после явной
   отправки; пропуск обоих или любого одного разрешён. Отсутствующий вход означает
   честное «не хватает данных для норматива», а не вымышленный пол/возраст.
3. Нужен расчёт с массой тела: `body_mass_kg` отсутствует. Настройка курса показывает
   существующий обязательный вход «Ваш вес (масса тела)»; старт/1RM не считает массу
   равной 0, 70 или иной подставленной величине. После ввода **78.5 кг** используется
   ровно **Decimal('78.5')** в существующем входе/снимке курса. Формула не меняется.
   Перед реализацией проверить также legacy-путь бота: отсутствие массы не должно
   обходить проверку или молча менять подсказку тяжёлого веса.
4. Существующий аккаунт: вес **78.5**, рост **180**, дата **1996-03-15**, **2** старые
   тренировки. Новая анкета отправляет только пояс. После неё все старые значения и
   обе тренировки сохранены; пустые/пропущенные поля не являются командой удаления.
5. Повторный вход после смены Telegram username: тот же внутренний `users.id`, тот же
   замер/план/журнал; новые username не сохраняются. Другая Telegram identity не
   получает чужую историю. Подпись Telegram проверяется по прежнему алгоритму.
6. Дневник: новая добровольная заметка сохраняется в личной истории; её пропуск
   разрешён. Заметки не добавляются к диагностике исключений. Старые записи и
   неотправленные offline-очереди не удаляются новой анкетой.
7. Пояс в боте: выбор **UTC+5 / Asia/Yekaterinburg** даёт ровно этот IANA-id. Ввод
   неизвестного города не завершается молчаливым выбором Москвы. После рестарта
   пользователь может закончить анкету с валидным выбором; старый Redis FSM не
   возобновляет обязательный сбор веса/роста.

## Порядок реализации

1. Сначала регрессии примеров 1–7 на синтетическом Postgres и реальные Dispatcher
   updates; зафиксировать ожидаемый отказ старого кода.
2. Серверный контракт анкеты: обязательный валидный timezone; добровольные пол/дата;
   вес/рост исключены из нового onboarding write-path. Старые колонки не удаляются.
   Явно определить совместимость старых клиентов, присылающих прежний payload:
   они не должны незаметно возобновить сбор удалённых полей.
3. Bot FSM и Mini App: короткая анкета, явный пропуск добровольных полей, выбор пояса;
   переходы «Назад»/повторный вход/рестарт не возвращают обязательные вес/рост.
4. Убрать новый ввод роста также из правки профиля/замеров; старую историю показывать
   только как историю. Вес запрашивать в контексте нужного расчёта, не на входе.
   Не подменять это одним скрытием полей в UI: проверить API write-paths.
5. Подтвердить курс и legacy-бот без массы/с массой, нормативы при неполном профиле,
   серверную синхронизацию двух клиентов и невозможность чтения чужих объектов.
6. Обновить существующие onboarding E2E под согласованное поведение, сохранив
   проверки прогрессии/подписок/сохранности. Focused → полный Linux gate → реальные
   fresh/aged staging-проходы, WebKit/Chromium и собственный Telegram WebView.

## Отдельные незакрытые вопросы перед production

- Минимизация не равна анонимизации: серверная история связана с Telegram identity.
  Нельзя обещать «персональные данные не обрабатываются».
- Нужны согласованные политика/цели/сроки хранения и процедура обращения по данным,
  включая events, Redis FSM, backups и ранее созданные внешние копии.
- План хранения/переноса инфраструктуры остаётся отдельным решением владельца;
  эта работа не создаёт платных ресурсов и не переключает production.
- Требуется отдельный аудит web/worker/proxy diagnostics: исправления глобального
  bot error handler и поддержки не доказывают отсутствие всех возможных утечек.
- Старые данные не удаляются автоматически. Любая отдельная очистка требует
  понятного scope, восстановления, dry-run и специального разрешения.
