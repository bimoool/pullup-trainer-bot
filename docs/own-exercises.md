# Собственные упражнения: что есть и план переименования/архивации

Состояние на `6475bc0` (аудит staging, приоритет 2). Проверено API-тестами под двумя обычными пользователями —
`tests/test_web/test_v2_own_exercises_two_users.py`.

## Что работает сейчас

- **Создание:** `POST /api/v2/exercises` (только `name`) → `Exercise(source_type="user", owner_user_id=<я>,
  visibility="user", category «Мои упражнения»)`. Вход в UI — «Добавить упражнение» в редакторе своей
  тренировки (`ExercisePickerScreen.tsx`: «Создать своё упражнение: «…»»).
- **Повторное использование:** одно и то же упражнение добавляется в несколько своих тренировок и в план
  (`POST /workouts/{id}/items`, `POST /plan-items`) — строка `Exercise` одна, копий нет.
- **Изоляция:** чужое упражнение не возвращается `GET /exercises`, не прикрепляется к тренировке или плану
  (404, не 403 — существование чужого не раскрывается), своя тренировка с ним не попадает в общий каталог
  `GET /workouts/catalog` и не открывается другим (`GET /workouts/{id}` → 404).
- **Переименования и удаления/архивации нет** — ни эндпоинта, ни UI (`create_exercise`: «rename/delete/update —
  явно вне scope этой волны»). В таблице `exercises` нет колонки архива.

## Почему нельзя просто добавить `PATCH name`

Название упражнения в истории берётся из **живого** `Exercise.name` везде, где у тренировки нет `workout_snapshot`:
вручную записанные/бэкдейт-тренировки из одного упражнения, старые сессии, фолбэк CSV-экспорта
(`routes_v2.py::_session_response` → `_catalog_exercise_names`, `history_export.py`). Проба на `6475bc0`:
тренировка «Старое» (бэкдейт, 1 подход × 5), затем `UPDATE exercises SET name='Новое'` → `GET /api/v2/sessions`
показывает «Новое». Переименование без снимка переписало бы прошлые тренировки — нарушение требования
«изменение упражнения не меняет снимки выполненных тренировок».

Удаление строки невозможно и не нужно: `session_blocks`, `plan_items`, `complex_items`, `program_items` ссылаются на
`exercises.id` без `ON DELETE` (RESTRICT) — «архивировать, не удалять» (CLAUDE.md).

## План (нужна миграция — на согласование, не реализовано)

1. **Миграция** (одна, обратимая):
   - `exercises.archived_at TIMESTAMPTZ NULL` — без бэкфилла (все NULL = активны);
   - `session_blocks.exercise_name TEXT NULL` + бэкфилл одним `UPDATE … FROM exercises` для всех
     существующих блоков (имя на момент миграции = то, что пользователь видит сейчас; ничего не меняется
     на экране). Таблица `session_blocks` не входит в пять `*_archive_admin_reset`-таблиц
     (`b41882a0e3e8`) — зеркалить не нужно, проверить при ревью.
2. **Запись снимка:** при создании блока сессии (live start, `POST /sessions`, бэкдейт, копия) писать
   `exercise_name` = текущее отображаемое имя.
3. **Чтение истории:** `_session_response`, заголовки одиночных сессий, CSV-экспорт — порядок
   `session_blocks.exercise_name` → `workout_snapshot` → живое имя (только для строк без снимка).
   Аналитика остаётся на живом имени аналитической идентичности (это «что за упражнение», не «как называлось»).
4. **API** (владелец, иначе 404; системные — 404):
   - `PATCH /api/v2/exercises/{id}` `{name}` — те же правила, что у создания (1–255, trim);
   - `POST /api/v2/exercises/{id}/archive` и `/unarchive`.
   Архивное: не в `GET /exercises` и пикерах, не прикрепляется заново (`get_plan_attachable…`,
   `get_visible…` для добавления); уже стоящие в плане/тренировках строки остаются и показываются с пометкой
   «в архиве»; история не меняется. `ExerciseResponse` получает `source_type` (сейчас клиент различает своё
   только по категории «Мои упражнения»).
5. **UI:** в «Добавить упражнение» у своих упражнений — «⋯» → «Переименовать», «В архив» (подтверждение через
   `confirmAction`); раздел «Архив» с «Вернуть».

**Пример с числами.** У A упражнение id 501 «Узкий хват», три выполненные тренировки (12, 13, 14 окт) и строка
плана на 16 окт. После `PATCH {name: "Узкий хват (резина)"}`: журнал за 12–14 окт — «Узкий хват»; план на 16 окт и
библиотека — «Узкий хват (резина)»; тренировка 16 окт сохранит «Узкий хват (резина)». После «В архив»: в пикере
501 нет, строка плана на 16 окт остаётся с пометкой «в архиве», журнал без изменений. B ни на одном шаге
упражнение 501 не видит; `PATCH`/`archive` от B → 404.

**Тесты на каждый пример плана:** снимок не меняется после rename (бэкдейт, live, копия); чужой/системный → 404;
архивное не в списке и не прикрепляется, но стоящая строка плана жива; бэкфилл миграции даёт те же имена,
что `GET /sessions` до миграции.
