# PROJECT_SPEC — принятое продуктовое поведение

Репозиторий — единственный канонический источник истины. Не чат, не память агента, не
удалённая переписка. Всё, что принято как поведение продукта, записано здесь; чего здесь нет
и нет в коде/тестах — не принято.

**Порядок приоритета** (при конфликте выигрывает верхний; нижний затем исправляется):
1. `.specify/memory/constitution.md`
2. этот файл (`docs/PROJECT_SPEC.md`)
3. `docs/IMPLEMENTATION_PLAN.md`
4. `docs/ENGINEERING_NOTES.md`, `docs/adr/*`, `.claude/skills/*`
5. код и тесты как факт текущего состояния (не как источник решений)

Нет ответа на продуктовый вопрос в этих документах → **остановиться и спросить владельца
продукта**, не придумывать решение.

**Мандат владельца (2026-10-02):** Crimpd 8.5.x is the full functional UX reference. Replicate
user-visible capabilities where technically possible, adapted to our training domain. Differences
require an explicit documented domain/platform reason. Статус каждой возможности —
`docs/CRIMPD_FULL_PARITY_8_5.md`. Ограничения ниже («нет поиска», «не выдумываем длительность»)
описывают **текущее** состояние и снимаются соответствующими parity-issues, которые обновляют
этот файл в том же изменении.

## 1. Термины

| Продукт | Техническое хранилище |
|---|---|
| Workout | `Complex` (`complexes`) — без rename |
| WorkoutItem | `ComplexItem` (`complex_items`) — без rename |
| Exercise | `Exercise` |
| PlanItem | `PlanItem` — строка недельной матрицы плана |
| Сессия / блок | `TrainingSession` / `SessionBlock` (+ `SetTarget`, `SetLog`) |

Определения (`Complex`, `ComplexItem`, `Exercise`, `PlanItem`) при любых операциях над
сессиями не изменяются и не удаляются. Дерево сессии — `TrainingSession` →
`SessionBlock` → `SetTarget`/`SetLog`, плюс `SessionPlanItem`.

Протоколы блока (`app/domain/workout_protocol.py`, ADR `docs/adr/WORKOUT_PROTOCOL_V1.md`):
`reps_sets`, `time_sets`, `max_effort`, `interval`.

## 2. Исполнение Workout (Builder)

1. **Цели из prescription.** Для Builder-блока цели подходов выводятся из resolved-протокола
   замороженного снимка: `reps_sets` — подходы×повторения; `time_sets` — подходы×секунды;
   `max_effort` — число попыток (цели нет, `value = 0` не является планом); `interval` — ноль
   целей (таймер). `ComplexItem.sets/target_value` при наличии протокола не используются.
   Legacy (`protocol = None`) ведёт себя как раньше.
2. **Замороженное определение.** Builder-сессия хранит `TrainingSession.workout_snapshot`.
   Идентичность протокола и имени упражнения блока — из снимка по позиции (блок *i* ↔ пункт *i*),
   а не из изменяемого `ComplexItem`.
3. **`SessionBlock.started_at`** — nullable. Блок 0 начинается вместе с сессией (эффективное
   время — `performed_at`); остальные блоки Builder-тренировки получают его при явном старте.
4. **Смешанные блоки.** Одна Workout может содержать, например, reps → interval → max.
   Исполнение идёт блок за блоком по `TrainingSession.current_block_index` (второго индекса
   нет).
5. **Ручной переход.** После завершения блока следующий НЕ стартует сам: показывается
   interstitial «Готово ✓ / Следующее упражнение / <название · план> / Начать»; блок начинается
   только явным «Начать» (`POST /api/v2/sessions/live/{id}/blocks/start`, идемпотентен).
   «Пропустить» нет. Правило действует только для Builder-сессий; STEP и legacy-комплексы без
   протокола продолжают автоматический переход.
6. **Interval — серверное время.** Таймер считается от `SessionBlock.started_at` блока (+ 5 с
   подготовки). Истёкший interval-блок в середине тренировки пишет результат и продвигает
   `current_block_index` к следующему НЕ начатому блоку; только последний блок завершает
   сессию. Не начатый interval-блок не проецируется как активное interval-состояние.
7. **Обычный блок в середине** продвигает сессию к следующему блоку, но не завершает её.
   STEP/программное поведение не меняется.
8. **Дубли упражнения.** Запись подхода адресуется блоком (`block_index`), не только
   `exercise_id`; без `block_index` — текущий блок сессии.
9. **Локальное состояние (IndexedDB/офлайн).** Не переносится из блока в блок: сбрасывается на
   переходе, не переиспользуется, если отстаёт от сервера.
10. **Summary** показывает каждый блок независимо (interval в любой позиции), без сырых id,
    JSON протокола и «8.00 reps».
11. **Дубли запросов безопасны.** Одинаковые `sets:batch`, пришедшие одновременно (реконнект +
    «Завершить»), сходятся к одной строке на `(session_id, set_index)` и оба получают 200.
    Повторный/конкурентный `complete` уже завершённой сессии — 200 с текущим состоянием и
    `progression_skipped_reason = "already_completed"`: прогрессия применяется ровно один раз.
    Клиент досылает офлайн-очередь одним флашем за раз (single-flight).
12. **Оценка тренировки при завершении (#257).** «Завершить» открывает review-шаг:
    «Как прошла тренировка?» (шкала 1–5, необязательно) и «Заметка» (необязательно); «Сохранить
    и завершить» — явное подтверждение. `POST …/complete` принимает необязательные `effort`
    (1–5) и `comment` (≤1000, пустой → null), хранит их в `TrainingSession.effort/comment`;
    невалидное → 422. Повторный `complete` никогда не затирает сохранённое (null/другое
    значение игнорируется, заполняется только пустое). Оценка и заметка очередью офлайн
    (`completeRequested`) уходят вместе с `complete`; на прогрессию **не влияют**. Эффорт
    подхода — те же сохранённые 1–5, подписи: 1 Очень легко · 2 Легко · 3 Средне · 4 Тяжело ·
    5 Предел, вопрос «Насколько тяжело было?». Журнал показывает оценку со словом и заметку.
    BackButton-выход по-прежнему завершает через confirm без review.
13. **Ещё подход и пауза (#264).** После последнего планового подхода блока (экран `done` или
    interstitial перед следующим блоком) reps/time/max-блок показывает «+ Ещё подход»: форма
    значения → подход уходит обычным `sets:batch` с `is_extra: true`, пишется как `SetLog` с
    `is_extra = true` (аддитивная колонка, default `false`) в завершённый блок, **не** двигает
    фазу и не является целью; офлайн — через ту же очередь `pendingSets`. Идемпотентность по
    `(session_id, set_index)` и exactly-once `complete` не меняются. **Прогрессия игнорирует
    extra-подходы** (STEP: `_session_block_input_from_detail` отфильтровывает `is_extra`; других
    потребителей «всех логов» у live-complete нет). Известный пробел: правка исторической
    сессии (`update_set_logs_for_blocks`) перезаписывает подходы блока без extra-флага.
    **Пауза** — «Пауза»/«Продолжить» на обратном отсчёте (`get_ready`, `rest`): остаток
    замораживается в локальном снимке IndexedDB (`pausedRemainingMs`), «Продолжить» ставит
    новый конец фазы (`endsAtOverride`); переживает reload/фон. Сервер таймер не ведёт —
    пауза чисто клиентская; при синхронизации она сохраняется, пока серверная фаза (номер
    перехода/позиция) та же, и сбрасывается при любом переходе. Interval-блоки (серверные часы,
    безопасно паузить нельзя) живут на отдельном экране и паузы не предлагают.
    **Панель записи подхода следует за таймером (#265)** — во время «Пошёл» свёрнута: поле
    результата + «Готово», оценка/заметка раскрываются вручную («Оценка и заметка»). На
    отдыхе ≥ 20 с панель только что записанного подхода (значение, усилие, заметка)
    раскрывается сама, на коротком отдыхе свёрнута (сводка + «Изменить»). Правка («Сохранить
    подход», либо автоматически при «Пропустить отдых»/«Завершить») — тот же `set_index` в
    `sets:batch` (сервер перезаписывает строку, дубля нет), редактируется до начала следующего
    подхода; последний подход блока (без отдыха) правится только до «Готово». В последние 10 с
    любого отдыха под таймером показывается «Приготовься · N»; звук конца фазы прежний.
    Состояние выводится из локального снимка (`lastLogged`, метки времени фаз) — работает
    офлайн и после reload/фона; формат хранимых данных не меняется.

**Фон/блокировка (#269).** Все обратные отсчёты (отдых, «Приготовься», interval) считаются из
абсолютных меток (`ends_at`, `execution_started_at` + серверный сдвиг часов), а не декрементом, и
пересчитываются на `visibilitychange → visible`: ОС не «ставит таймер на паузу». Фаза, истёкшая в
фоне, показывает 0:00 и сама ничего не переключает и не пишет (переход — только действие
пользователя, у interval — один дедлайн-вызов `blocks/finish`). Звук конца фазы уходящим в фон
снимается и на возврате планируется заново только для ещё идущей фазы — для истёкшей в фоне
бипа нет. Wake Lock берётся заново на возврате, пока открыт экран сессии, и снимается при
завершении/выходе. Платформенный предел: Mini App — WebView в Telegram, без Live Activity /
Dynamic Island / управления с экрана блокировки / фонового звука (docs/CRIMPD_FULL_PARITY_8_5.md,
раздел Platform); вместо этого — точный пересчёт при возврате, Wake Lock и напоминания бота.

Перезагрузка в любой момент восстанавливает состояние с сервера: активный блок, interstitial
перед не начатым блоком, идущий interval.

## 3. Журнал v2

Список — завершённые `TrainingSession`; **не** сливается с legacy-историей (две разные
хронологии, пока владелец не решит иное).

- **Карточка** — каждый блок независимо (нет допущения «`blocks[0]` определяет протокол»):
  reps `Подтягивания / 8 · 7`; time `Планка / 0:30 · 0:25`; max
  `Отжимания · Максимум повторений / 2 попытки · лучший 22`; interval
  `Бёрпи · Интервалы / 0:04 · 2 интервала`. Не показываются: сырые id, JSON протокола,
  «8.00 reps», фальшивый план «0:00» из нулевых целей.
- **API** отдаёт по блоку `protocol_type` (из снимка), `exercise_name`, `started_at`,
  `set_targets`, `set_logs`, `result`, `interval_config`.
- **Детали** открываются из уже загруженного объекта списка (отдельного endpoint нет): название,
  дата/время, каждый блок, протокол, план/факт там, где осмысленно, комментарий/усилие.
  Навигация — Telegram BackButton и видимая кнопка «← Назад» вызывают один и тот же обработчик.
- **Пагинация** — существующий `GET /api/v2/sessions` (`limit`/`offset`, `has_more`), страница
  25, «Показать ещё»: без дублирующих запросов, слияние по `id`, сбой догрузки не стирает
  загруженное, удаление не сдвигает следующий offset, возврат из деталей сохраняет список.
- **Календарь и группировка (#256)** — вверху Журнала месяц-бар «‹ Октябрь 2026 ›»: стрелки
  меняют месяц, тап по подписи раскрывает/сворачивает календарь (Пн-первая сетка), точка у дня
  с хотя бы одной завершённой тренировкой (v2 и legacy). Тап по дню выбирает его (список — только
  этот день), повторный тап снимает выбор; смена месяца сбрасывает выбор. Список сгруппирован
  «неделя (Пн–Вс) → день», карточки/детали/удаление/правка без изменений. Пустой месяц —
  «В этом месяце тренировок нет» (день — «В этот день тренировок нет»). Стартовый месяц — текущий
  в поясе пользователя; если он пуст, а тренировки есть — месяц самой свежей.
- **Данные по месяцам, без полного скана**: `GET /api/v2/journal/days?month=YYYY-MM` →
  `{month, timezone, days:[{date,count}], latest_month}` (неверный месяц — 422);
  `GET /api/v2/sessions` и `GET /api/history` принимают `date_from`/`date_to` (включительно).
  День v2-сессии — локальный день пользователя (`user.timezone`, дефолт Europe/Moscow, как в
  Analytics v2); день legacy `Workout` — показываемая на карточке дата (`performed_at.date()`).

- **Перенесённые backfill-ом тренировки не дублируются (#282 → #284).** Старая схема остаётся источником
  правды для мигрированной истории (docstring `scripts/backfill_multi_program.py`), поэтому Журнал показывает
  **все legacy-карточки** (`GET /api/history`, с «✏️ Изменить»/«🗑 Удалить» — PATCH/DELETE `/api/history/{id}`,
  только у них эти действия проверены) и **скрывает v2-сессии, созданные backfill-ом**: `GET /api/v2/sessions`
  принимает `exclude_backfilled=true` (его передаёт только Журнал; без флага ответ прежний — им пользуется,
  например, лабораторный «Журнал (v2)»). Backfill-сессия опознаётся по отпечатку
  (`TrainingSessionRepository._backfilled_fingerprint`): завершённая, источник plan/freeform/backdated, без
  `client_session_id`/`workout_snapshot`/`activity_type`/`SessionPlanItem`, а первый блок — системное
  упражнение блока A подтягиваний (`category=pull_ups`, `subcategory=block_a`). Скрытие **не сопоставляется**
  с legacy-записью (ни по моменту, ни по источнику): правка legacy-записи после миграции видна сразу, а
  удаление legacy-записи не «воскрешает» её v2-копию. Электив (#279, `source=elective`), живые и Builder-
  сессии, записи «активность» под отпечаток не подпадают и показываются. Срез `offset/limit` и `has_more`
  списка v2 считаются уже после скрытия; те же правила — в счётчиках `GET /api/v2/journal/days` и
  `latest_month` (день = v2-сессии без копий + все legacy-тренировки). Это display-only: ни одна запись не
  меняется и не удаляется. `GET /api/history` снова отдаёт все записи (параметр `exclude_migrated` из #282
  удалён; старый клиент, который его ещё шлёт, получает полный список), а цель следующей тренировки
  (`target_a/b`) — только на самой свежей записи ВСЕЙ истории пользователя, независимо от `date_from/date_to` и
  `offset/limit` (#285: раньше свежайшая запись каждого месяца считалась «последней» и показывала цель).
- **Сводка Профиля считает и Журнал v2 (#277, D2).** `GET /api/profile`: `workouts_count` = все legacy
  `Workout` + завершённые v2 `TrainingSession`, **кроме** backfill-копий (тот же отпечаток
  `_backfilled_fingerprint`, что скрывает их в Журнале, #284: legacy — источник правды для перенесённой
  истории), поэтому мигрированный пользователь не считается дважды; `days_since_last_workout` — по самой
  свежей из legacy и не-backfill v2. Пользователь только с v2-сессиями больше не видит «Тренировок пока не
  было.». Display-only: хронологии не сливаются, готовность/прогрессия (`/api/dashboard`, бот) считаются по
  legacy как раньше; карточки ГТО/ВСФ остаются на legacy-данных подтягиваний.

### Запись в Журнал: задним числом и свободная активность (#263)

Журнал и «+» на Главной («Записать в журнал») открывают шторку «Тренировку из моих» /
«Другую активность»; обе формы пишут через `POST /api/v2/sessions` завершённую сессию.

- **«Тренировку из моих»** — `source=backdated`: своя Workout, дата (сегодня или прошлое),
  значения подходов по упражнениям, усилие 1–5, заметка. Без `program_inclusion_id` (с ним — 422):
  прогрессия курсов не пересчитывается. `completed_at = performed_at`, поэтому записи не дают минут
  («без данных о времени» в Analytics), но считаются тренировками.
- **«Другую активность»** — `source=freeform` + `activity_type` (`running`, `cycling`, `swimming`,
  `hiking`, `yoga`, `gym`, `martial_arts`, `other`; подписи — `app/domain/activity_types.py`) +
  `duration_seconds` (60…43200), без блоков. Колонки `training_sessions.activity_type` /
  `duration_seconds` — аддитивные nullable. Минуты Analytics берутся из `duration_seconds`
  (для остальных сессий — `completed_at − performed_at`, 1 мин…6 ч). Карточка показывает тип и
  длительность; такая сессия доказуемо независима от прогрессии, поэтому `can_delete = true`.
  Backdated-сессия удаляется только по общему предикату (т.е. сейчас — нет).
- **Валидация:** дата из будущего (допуск 5 мин) — 422; длительность вне 1 мин…12 ч, неизвестный
  тип, `effort` вне 1…5 (только для этих записей) — 422; упражнение/тренировка не видимы
  пользователю (чужие, несуществующие) — 404. `performed_at` «сегодня» = текущий момент, прошлого
  дня — локальный полдень.
- Обе записи — точки календаря и карточки Журнала, считаются тренировками в Analytics.

### Безопасное удаление Builder-сессии

Жёсткое удаление разрешено **только** если бэкенд доказал безопасность. Условия (все сразу):

1. сессия завершена;
2. не связана с program-backed `PlanItem`;
3. доказана Builder-природа: валидный замороженный снимок, чей Workout — пользовательский
   (`source_type = user`) этого же владельца; либо (сессия до снимков) все связанные PlanItem —
   complex-backed на такие Workout;
4. блоки не совпадают с ролями STEP A/B ни одной STEP-инклюзии пользователя (и не используют
   упражнения этих ролей).

Кроме Builder-сессии и свободной активности (#263), доказанно независим от прогрессии **факультатив**
(#279): `source = elective` (завершённая запись, перенесённая backfill-ом #163 из legacy
`ElectiveWorkout`), без связей с `PlanItem`, каждый блок — на **системное** `Exercise` с
`subcategory = elective_*` (не пользовательское, не комплекс); условие 4 (STEP-роли) проверяется так же.
Такая запись получает `can_delete = can_edit = true`: правка — дата, значение/усилие подхода, усилие и
комментарий (упакованный в `SetLog.note` JSON формата/снаряда не меняется и наружу не отдаётся —
вместо него строка «Подходы: 4 · 3 · 2»); «Повторить (клонировать)» для факультатива — 409, кнопки нет.
Legacy-строка `ElectiveWorkout` (лимит/ротация факультативов, ачивки) удалением/правкой записи Журнала не
меняется.

Всё недоказанное — отказ. `DELETE /api/v2/sessions/{id}`: чужая/несуществующая → **404**;
небезопасная → **409** с человекочитаемой причиной; успех → 204 и удаляется только дерево
`TrainingSession`. Фронтенд показывает «Удалить» только при `can_delete = true` из ответа,
собственных эвристик нет; двойной клик защищён.

**Соотношение с конституцией.** Принцип V (`Архивировать, не удалять`) остаётся общим правилом:
исторические/критичные для прогрессии записи не удаляются разрушающе, если это может нарушить
прогрессию или историю. Жёсткое удаление Builder-сессии — узкое принятое исключение для записей,
которые бэкенд доказанно отделил от защищённой прогрессии. Дословная сверка этого исключения с
Принципом V — открытый вопрос владельца (поправка к конституции не вносилась).

### «Открыть тренировку» из записи Журнала (#281)

- `SessionResponse.workout_id` (`GET /api/v2/sessions`, ответы правки/клона) — id **своей живой**
  (не архивной) Workout из замороженного `workout_snapshot.workout_id`; удалённая, чужая или системная
  тренировка и сессии без снимка → `null` (`ProgramRepository.list_own_workout_ids`, один запрос на страницу).
- В деталях записи при не-null — «Открыть тренировку»: вкладка «Главная» открывается сразу на Workout
  Detail (#255) этой тренировки; Telegram BackButton с неё возвращает в Журнал (один раз), дальнейшая
  навигация обычная. Новых эндпоинтов и миграций нет.

### Правка и клон записи Журнала (#262)

Crimpd «Edit Log» / «Clone Log». Доступны **только** для сессий, прошедших тот же предикат
безопасности, что и удаление (`SessionDeletionService`); в ответе `GET /sessions` это `can_edit`
(= `can_delete`), собственных эвристик на фронте нет. Program-backed/STEP/активные/недоказанные
сессии этим путём не правятся и не клонируются.

- `PATCH /api/v2/sessions/{id}`: меняет `value`/`effort`/`note` СУЩЕСТВУЮЩИХ подходов
  (`sets[{block_index, set_number, …}]`; добавлять/удалять подходы и блоки нельзя), `effort`
  (1–5) и `comment` тренировки (`null` очищает), `performed_on` — локальный день пользователя,
  не в будущем (время суток сохраняется; сегодняшний день ограничен «сейчас»). Чужая — **404**,
  небезопасная — **409** с причиной, невалидное (будущая дата, неизвестный подход, значение вне
  0…99999.99, усилие вне 1–5) — **422**, ничего не применяется частично. Прогрессия не
  пересчитывается. Календарь и аналитика читают `performed_at`/подходы, поэтому отражают правку.
- `POST /api/v2/sessions/{id}/clone` (`performed_on`, по умолчанию сегодня): новая завершённая
  сессия `source = backdated` с теми же блоками, целями, фактом, снимком и связями с `PlanItem`;
  `completed_at = performed_at`. Без прогрессии, оригинал и определения не меняются. 404/409/422
  как у правки.

UI: в деталях записи рядом с «Удалить» — «✏️ Изменить» и «⧉ Повторить (клонировать)» (только при
`can_edit`); правка — форма (дата, значение/усилие/заметка каждого подхода, усилие и комментарий
тренировки); клон — выбор даты (по умолчанию сегодня), после создания Журнал переходит к месяцу
новой записи.

## 4. Analytics v2

Отдельный конвейер `GET /api/v2/analytics/training` по **всем** завершённым сессиям
пользователя — не выводится из страниц Журнала.

- **Агрегация** по `(exercise_id, protocol_type)`; несовместимые протоколы одного упражнения
  никогда не суммируются (повторения и максимум «Подтягиваний» — разные панели).
- **Активность:** число завершённых сессий и активных дней за последние 30 локальных
  календарных дней; 12 календарных недель с понедельника. Часовой пояс — пользовательский,
  при отсутствии/невалидности — проектный дефолт (`Europe/Moscow`). Будущие сессии
  исключаются; смешанная сессия считается один раз. STEP/null-протокол-сессии дают вклад
  только в активность.
- **Метрики.** REPS: всего повторений, подходов, лучший подход, тренд. TIME: время в работе,
  подходов, лучшая длительность, тренд. MAX: число попыток, лучший результат, кумулятивный PB,
  флаги нового рекорда (первая запись — точка отсчёта, не рекорд). INTERVAL: фактическая
  длительность, циклы, точки.
- **Не выдумываем:** общий объём между протоколами, стрик, вес/нагрузку, RPE, «план vs факт»
  для интервалов; длительность — только по правилу ниже.
- **Метрика «Тренировки / Минуты» (#259).** Аддитивная nullable-колонка
  `training_sessions.completed_at` ставится при завершении: live-complete (момент запроса),
  авто-финиш интервала (дедлайн интервала, не момент ленивой финализации), ручное создание
  (момент записи). Старые сессии НЕ backfill-ятся (NULL). Длительность сессии =
  `completed_at − performed_at` только если обе даты есть и результат в пределах 1 мин – 6 ч;
  иначе сессия считается тренировкой, но исключается из минут, а UI пишет «без данных о
  времени: N». `GET /api/v2/analytics/training?from=YYYY-MM-DD&to=YYYY-MM-DD` (локальные даты
  пользователя, включительно; по умолчанию — последние 30 дней; `from > to` или диапазон
  ≥ 366 дней → 422) возвращает `metrics`: недельные ряды `weeks[{week_start (понедельник),
  workouts, minutes}]` для обеих метрик, `total_workouts`, `total_minutes`, `without_duration`.
  Неделя/день — в часовом поясе пользователя; пустые недели диапазона присутствуют.
- **Распределение по категориям (#274):** тот же ответ содержит `distribution` за тот же
  диапазон: `categories[{name, workouts, minutes, subcategories[{name, workouts, minutes}]}]`,
  `total_workouts`, `total_minutes`. Категория/подкатегория — у `Exercise` блока сессии.
  Смешанная сессия **делится поровну по блокам** (дробные `workouts`; доли одной сессии в
  сумме дают 1, поэтому итог = число тренировок диапазона), её минуты делятся так же; сессия
  без валидной длительности даёт долю тренировки, но не минут. Свободная активность (#263)
  целиком — категория «Другая активность»; блок без упражнения/категории — «Без категории».
  Категории каталога, видимого пользователю (system + свои), присутствуют с нулями;
  служебные категории — в конце. UI: кольцо «По типам» (внутреннее — категории, внешнее —
  подкатегории; цвета из палитры проекта, служебные — нейтральные) с легендой и таблица
  «Сводка» (Тренировки / Минуты, строка TOTAL) под графиком, по выбранной метрике/периоду.
- **UI:** вкладка «Аналитика», сверху «Тренировки | Программа» (по умолчанию «Тренировки»);
  прежняя аналитика программы — под «Программа», доступна и при ошибке v2. Карточки за 30 дней,
  переключатель «Тренировки | Минуты» и период «1 мес | 3 мес | Свой» (по умолчанию
  1 мес / Тренировки; «Свой» — две даты и «Применить»), недельный SVG-график выбранной метрики,
  кнопка ⓘ с определениями метрик, выбор упражнения, панели по протоколам, читаемые значения,
  ограниченный график (последние 30 точек из *N*), состояния loading/empty/error. Проверено на
  320 и 390 px.

### Тесты (Assessment Tests, #260)

Хаб «Тесты» поверх `AssessmentProtocol` / `AssessmentResult`.

- **Протоколы** — общий справочник, засеян аддитивной data-миграцией (идемпотентно, по имени):
  «Максимум подтягиваний» (reps, «повт.»), «Вис на перекладине, сек» (time, «сек»),
  «Подтягивания с весом, кг» (weight, «кг»). Скалолазных тестов нет. Единица результата
  определяется `metric_type` протокола.
- **API** `/api/v2/assessments`: `GET` — протоколы с `last_result`, `results_count` и `trend`
  (последние 12 значений, старые → новые); `GET /{protocol_id}/results` — протокол и свои
  результаты, новые первыми; `POST /{protocol_id}/results` (`performed_on`, `value`, `note?`);

- **Валидация:** `performed_on` — локальная дата пользователя, не в будущем (иначе 422); значение

  результатах. Деталь: описание, SVG-график (≥ 2 результатов), форма «Записать результат»

  (удаление — с подтверждением). Проверено на 320 и 390 px.

### Сравнение с похожими (Peer Insights, #276)

Блок «Сравнение с похожими» на детали теста: как последний результат пользователя соотносится с
другими пользователями приложения. Только анонимные агрегаты.

- **API** `GET /api/v2/assessments/{protocol_id}/peer-insights`. Ответ: `status`
  (`ok` | `insufficient` | `no_result`), `min_cohort_size` (20), `unit`, `own_value`, `cohort`
  (`level`, `label`, `size_bucket`), `percentile`, `median`, `next_target` (`percentile`, `value`).
  Числовые поля заполнены только при `ok`. Неизвестный протокол и неизвестный пользователь — 404.
- **База сравнения:** последний результат каждого пользователя по этому протоколу (по дате замера,
  при равенстве — по id). Сам пользователь входит в когорту.
- **Когорта:** кандидаты — «все пользователи» (ALL), «пол» (G) и «пол + возрастная ступень»
  (C; `app.domain.leaderboard.age_bucket`: 18–29 … 70+). Пользователь без пола, без даты рождения
  или младше 18 — «невыбираемый остаток» своего родителя (в ALL / в G). Кандидат показывается,
  только если в нём ≥ 20 человек **и** он пережил комплементарное подавление (ниже). Когорта
  пользователя — самая узкая **показываемая** на его пути C → G → ALL (нет пола — только ALL; пол
  без ступени — G → ALL). Ни одна не показывается — `insufficient`, UI: «Пока мало данных для
  сравнения (нужно ≥20 человек)», никаких чисел. Нет собственного результата — `no_result`.
- **Процентиль:** (число строго худших + половина равных) / размер когорты, в целых процентах
  (половина вверх), зажат в 1..99, затем **floor до 10-пунктовой полосы** (0, 10, …, 90) — наружу
  идёт только полоса; показывается как «Лучше, чем у ~70% похожих» (полоса 0 — «менее 10%»).
  Медиана и пороги — `percentile_cont`, **округляются до точности протокола**: повторения — целые,
  остальные метрики — один знак; `next_target` — ближайший порог из p25/p50/p75/p90 строго выше
  результата (округление вверх, остаётся выше результата); выше всех порогов — отсутствует.
- **Защита от реконструкции (ревью #283):** пользователь сам задаёт своё значение (результат «за
  сегодня») и свою когорту (пол/дата рождения), поэтому точный процентиль раскрыл бы число
  результатов ниже заданного, а разность ответов по вложенным когортам — малую группу.
  Правила: (1) процентиль — только полосами по 10 пунктов; (2) **комплементарное подавление
  узких когорт** (#284, `shown_cohorts` в `app/domain/peer_insights.py`): набор показываемых
  когорт — функция **только данных**, не зрителя. Для каждой показываемой когорты P берутся её
  ближайшие показываемые потомки (непересекающиеся: пол → ступени, ALL → полы, а если пол скрыт —
  его ступени); остаток = |P| − Σ|потомков|. Остаток 1–19 человек раскрыл бы агрегаты малой группы
  вычитанием двух ответов, поэтому скрывается **самый маленький** из этих потомков; повторяется до
  неподвижной точки. Широкие уровни не страдают из-за малого меньшинства (200 мужчин + 8 женщин —
  «все» остаётся для всех, прячутся «мужчины»/ступени). Инвариант: для двух показываемых когорт
  P ⊃ C разность размеров равна 0 (тождественные когорты — можно) или ≥ 20, то же для любой суммы
  непересекающихся показываемых потомков. Все размеры и агрегаты кандидатов приходят одним SQL
  (`GROUPING SETS`), выбор когорты — в чистом домене; (3) **лимит запросов** на пользователя —
  token bucket в памяти процесса (`app/web/rate_limit.py`): запас 20, пополнение 1 запрос в 5 с;
  сверх лимита — `429` с `Retry-After` и текстом «Слишком много запросов сравнения. Попробуйте
  чуть позже.»; (4) округление медианы/ориентира (см. выше).
- **Приватность и стоимость:** наружу — только агрегаты и грубый размер когорты («20–49» / «50–99» /
  «100+»); id, имена и значения других пользователей не отдаются и не читаются в Python. Агрегаты
  кандидатов считает один SQL (`AssessmentRepository.peer_cohorts`), без цикла по пользователям;
  возрастная ступень задаётся диапазоном дат рождения от «сегодня» (чистая функция в
  `app/domain/peer_insights.py`). Кэша нет. Согласия/opt-out нет — как и у лидерборда, данные
  агрегированы и обезличены. Результаты по-прежнему не влияют на прогрессию, монеты, GTO и WSF.

## 5. Доступ и безопасность

- **`POST /api/v2/plan-items`** не привязывает произвольный объект по id. Разрешено: свой
  пользовательский Workout; свой пользовательский Exercise; system Exercise из публичной
  библиотеки. Запрещено: чужой приватный Workout, чужой пользовательский Exercise, внутренний/
  программный `Complex` и внутренняя STEP-роль. Недоступное и несуществующее неразличимы (404);
  при отказе `PlanItem` не создаётся. Внутренняя материализация Program/STEP этот путь не
  использует.
- **Мои тренировки** (`GET /api/v2/workouts`): `source_type == user AND owner_user_id ==
  текущий пользователь`; ответ содержит items (канонический построитель ответа Workout), без
  N+1. Публичного/системного каталога Workout нет и не придумывается.
- **История тренировки** (`GET /api/v2/workouts/{id}/sessions`, #255): завершённые сессии
  *текущего* пользователя, чей замороженный `workout_snapshot.workout_id` равен этой тренировке;
  новые первыми; элемент — `id`, `performed_at`, `exercises_count`, `sets_done`. Видимость как у
  `GET /workouts/{id}`: чужой user Workout и несуществующий — 404.
- **Удаление тренировки** (`DELETE /api/v2/workouts/{id}`, #261): только свой user Workout
  (чужой / system / несуществующий / уже удалённый — **404**), ответ 204. Мягкое удаление:
  `complexes.archived_at` проставляется, строки `Complex`/`ComplexItem` остаются (на них ссылаются
  замороженные снимки сессий), а из `GET /workouts`, `GET /workouts/{id}`, избранного, поиска и
  привязки к плану архивная тренировка пропадает. Завершённые сессии и Журнал не меняются. Ручные
  `PlanItem` этой тренировки **удаляются из плана** (не 409; program-backed строки не затрагиваются —
  user Workout в каталожных программах не бывает), запись в избранном удаляется. Решение: «убрать
  из плана», а не отказ 409 — пользователь удаляет тренировку сознательно, UI предупреждает текстом
  подтверждения «Удалить тренировку? Это не удалит уже выполненные тренировки из журнала.».
- **Дублирование** (`POST /api/v2/workouts/{id}/duplicate`, #261): только свой user Workout (иначе
  404); создаёт новый user Workout «<название> (копия)» (≤255 символов) того же владельца с копиями
  `ComplexItem` (упражнение, порядок, `protocol`); возвращает `WorkoutResponse` с items.

## 6. Ограничения и известный долг

- **Монеты v2 не работают.** Завершение `TrainingSession` не начисляет монеты/ачивки
  (`GamificationService` не вызывается ни из live-, ни из session_log-путей). Не заявлять
  обратное, пока это не реализовано.
- **Главная (G3):** секции «Курсы» (каталог Программ, как раньше) и «Мои тренировки» (компактные
  карточки из `GET /api/v2/workouts`: название, число упражнений, первые названия и цель первого
  упражнения — только реальные данные, без id/JSON/нулевых целей). Вход «Создать» — на самой Главной
  (в пустом состоянии — крупная кнопка). Карточка (и такая же в «Мои тренировки» на «Планах») открывает
  **Workout Detail** (#255, только чтение): название, «Своя тренировка», число упражнений и оценка
  длительности «≈ N мин» — только если она считается из сохранённых полей у каждого упражнения
  (time_sets: подходы×время + отдых между подходами; interval: общее время; у повторений и
  max_effort длительности нет → оценки нет, не догадка); упражнения через общие форматтеры
  («3 × 8 повторений · отдых 1:00»); круглые кнопки «Добавить в план» и «Редактировать»
  (редактор; «назад»/«Сохранить» возвращают на деталь); «История» с пустым состоянием «Вы ещё не
  выполняли эту тренировку». **«Начать» (#273):** `POST /api/v2/sessions/live` принимает `workout_id` (взаимоисключающе с
  `plan_item_ids`) — свободная сессия `source=freeform` из замороженного снимка видимой пользователю
  тренировки (§5: чужая/несуществующая → 404; без упражнений → 422), без PlanItem; идемпотентна по
  `client_session_id`; если уже идёт другая живая сессия — 409 `{code: active_session_exists,
  active_session_id}`, UI предлагает «Продолжить текущую». Идёт обычным pre → live → summary;
  завершение не трогает прогрессию курса (`progression_skipped_reason=not_plan_session`) и счётчики
  плана (SessionPlanItem не создаётся — связать с планом можно только явно, отдельной задачей);
  попадает в Журнал и «Историю» тренировки (по `workout_snapshot.workout_id`). **«Записать» (#273)**
  открывает форму записи задним числом (#263) с выбранной этой тренировкой. Рядом с названием — сердечко «Избранное» (#272, ниже).
  Telegram BackButton с детали возвращает туда, откуда открыли. «← Назад» из формы «Записать» (и Telegram
  BackButton) возвращает на Workout Detail той вкладки («Главная» / «Планы»), откуда нажали «Записать» (#277);
  после сохранения остаёмся в Журнале с новой записью. «Добавить в план» ведёт на «Планы». Публичного каталога Workout и ссылок «Все» нет.
  **Избранное (#272):** таблица `user_favorites` (user, `workout|program`, target_id, уникально на
  пользователя+цель); `GET /api/v2/favorites`, `PUT`/`DELETE /api/v2/favorites/{type}/{id}` —
  идемпотентны. Избранным может быть только видимое пользователю: свои user-Workout и программы
  каталога (флага публикации у Program нет — каталог виден всем); чужое/системное/несуществующее/
  неизвестный тип → 404. Удалённые и ставшие недоступными цели молча выпадают из списка (строки не
  ломают сущности). Сердечко на Workout Detail и Program Detail — мгновенный оптимистичный тумблер,
  при ошибке откат + «Не удалось обновить избранное». На Главной ряд «Избранное» (над каталогом);
  пустой — подсказка «Нажмите ♡ на тренировке, чтобы добавить» только пока пользователь ни разу
  ничего не добавлял (флаг `favorites_seen` в localStorage), иначе ряд скрыт. В поиске — чип
  «Избранное» (только избранные программы и тренировки; упражнения в избранное не добавляются).
  **Витрина (#254):** sticky-шапка с «пилюлей» поиска «Что потренируем сегодня?» и кнопкой «+»;
  программы — горизонтальные ряды по `Program.category` (без категории — ряд «Другое», последним).
  «+» открывает шторку только с рабочими действиями: «Создать тренировку» (редактор), «Тренировка на
  сегодня» (вкладка «Планы»), «Отмена». Поиск — клиентская фильтрация (без нового эндпоинта) по

  реальных `category` (при активной категории тренировки скрыты — у них категории нет). Результат
  открывает существующий экран: Program Detail / редактор Workout / «Добавить в план» для упражнения
  (`POST /plan-items` с `exercise_id`). Закрытие поиска возвращает на Главную с прежней прокруткой.
  **Остаточные дыры паритета (#281):** (1) у ряда категории на Главной кнопка «Все ›» (кроме «Другое»)
  открывает поиск, уже отфильтрованный этой категорией (заголовок категории + активный чип); вкладки
  «Featured» нет — избранное содержимое даёт ряд «Подборки». (2) Тесты (Assessment Tests, #260) ищутся

- **Подборки (#271):** редакционные подборки программ и system-упражнений («Подборки» на Главной,

- **Планы: неделя и счётчики (#258):** «Планы» показывают ОДНУ неделю со степпером
  «‹ Неделя N · 29 сен – 5 окт ›» и чипом фазы (`PlanWeek.phase`); по умолчанию — текущая (последняя
  начавшаяся), ‹ ведёт к прошлым, › — к будущим (см. «Планы: расписание вперёд», #275). Каждая строка плана — счётчик «сделано/план» (`done_count`/`count_per_week`), у группы из

  ЗАВЕРШЁННЫХ (`status=completed`) сессий пользователя, связанных через `SessionPlanItem`, чья дата

  «Перенести»/«Убрать из плана». Незавершённое по итогам недели «сгорает» (отдельного статуса нет).

  inline-подтверждением) — пункты нижнего листа «⋯» строки (+ «Отмена»). Действия плана — лист «⋯» карточки
  курса: «Скопировать неделю → на следующую» (подтверждение остаётся на карточке недели) и «Убрать курс из

  — по локальной дате устройства — есть тренировки): строки с «Начать» (имя кнопки «Начать: название»).
  «Сейчас | Завершённые» — вкладки с подчёркиванием.

- **Планы: обзор и превью программы (#266):** вверху «Планов» вкладки «Сейчас | Завершённые».

  «N раз в неделю», для STEP-блоков «старт: N повт. × K подх.» из `Program.config`); у программы без
  строк (или при сбое запроса) показывается только описание — расписание не выдумывается.
  «Добавить в план» остаётся главным действием.
