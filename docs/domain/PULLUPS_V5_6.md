# PULLUPS_V5_6 — основная программа «Подтягивания» V5.6 (канонический контракт)

**Источник истины** — документ владельца «Программа V5.6: авторегуляция внутри фиксированной
структуры» (11.10.2026). Этот файл фиксирует, как он реализован (issue #305): что считается, где лежит,
какие места оставлены явным швом. При расхождении прав документ владельца, а не этот файл и не общие
представления о тренировках.

**Решение владельца V5.6 заменяет прежнее решение OD-3 «прогрессию двигает только подход на максимум»**
(#305, `cc4aa65`). Универсального «MAX двигает прогрессию» больше нет: у каждого блока свой сигнал.
Прежняя история решения сохранена в `PROGRAM_PLAN_V2.md` §11 как контекст устаревшей версии.

Код: чистый домен `app/domain/pullups_v5.py` (без aiogram/SQLAlchemy, вес — `Decimal`), оркестрация
`app/services/course_v5.py`, HTTP `app/web/routes_v2_course.py`. Золотые тесты — `tests/test_pullups_v5.py`
(каждый пример документа владельца с точными числами), API — `tests/test_web/test_v2_course_v5.py`.
Сквозной путь на свежем обычном профиле (онбординг → A по рецепту → итог → Журнал → прогрессия → рецепт B и
отдых между занятиями) — E2E `webapp-frontend/e2e/scenarios/program-journey-v56.spec.ts`.

## 1. Версии программы

|---|---|---|
| `pullups_v5_6` | `progression_state.program_version` новых инклюзий; правило `pullups_v5_6@1` (`decided = true`) | этот контракт |
| `pullups_legacy_step` | состояние без `program_version` (`block_a`/`block_b` бот-эпохи); правило `program_config_default@0` | прежний код: рабочие подходы + подход на максимум, `StepProgressionStrategy` (`session_log._apply_step_progression`) |

* Новая инклюзия — V5.6 по умолчанию. Устаревшая — только явно: `program_version: "pullups_legacy_step"` или
  прежние поля `initial_target_a/b` (они описывают состояние устаревшей версии). `pullups_v5_6` вместе с

  Это шов раскатки, см. §13.

## 2. Структура занятия

Две основные тренировки в неделю, **A** и **B**, по последовательности (не по календарю):
`state.next_role` чередуется после каждого завершённого основного занятия, роль занятия фиксируется в его
снимке. В каждой: разминка → объёмный блок → 15 минут → подводка к рабочему сопротивлению → силовой блок.

| Отдых | Значение |
|---|---|
| A, объём, между подходами | 240 с |
| B, объём, между подходами | 30 с (от конца подхода до начала следующего; в программе не варьируется) |
| объём → сила | 900 с |
| сила (оба уровня), между подходами | 180 с |
| тест 1RM, между подходами | 180 с |

Эти значения — часть выданного рецепта (снимка), не таймера движка v1 (§11).

**Расписание (решение владельца, version-scoped).** Новая инклюзия `pullups_v5_6` получает ровно
**2 основных занятия в неделю** (`MAIN_SESSIONS_PER_WEEK`): при подключении main-слот её снимка
замораживается с `sessions_per_week = 2` и меткой `snapshot.schedule = {program_version, main_sessions_per_week}`
(`schedule_snapshot`). Каталог программы (`programs.frequency`, у «Подтягиваний» — 3) **не меняется**:
инклюзии устаревшей версии — и с замороженными слотами, и старые снимки без слотов (частота из каталога) —
сохраняют своё расписание. Прошлые занятия плана не перестраиваются; повторная сходимость (convergence)
объём не меняет (0 изменений).

**Разминка и подводка.** Названы в источнике (§1 п. 1 «разминка», §1 п. 4 «подводка к рабочему
сопротивлению»; §8.4 «короткая подводка, не входящая в пять рабочих подходов»; §8.2 «одно-два собственных
повторения можно оставить в подводке»), но их содержание не задано. В рецепте — явные записи
`warm_up` / `strength_ramp_up` с `prescribed = false` и списком недостающего; подходы не выдумываются.
**Не хватает в источнике:** содержание и длительность разминки; подходы/повторения/нагрузка/помощь подводки;
отдых внутри подводки и перед первым рабочим подходом; отдых между разминкой и объёмом; нужно ли их
записывать как подходы; PREP-секунды перед блоками (#306).

## 3. Входы (§3 документа)

`M` — свежий максимум строгих подтягиваний без веса (из ввода, иначе из валидного замера: результат протокола
программы или замер онбординга). `R` — расчётный максимум в ТЕКУЩЕМ варианте объёмного движения: на уровне 1 —
способность с объёмной резиной, калиброванной на ≈8–12 строгих повторений (правило калибровки продукта, не
физиологический порог); с массой тела — `R = M`. `BW` — масса тела (профиль, `User.weight_kg`; обновляется раз
в неделю и переносится во входы только вперёд). `E1RM` — максимальный ДОПОЛНИТЕЛЬНЫЙ вес на одно строгое
повторение, из M не выводится и вручную не вводится: только результат теста 1RM (§10), проверенного сервером
(общий ввод с `e1rm_kg` — 422). Подтверждённая история (`known_a_targets`, `known_volume`,
`known_strength_a/b_kg`) сильнее стартовых формул. **Происхождение:** это входы со слов пользователя
(user-attested), сервер не сверяет их с сохранёнными сессиями — в рецепте/провенансе это заявленные значения,
а не серверно подтверждённые. Шаг дополнительного веса — `load_step_kg` (ввод
оборудования; глобального инвентаря нет).

Недостающий вход ничего не подставляет: `pending_inputs` следующего занятия, старт main — **409**
`{code: "course_setup_required", missing: [...]}`, Dashboard — `status = course_setup_required`.

## 4. Уровни

| Уровень | Когда | Объём | Сила |
|---|---|---|---|
| `assisted` (уровень 1) | M < 10 | с резиной (R по резине) | A и B одинаково: `5/5/5/5/5–8`, помощь |
| `transition` | допуск получен внутри программы ИЛИ стартовый M = 10–14 | без резины: A `5/5/5/5+`, B `10×3` | A `5×5`, B `5×3` с весом |
| `weighted` (уровень 2) | стартовый M ≥ 15; или выход из переходной лестницы B (закрыт `10×5`) | стандартные формулы | A `5×5`, B `5×3` с весом |

Допуск к весу — два равноправных продуктовых сигнала (не биологические пороги): свежий M ≥ 10 на старте;
внутри программы `5/5/5/5/8` с массой тела, отдыхом 180 с и подтверждённой техникой. При допуске резина
убирается из объёма, начинается переходная неделя, силовые блоки ждут 1RM (отдельный свежий день).

## 5. A — длинный объём

* Старт без истории: `a = min(20, max(3, floor(0,70 × R)))`, план `a/a/a/a+`. Потолок 20 — только старт.
* Последний подход — технический AMRAP (строго, без неудачной попытки, киппинга, отдыха на одной руке,
  отпускания хвата; минимальная цель `p4`). `VA_fact = факт1+…+факт4`. Результат AMRAP **не** свежий M.
* Зелёный: первые три закрыты, последний ≥ `p4+2`, техника подтверждена → +1 обязательное повторение
  ВСЕГО, в подход с наименьшей целью, при равенстве — в самый ранний (`18/18/18/18+ → 19/18/18/18+ → …`).
* Жёлтый (`p4` или `p4+1`) и красный (любая цель не закрыта) — план повторяется. Запас +2 без
  подтверждённой техники — повтор (`unconfirmed`).
* Два красных подряд — откат последнего добавленного повторения (стек `additions` делает откат
  детерминированным). Откатывать нечего — намерение `increase_assistance` (резина — по личному порядку,
  иначе выбор пользователя; конкретная резина не угадывается).

## 6. B — короткий объём

* Старт: `V_ref` — подтверждённый объём (`known_volume`) или факт первой A. `S = min(20, max(10, floor(V_ref/5)+1))`,
  `q = 5`; при `V_ref ≥ 100` — `S = 20`, `q = floor(V_ref/20)+1`. Примеры: 30 → `10×5`, 70 → `15×5`, 100 → `20×6`.
* Исполнение: каждый подход пишет факт; 3 повторения — продолжать; ≤ 2 — подход засчитывается в `VB_fact`
  и блок заканчивается; также по нарушению техники и после S подходов. Максимального подхода в B нет.
* Прогрессия — только при полном закрытии `S×q` с подтверждёнными техникой и отдыхом 30 с:
  `S < 20 → (S+1)×q`; `S = 20 → 20×(q+1)`. Иначе S и q не меняются; следующее занятие показывает
  промежуточную цель `прошлый VB_fact + 1` — только отображение, ступень она не открывает.
* Переходная лестница: `10×3 → 10×4 → 10×5 → 11×5 → …` (закрытие `10×5` переводит уровень в `weighted`).

## 7. Сила уровня 1 — `5/5/5/5/5–8`

Первые четыре — ровно по 5; пятый — контрольный (минимум 5, жёсткий потолок 8, неудачная попытка не
нужна; факт выше 8 считается как 8). У A и B — своя помощь (следующая одноимённая тренировка):

| Результат | Намерение |
|---|---|
| первые четыре закрыты и пятый = 8 (техника подтверждена) | `decrease_assistance` на одну доступную ступень |
| пятый 5–7 | `keep_assistance` |
| недобор в первых четырёх или пятый < 5 | `increase_assistance` |
| `5/5/5/5/8` с массой тела, отдых 180 с подтверждён | допуск к весу |

## 8. Помощь и оборудование

* Запись помощи однозначна: `kind` (`band`/`bodyweight`), `equipment_item_id`/название, цвет, крепление,
  положение стопы/колена. Килограммы резине не приписываются.
* Запись **готова к использованию** только целиком: модель/название, цвет, крепление, положение стопы или
  колена (`AssistanceSetup.is_complete`; «без помощи» — всегда готова). Неполная стартовая запись — блок ждёт
  ввода (`volume_assistance` / `strength_assistance`).
* «Одна доступная ступень» — по ЛИЧНОМУ упорядоченному списку резин (`EquipmentItem.position`, 0 — больше всего
  помощи); после самой лёгкой — масса тела (готова сразу). Порядок списка **не подтверждает** цвет, крепление
  и положение: смена на резину из списка — запись `assistance_pending` `{block, intent, proposed}`, блок
  хранит прежнюю подтверждённую помощь, старт занятия этой роли — 409 `assistance_confirmation`. Нет списка
  или следующей ступени — `proposed = null`, резину выбирает пользователь. Подтверждение — только полной
  записью (`PUT …/course/inputs`, `assistance_confirmations[{block, setup}]`, неполная — 422); пред-экран
  показывает форму с предложенным названием.

## 9. Сила уровня 2 — `5×5` (A) и `5×3` (B)

* Вход по приоритету: недавний `5×5`/`5×3` со слов пользователя (не сверяется сервером) → стандартизированный
  1RM (только записанный тест §10) → (до допуска — уровень 1).
* `T1RM = BW + E1RM`; `E5 = вниз до шага (0,75·T1RM − BW)`, `E3 = вниз до шага (0,80·T1RM − BW)`; ≤ 0 — масса
  тела (без помощи, пока план не провален). 75/80 — консервативная формула продукта.
* Прибавка (A и B независимо): `Δraw = 0,02 × (BW + Ework)`; `Δ` — ближайший доступный шаг (кратный
  `load_step_kg`) в пределах 0,5–2,5 кг, при равенстве меньший; нет шага в пределах — прибавки нет
  (`load_increment_unavailable`). Примеры: 70/10 при шаге 0,5 → +1,5; 80/40 → +2,5; 95/60 → +2,5.
* Все повторения закрыты, техника и отдых ≤ 180 с подтверждены → следующий одноимённый день `E + Δ`.
  Любой недобор — тот же вес. Лишние повторения не ускоряют (в расчёт идёт не больше цели).
* Плато (§8.6): сумма повторений растёт — ждём; 1–2 одинаковых неполных — вес тот же; 3 сопоставимых
  неполных без улучшения или 2 ухудшения подряд — калибровка: отмена ТОЛЬКО последней прибавки, схема
  сохраняется. Снова 3 попытки без прогресса (или отменять нечего) — предложение свежего 1RM либо
  калибровки снизу; новый 1RM не обязателен, вес сам не меняется.

## 10. Тест 1RM

Отдельный свежий день, не после объёма, не раньше 48 ч после тяжёлой тяговой работы (409
`one_rep_max_too_soon`). Не больше 8 подходов: BW×5 → +10% BW ×3 → +20% BW ×1 → одиночные с прибавкой
≈10/5/2,5% BW после быстрого/обычного/медленного повторения, проценты вниз до шага. Стоп после первой
неудачной попытки; результат — последний успешный ОДИНОЧНЫЙ (×1) дополнительный вес; успешный и не медленный
восьмой — консервативный максимум (девятого нет). Реализация: если округление прибавки вниз даёт 0, берётся один
шаг (иначе попытка повторяла бы тот же вес). 2RM не используется. Более крупные первые шаги для опытных —
не реализованы (шов). Ведение теста — `POST …/one-rep-max/next-set`; запись — `POST …/one-rep-max`
(факт в `state.one_rm_tests` вместе с BW и шагом, по которым проверена лестница, способом окончания и серверным
временем записи; подтверждённый E1RM заполняет ожидающие веса вперёд).

**Серверная проверка (review #305, `validate_one_rm_attempts`).** Лестница не придумывается заново — попытки
сверяются с `next_one_rm_set` шаг за шагом. Оба эндпоинта на каждом запросе: тест применим — есть сила с весом
(иначе 409 `one_rep_max_not_applicable`); есть BW и шаг (409 `course_setup_required`); ≥ 48 ч по серверному
времени (409 `one_rep_max_too_soon`; проверка на каждом шаге, поэтому присланные попытки не делают тест «уже
идущим»); каждая попытка — тот вес и те повторения, что лестница выдала после предыдущих; после
неудачной/недействительной попытки и после восьмого подхода попыток нет; успешный одиночный подход несёт скорость,
у неудачной попытки и у подходов ×5/×3 скорости нет. Некорректный запрос — 422 `one_rep_max_invalid`, весь
запрос отклоняется, состояние и история тестов не меняются.

**48 ч — и от предыдущего сохранённого теста (review #318).** «Тяжёлая тяговая работа» для допуска к тесту —
старт основного занятия (MAIN) **и любой сохранённый тест 1RM** (оконченный или остановленный), оба по серверным
временам (`performed_at` записи теста ставит сервер, клиент его не задаёт; `latest_one_rm_test_at`,
`course_v5.last_heavy_pulling_at`). Тесты ищутся во всех V5.6-инклюзиях плана пользователя: снятие курса и
подключение заново (`restart`) 48 ч не обнуляет. Повторный тест раньше 48 ч — 409 `one_rep_max_too_soon` и на
записи, и на начале новой лестницы; данные не меняются.

**Конкурентные записи (review #318).** Запись берёт транзакционный advisory-лок пользователя — тот же, что старт
занятия (`live_session.lock_user_starts`), затем перечитывает инклюзию и только после этого проверяет 48 ч.
Два одновременных запроса (двойной тап, два устройства) сериализуются: победитель пишет тест, проигравший видит
закоммиченный тест и получает 409; в истории ровно один тест. Тот же лок сериализует запись теста со стартом MAIN.

**Способ окончания: оконченный тест или явная остановка (review #318).** Дойти до неудачи или восьмого подхода
не обязательно — это было требование реализации, не контракта.

| `outcome` записи | Когда | E1RM | Нагрузка |
|---|---|---|---|
| `completed` (`standardized: true`) | лестница окончена по своему правилу: неудача/недействительная попытка или восьмой подход | последний успешный одиночный вес; нет успешного одиночного — **не назначается** | веса силы считаются от E1RM |
| `stopped` (`standardized: false`) | пользователь явно остановил тест (`stopped: true`), лестница по своему правилу ещё не окончена | **не назначается** — это не подтверждённый 1RM | не считается; курс ждёт тест (`pending_inputs` = `one_rep_max`) |

Остановка не записывает ложную «неудачу»: попытки сохраняются как были, в записи — `last_successful_single_kg`
(последний успешный одиночный вес или `null`). Проверка лестницы та же; кроме того: хотя бы одна попытка;
`stopped: true` у лестницы, уже окончившейся по правилу, — 422 (это оконченный тест); без `stopped` неоконченная
лестница — 422 (как раньше). Ответ записи: `one_rep_max = {e1rm_kg, conservative, sets_used, outcome, confirmed,
last_successful_single_kg}`; UI называет «1RM» только `confirmed`. Записи до review #318 без `outcome` читаются как
`completed`.

Примеры (BW 80, шаг 1,25; лестница: BW×5 → +7,5×3 → +15×1 → …):

* +15 обычный → +18,75 неудача → `completed`, E1RM +15.
* BW×5, +7,5×3, +15 неудача → `completed`, успешного одиночного нет → E1RM не назначается (раньше брался +7,5
  из подхода ×3 — это не вес на одно повторение).
* BW×5, +7,5×3, +15 обычный → «Остановить тест» → `stopped`, `last_successful_single_kg` +15, E1RM нет.
* +15 быстрый → +22,5 обычный → +26,25 медленный → стоп → `stopped`, последний одиночный +26,25, E1RM нет.
* BW×5 → стоп → `stopped`, одиночного нет, E1RM нет.

Регрессия: `tests/test_pullups_v5.py` (остановка, лестница при остановке, E1RM только от одиночного,
`latest_one_rm_test_at`), `tests/test_web/test_v2_course_v5.py` (две последовательные записи после оконченного и

## 11. Техника и отдых

Определить технику автоматически нельзя. Пользователь отвечает по блоку: техника соблюдена / отдых в пределах
— «да», «нет» или «не знаю» (`session_blocks.technique_valid` / `rest_within_limit`, nullable, миграция
`b5d8e1f3a6c9`). **NULL — неизвестно и никогда не «валидно»** для правил, которые требуют техники (зелёный A,
закрытие B, уменьшение помощи, допуск, прибавка веса) или отдыха (B, допуск, прибавка веса). «Не знаю»
завершает тренировку, но соответствующую прибавку не открывает. Компьютерной оценки нет.

Подтверждения собирает движок #306 (LIVE_ENGINE_V2 §9 п. 14) ДО канонического завершения: после последнего
подхода — фаза CONFIRM, ответы — событие `confirm_blocks` (журнал событий, воспроизводимо), затем одно
завершение и прогрессия. Выход раньше конца (`finish_early`, `POST …/complete` с `block_checks`) несёт ответы в
том же событии; неотвеченное — неизвестно. Подтверждение после завершения ничего не пересчитывает.
Серверные факты: остановка B по «техника нарушена» записывает технику блока как нарушенную; пауза в отдыхе
между подходами блока записывает «отдых превышен» — подтвердить отдых сервер не может, только опровергнуть.

## 12. Снимок рецепта, история, только вперёд

Рецепт занятия пишется **один раз** при живом старте в `prescription_snapshot` (S1):
`provenance.course_program` — версия, уровень, роль A/B, структура, блоки (роль блока, подходы с целями,
маркеры `working`/`amrap`/`control`/`dynamic`, потолок 8, отдых каждого подхода, помощь, внешний вес,
стоп-правило B, промежуточная цель, ступень переходной лестницы), 900 с между блоками, входы расчёта
(M, R, BW, E1RM, шаг, известные результаты, V_ref, допуск); `provenance.strategy = pullups_v5_6`,
`progression_state_rev`; в стандартных полях снимка — `rest_after_seconds` подходов и
`rest_after_block_seconds = 900`. SetTarget: AMRAP — `is_max_set` с минимальной целью `p4` в `value`;
прогрессия читает факт по позиции и тип блока из рецепта, а не флаг.

Прогрессия считается один раз — при завершении основного занятия, из рецепта СНИМКА этой сессии и её факта
(`advance_session`); результат типизирован по блокам (`a_volume`, `b_volume`, `assisted_strength`,
`a_weighted_strength`, `b_weighted_strength`). Правка истории (#307) меняет факт, но не состояние, не снимки,
не SetTarget и не занятия плана; каскадный реплей (`/progression/{preview,apply}`) к V5.6 неприменим (422).
Повторное завершение — без второй прогрессии; копия сессии — ручной повтор без кредита и прогрессии.
Целиковая запись `POST /sessions` рецепта не несёт — `v5_requires_prescribed_session`, прогрессии нет.

**Правило §9 — источник:** документ V5.6, раздел «9. Как изменения не конфликтуют», 2-й абзац, дословно:
«Если два занятия подряд показывают одновременное ухудшение обоих блоков, новые прибавки временно не
назначаются до проверки восстановления и внешней тяговой нагрузки». Реализация: `recovery_check_required`,
снимается `clear_recovery_check`. Пауза — **не** недостающий вход: старт не блокируется (не 409
`course_setup_required`), занятие идёт с удержанной нагрузкой, прибавки при завершении — `recovery_check_required`;
пред-экран показывает подтверждение рядом со стартом (Dashboard `course_recovery_check_required`). Это следует из
текста источника («прибавки временно не назначаются»), а не из трактовки. **Требует сверки с владельцем** (в источнике не определено, выбрано
реализацией): (1) «ухудшение блока» = факт ниже прошлого факта того же блока при **том же** плане (иначе
несопоставимо); (2) «прибавки» = +1 повторение A, ступень B, вес силы, уменьшение помощи; (3) «проверка»
= явное подтверждение пользователя; (4) серия считается по занятиям подряд независимо от роли A/B.
