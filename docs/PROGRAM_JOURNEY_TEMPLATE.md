# Шаблон маршрута программы — предложение #351

**Статус: DRAFT, для согласования.** Это заполняемый документ, а не новый контракт
приложения, дизайн экранов или разрешение на реализацию. Правило #347 сохраняется:
сначала согласовать конкретный пользовательский путь, затем отдавать его в код.
Этот шаблон не означает завершение скана Crimpd или приёмки Турникмэна.

Конкретный исходный пример и варианты для обсуждения: [замеры V5.6, #352](ASSESSMENT_JOURNEY_352.md).
Пример тоже DRAFT и не задаёт требований всем будущим программам.

Скопировать разделы 1–7 для одной программы и её версии. Все поля `<…>` заполнить
либо оставить `UNKNOWN` с причиной и следующим проверяемым шагом. `N/A` допустимо
только с объяснением, почему пункт неприменим к этой программе. Не переносить
замеры, интервалы отдыха или формулы другой программы по умолчанию.

Источники правил: [PROJECT_SPEC](PROJECT_SPEC.md), [доменный индекс](domain/README.md),
[Program/Plan](domain/PROGRAM_PLAN_V2.md), [Live](domain/LIVE_ENGINE_V2.md),
[Session/Journal](domain/TRAINING_SESSION_V2.md). Для текущей программы подтягиваний
читать её [версионный контракт V5.6](domain/PULLUPS_V5_6.md), а не переносить
исторические значения legacy-программы из общих примеров.

Для каждого утверждения отдельно указать: **ACCEPTED** (ссылка на решение),
**PROPOSAL**, **OBSERVED** (где/когда наблюдалось), **INFERRED** или **UNKNOWN**.
Наблюдение референса не переводит предложение в ACCEPTED. Эти метки описывают
происхождение сведений, а не результат машинного теста.

## 2. Замеры и подготовка

Одна строка на каждый необходимый именно этой программе вход. Программа может
не требовать замеров; тогда зафиксировать `N/A` и обоснование вместо фиктивного теста.

|---|---|---|---|---|---|
| `<…>` | `<до первого старта / условно / опционально / N/A + причина>` | `<…>` | `<валидность/актуальность из принятого контракта>` | `<принятый вариант либо UNKNOWN>` | `<ссылка; не придумывать формулу>` |

Для обязательного замера описать полный выход: объяснение «зачем» → подготовка →
выполнение → подтверждённый результат → видимый следующий шаг. Отмена, ошибка,
невалидный результат и недоступное оборудование также должны иметь описанный путь.
Не заменять неизвестную нагрузку нулём. Не собирать новые персональные данные ради
заполнения шаблона; требования к данным согласуются отдельно.

## 7. Критерий готовности заполненного маршрута

- Для каждого этапа есть результат, следующий шаг и применимые отказные состояния.
- У каждого необходимого входа есть инструкция, источник и связь с нагрузкой;
  необязательные/неприменимые замеры явно отличаются от обязательных.
- Область корректировок и сохранность истории описаны без новых неоговорённых правил.
- Продуктовые вопросы отделены от технических blockers и имеют конкретные зависимости.
- Проверки имеют честные результаты и границы доказательств; незавершённая приёмка видна.
- Согласование пути, source integration, installation и runtime acceptance записаны отдельно.
