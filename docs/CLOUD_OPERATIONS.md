# Управление проектом из облака

Цель: владелец общается в одном основном чате; код, проверки и управление
сервером доступны без включённого Mac. GitHub хранит код, PR, результаты
проверок и контрольные точки. GitHub Actions выполняет серверные операции
через существующие SSH forced-command wrappers. Приватные SSH-ключи остаются
в GitHub Secrets, а не в чатах, репозитории или среде агента.

## Однократное подключение

Администратор облачной среды подключает runtime secret `PULLUP_ACTIONS_TOKEN`:
fine-grained GitHub token с доступом только к `bimoool/pullup-trainer-bot`,
Actions read/write (Metadata read автоматически). Нужен срок действия и
порядок ротации; токен нельзя присылать в чат или записывать в отслеживаемый файл.
Секрет должен быть доступен при выполнении задачи, а не только при setup.
Это разрешение позволяет запускать другие workflows репозитория; клиент ниже
ограничивает штатные команды, но не является границей полномочий самого токена.

В сетевой политике среды разрешить `api.github.com` (HTTPS); сохранить proxy,
проверку TLS и остальные ограничения. `staging.app.bimoool.com` нужен, если
облачный агент будет напрямую проверять staging; для запуска QA через Actions
достаточно GitHub API. SSH-доступ из среды агента не требуется.

Существующее подключение GitHub для чтения PR и git push само по себе не
подтверждает наличие права `workflow_dispatch`. Не менять глобальные разрешения
всех приложений ради этой операции.

## Проверка готовности оператором

Команды выполняет агент в облаке; владельцу не нужно копировать их в терминал:

```bash
python tools/cloud_control.py access-check
python tools/cloud_control.py staging-preflight --sha <40-hex-candidate-sha>
python tools/cloud_control.py status <run-id>
python tools/cloud_control.py staging-qa
```

`access-check` только читает регистрацию workflows; успех ещё не доказывает
право dispatch или серверный доступ. Preflight запускается из workflow в main,
передаёт точный SHA кандидата, `converge=preflight`, `start=no`; он не выкатывает
кандидат. После принятого dispatch оператор находит запуск в Actions, проверяет
его входы, SHA, завершение и результаты. Не считать HTTP acceptance успехом
тестов/выкладки. При неопределённом результате POST сначала проверить историю;
не повторять dispatch автоматически.

QA выполняет полные journeys на уже развёрнутом staging, используя только
существующие синтетические QA-аккаунты. `reprovision=false`: клиент не сбрасывает
аккаунты. Отсутствующие QA-аккаунты — блокер, а не разрешение использовать данные
владельца. Первичное создание — по `STAGING_QA_HARNESS.md` через существующий
ограниченный wrapper и отдельный разрешённый запуск.

## Сервер и выпуск

Тестовый бот — `@fittest111_bot`, Mini App — `staging.app.bimoool.com`.
Действующий бот — `@pullup_trainer_bot`, Mini App — `app.bimoool.com`.
Staging использует отдельную БД `pullup_staging` и отдельный bot token.

Проверить наличие GitHub Secrets: `VPS_HOST`, `VPS_STAGING_GUARDED_SSH_KEY`,
`VPS_STAGING_DEPLOY_SSH_KEY`, `STAGING_BOT_TOKEN`. Не читать/печатать их значения.
Наличие workflow в main не доказывает, что серверные wrappers установлены.
Первый guarded preflight должен подтвердить доступ; rejected command или
отсутствующий ключ — блокер. Установка — `STAGING_RC_RUNBOOK.md`, QA —
`STAGING_QA_HARNESS.md`. Не заменять forced command произвольным shell.

Выкладка staging и production пока не включены в этот клиент. Использовать
существующие guarded workflows и соответствующие runbooks; обычный push ничего
не выкатывает. `dry-run` staging **меняет состояние**, останавливает сервисы и
выполняет миграции; это не проверка только чтением.

Production требует отдельного решения владельца на конкретный проверенный
кандидат, успешного staging, резервного копирования и проверенного отката
(`PRODUCTION_RUNBOOK.md`). Сохранить environment `production`, проверки exact
SHA и подтверждение apply. Не заменять их устаревшим `deploy.yml`.

## Завершение настройки

Система считается подключённой только после фактического успешного access-check,
guarded staging preflight и полного QA на точном развёрнутом кандидате. До этого
код клиента — подготовка, а доступ/серверный запуск остаются неподтверждёнными.
В PR/issue сохранять SHA, ссылки на runs, точные результаты и следующий шаг;
приватные аудиты, токены и пользовательские данные не публиковать.

Тест клиента: `python -m unittest discover -s tools/tests -v` — без БД и сети.
Для продуктового релиза остаются обязательными все существующие интеграционные
gates; эти unit-тесты их не заменяют.
