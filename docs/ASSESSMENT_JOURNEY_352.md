## 2. Три разных вида результата

| Результат | Действующее назначение | Чего из него не следует |
|---|---|---|
| Стартовый максимум M онбординга / вход курса | Исходные данные и квалификация по V5.6; после подтверждения онбординг показывает объяснение уровня | Число повторений не является готовой силовой нагрузкой в килограммах; 1RM не вычисляется из M |
| Стандартизированный 1RM внутри курса | Сервер проверяет лестницу, применимость, входы и временной допуск; оконченный тест с успешным одиночным подходом может дать E1RM | Добровольная остановка или тест без успешного одиночного подхода не дают подтверждённого 1RM |
| Запись в хабе «Тесты» | Отдельная история AssessmentResult; CRUD не пересчитывает уже применённую прогрессию, план, сессии и baseline онбординга | Это не означает «результат никогда не используется»: валидный максимум может стать стартовым входом нового/ожидающего замера курса; прошлый расчёт от этого не переигрывается |

Источник: PROJECT_SPEC «Тесты», раздел V5.6 и
[routes_v2_course.py](../app/web/routes_v2_course.py).
Альтернатива тесту — недавний 5×5 или 5×3 с дополнительным весом **со слов пользователя**,
а не серверное доказательство по сохранённым сессиям. Не называть её подтверждённым 1RM.
Альтернативы относятся к разным ролям: 5×5 — к A, 5×3 — к B. Одно значение может
разблокировать следующую A, но не настраивает автоматически будущую B; список
недостающего зависит от следующей роли. Чтение валидного максимума для начального
состояния прослеживается отдельно в [course_assessment](../app/services/course_assessment.py).

### Последующие замеры — отдельная часть маршрута

SOURCE: backend допускает последующий подходящий стандартный тест, но компонент
1RM в просмотренной форме показывается только при недостающем `one_rep_max`.
Постоянный пользовательский вход повторного тестирования из этого условия не следует.
Домен не обнуляет все рабочие веса при каждом новом E1RM: до первого завершённого
занятия входы пересобирают начальное состояние; позднее меняются ожидающие нагрузки
или роли с явным предложением перекалибровки. Прочие нагрузки и выданные снимки
сохраняются. Добровольная остановка не назначает новый E1RM и не стирает предыдущий.

ACCEPTED: контрольный свежий M через 4–6 недель в V5.6 — показатель результата,
не автоматический пересчёт состояния курса. Отдельный периодический UI-вход в
просмотренных поверхностях не найден; его наличие в других маршрутах — UNKNOWN.
Добавление такого входа требует своего согласованного пути, а не вывода из наличия API.

### Почему после «15 подтягиваний» ещё нужны данные

SOURCE: для M ≥ 15 показан допуск к силе с весом. Это не обещание конкретного
дополнительного веса: для него нужен применимый результат стандартного теста либо
допустимые недавние рабочие веса, масса тела и шаг оборудования. Конкретные потребности
определяет текущий уровень/состояние курса, не одна цифра M. Для помощи нужны свои
полные записи резины. Требовать одинаковый набор тестов у всех пользователей нельзя.

## 4. Остаток и конкретное предложение

**SOURCE RISK:** `OneRepMaxTest.record` сначала кладёт текст результата в локальное
состояние, затем немедленно вызывает `onSaved`. Callback обновляет состояние
пре-экрана; при переходе из setup в ready форма с локальным результатом заменяется.
Наличие formatter-функции не доказывает, что человек успевает увидеть итог и связь
с новой нагрузкой. Продолжительность/воспринимаемость этого перехода в текущем UI —
**UNKNOWN**, нового UI FAIL/PASS здесь нет.

**PROPOSAL A, рекомендуется для рассмотрения:** после успешного сохранения иметь
явный устойчивый шаг результата до продолжения:

1. **Что сохранено:** подтверждённый 1RM, остановленный тест либо оконченный тест
   без успешного одиночного подхода — строго по ответу сервера.
2. **Что это означает:** может ли этот исход участвовать в расчёте; какие входы ещё
   нужны. Не показывать нагрузку, пока сервер её не разрешил.
3. **Что дальше:** перейти к существующему пре-экрану готовой тренировки либо
   вернуться к недостающим входам/допустимой альтернативе. Никакого обхода 48 часов.

**PROPOSAL B:** вместо отдельного шага сохранять тот же полный итог на обновлённом
пре-экране до явного действия пользователя. Это другая UX-реализация того же вопроса;
ни A, ни B пока не приняты. Формулы, лестница и границы сохранности в обоих вариантах
остаются действующими. Не обещать повторный тест сразу после остановленного.

Историческая жалоба на «0 кг» сама по себе не доказывает ошибку расчёта: нужны версия,
входы, роль блока и серверный рецепт. Здесь эти production-факты не получены;
причину конкретного прежнего кадра оставляем UNKNOWN, формулу не подгоняем под него.
Для иллюстрации действующей формулы: при синтетических BW = 75 кг и E1RM = 15 кг
общая масса = 90 кг; `0,75 × 90 − 75 < 0` для A и `0,80 × 90 − 75 < 0` для B,
поэтому дополнительный вес ограничивается нулём — собственный вес, а не ошибка.
Это пример из действующего расчёта с округлением вниз до шага оборудования,
не новые числа программы и не объяснение неизвестного production-кадра.

## 5. Что проверять после согласования конкретного варианта

Это проект приёмки, **NOT TESTED**, не отчёт о новых прогонах:

| Сценарий | Наблюдаемый результат |
|---|---|
| После исходного M = 15 | Понятны квалификация, недостающие данные и следующий шаг; килограммы не назначены по одной цифре M |
| 1RM успешно сохранён | Итог читаем после обновления, видно его значение для расчёта и следующий допустимый шаг; reopen не создаёт второй тест |
| Добровольная остановка | Сохранённый факт не называется новым подтверждённым 1RM; предыдущий E1RM не стирается, дальнейшая доступность определяется сервером, 48 часов не обходятся |
| Нет успешного одиночного подхода | Нет выдуманного E1RM; следующий шаг соответствует оставшимся входам |
| Недавний 5×5/5×3 вместо теста | Явно self-report соответствующей роли; не выдаётся за серверно проверенный тест или автоматическую настройку обеих A/B |
| 48 часов / невалидная лестница / нет нужного поля | Человеческий отказ, сохранность истории и возможность продолжить допустимым способом; правила не ослаблены |
| Правка/удаление в хабе «Тесты» | Пользователь понимает отсутствие автоматического пересчёта курса; сохранность плана/сессий/прогрессии |

Имеющиеся проверки для переиспользования: [course-setup-one-rep-max E2E](../webapp-frontend/e2e/scenarios/course-setup-one-rep-max.spec.ts)
и [API V5.6](../tests/test_web/test_v2_course_v5.py) (недостающие входы, лестница/48 ч,
невалидный тест, добровольная остановка, запрет ручного E1RM, сохранность истории).
Они не заменяют отсутствующий сценарий устойчивого показа результата. Свежую native
приёмку не выводить из старого браузерного прогона или mock/WebKit.
