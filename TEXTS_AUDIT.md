# Аудит текстов и навигации — pullup-trainer-bot

Снимок текущего состояния кода на момент составления. Ничего не переписано и не улучшено — только собрано в одном месте. Тексты приведены дословно, с точностью до символа (включая пунктуацию и переносы строк `\n`).

Обозначения:
- 🟡 **ЧЕРНОВИК** — явно помечено как черновик в самом коде (комментарием).
- 🔧 — текст задан не в `app/bot/texts.py`, а прямо в файле хендлера (константой или литералом строки). Это не нарушение, просто для полноты картины: аудит охватывает `texts.py` + все места, откуда реально приходят сообщения пользователю.

## 1. Полное содержимое `app/bot/texts.py`

Файл разбит на два блока комментариями в самом исходнике: «Онбординг» и «Тренировка», плюс отдельный блок «Пейволл». Привожу в том же порядке, что в файле.

### Блок: Онбординг

🟡 **ЧЕРНОВИК** (комментарий в коде прямо над этим блоком: *«маркетинговый/объясняющий текст, не финальная копия — заменить на реальную, когда будет готова»*):

```
ONBOARDING_INTRO:
"Это бот-тренер по подтягиваниям. Работаем по методу прогрессии: сначала
определим твой уровень бесплатным замером, а дальше бот сам считает цель
на каждую тренировку — резину или вес, число подходов, когда пора
увеличивать нагрузку.

Первый шаг — бесплатный замер. Он ничего не стоит и доступен без подписки."
```

```
BAND_SELECTION_GUIDE:
"Как подобрать резину для замера:
Возьми ту, на которой сможешь сделать МАКСИМУМ подтягиваний за один подход.
Если ни одного повторения не получается даже на самой толстой — это тоже
результат, просто напиши 0.

[здесь будет видео про подбор резины]

Когда будешь готов — напиши, сколько повторений получилось."
```

## 4. Структура навигации по сценариям

### Онбординг

**Экран:** первое сообщение после `/start`, если у пользователя ещё нет `onboarding_completed_at`.
**Хендлер:** `start.py::handle_start`
**Состояние после:** `OnboardingStates.waiting_for_baseline_reps`

Показывает **два** сообщения подряд, без кнопок:
1. `ONBOARDING_INTRO` 🟡
2. `BAND_SELECTION_GUIDE` 🟡 (внутри — плейсхолдер `[здесь будет видео про подбор резины]`)

Ввод пользователя (свободный текст) ведёт в сценарий «Замер».

Если у пользователя `onboarding_completed_at` уже есть — `/start` вместо этого сразу показывает «Главное меню» (см. ниже), состояние сбрасывается (`state.clear()`).

---

### Замер

**Хендлер:** `onboarding.py`

1. **Состояние `OnboardingStates.waiting_for_baseline_reps`** (`handle_baseline_reps`)
   Ждёт текстовое число повторений (0–100 включительно, только цифры).
   - Невалидный ввод → `BASELINE_INVALID`, состояние не меняется.
   - Валидный ввод → сохраняет в FSM, переходит в `waiting_for_band_thickness`, шлёт `BAND_THICKNESS_PROMPT`.

2. **Состояние `OnboardingStates.waiting_for_band_thickness`** (`handle_band_thickness`)
   Ждёт число (мм), поддерживает запятую как разделитель.
   - Невалидный ввод → `BAND_THICKNESS_INVALID`, состояние не меняется.
   - Валидный ввод → вызывает `OnboardingService.record_baseline_and_start` (создаёт замер, определяет ветку BAND/ASSISTED, для BAND — создаёт первый сет), переходит в `waiting_for_weight`, шлёт:
     - `WELCOME_BAND` (если ветка BAND) **или** `WELCOME_ASSISTED` (если ASSISTED) — с подстановкой `{reps}`
     - затем `QUESTIONNAIRE_WEIGHT_PROMPT`

Дальше без разрыва в сценарий «Анкета».

---

### Анкета

**Хендлер:** `questionnaire.py`

1. **`OnboardingStates.waiting_for_weight`** (`handle_weight`) — ждёт положительное число (кг), запятая допустима.
   - Невалидно → `QUESTIONNAIRE_INVALID_NUMBER`
   - Валидно → `waiting_for_height`, шлёт `QUESTIONNAIRE_HEIGHT_PROMPT`

2. **`OnboardingStates.waiting_for_height`** (`handle_height`) — ждёт положительное целое (см).
   - Невалидно → `QUESTIONNAIRE_INVALID_NUMBER`
   - Валидно → `waiting_for_age`, шлёт `QUESTIONNAIRE_AGE_PROMPT`

3. **`OnboardingStates.waiting_for_age`** (`handle_age`) — ждёт положительное целое (лет).
   - Невалидно → `QUESTIONNAIRE_INVALID_NUMBER`
   - Валидно → `waiting_for_timezone`, шлёт `QUESTIONNAIRE_TIMEZONE_PROMPT` + `timezone_keyboard()` (11 кнопок)

4. **`OnboardingStates.waiting_for_timezone`** (`handle_timezone`, реагирует на `callback_data` вида `tz:*`) —
   вызывает `OnboardingService.complete_questionnaire_and_start_trial` (сохраняет анкету, отмечает онбординг завершённым, стартует триал).
   - Редактирует исходное сообщение (`edit_text`) на `TRIAL_STARTED` (подстановка `{trial_days}`)
   - Отдельным сообщением шлёт `Что делаем?` 🔧 + `main_menu_keyboard()`
   - Состояние очищается

---

### Главное меню

**Клавиатура:** `main_menu_keyboard()` — 3 кнопки.
**Куда ведёт каждая:**
| Кнопка | callback_data | Ведёт в сценарий |
|---|---|---|
| 💪 Начать тренировку | `start_workout` | «Тренировка» (`workout.py`) |
| 📖 История | `show_history` | «История» (`history.py`) |
| 🔁 Внести пропущенную тренировку | `backdate_workout` | «Бэкдейт» (`backdate.py`) |

Появляется: после `/start` у уже онбордившегося пользователя (текст `WELCOME_BACK` 🔧), после завершения анкеты (текст `Что делаем?` 🔧), после итога тренировки (текст `Что дальше?` 🔧), после редактирования (текст `Что дальше?` 🔧), после бэкдейта (текст `Что дальше?` 🔧). Во всех пяти случаях — разный сопроводительный текст, хотя смысл один и тот же («что дальше»); сама клавиатура идентична.

Кнопки «Изменить результат» (`workout_result_keyboard()`, отдельная клавиатура) в главном меню нет — она приходит отдельным сообщением сразу после итога тренировки, до сообщения «Что дальше?».

---

### Тренировка

**Точка входа:** кнопка «💪 Начать тренировку» → `workout.py::handle_start_workout`

#### Проверки перед планом (в порядке выполнения в коде)

1. **Подписка** — если `SubscriptionService.has_access()` вернул `False` → уходит в сценарий «Пейволл», дальше не идёт.
2. **Готовность по дате последней тренировки** (только если есть хотя бы одна прошлая тренировка):
   - `TOO_EARLY` → `TOO_EARLY_FOR_WORKOUT` (подстановка `{ready_at}`), стоп.
   - `GAP_ROLLBACK` или `GAP_RETEST_REQUIRED` → литерал 🔧 `Заметили большой перерыв — для такого случая пересчёт плана пока не подключен автоматически. Напишите в поддержку.`, стоп. *(Это то, что по последней договорённости должно замениться на реальную логику отката/повторного замера — на момент этого аудита ещё не сделано.)*
   - `READY` → продолжает.
3. **Активный сет** — если не найден → литерал 🔧 `Нет активного сета — нужен новый замер. Напишите в поддержку.`, стоп.
4. **Снаряд** — если резина менялась (`equipment_changed` на прошлой тренировке) или это первая тренировка вообще (`band_thickness_mm is None`):
   - Состояние → `NewBandStates.waiting_for_band_thickness`
   - Текст: `NEW_BAND_THICKNESS_PROMPT` (если была смена) либо `BAND_THICKNESS_PROMPT` (если это первая тренировка) — ждёт число (мм)
   - Невалидный ввод → `BAND_THICKNESS_INVALID`
   - Валидный ввод → переходит к плану (см. ниже)
   Вес (кг) для блока B пересчитывается автоматически (без вопроса пользователю), если на прошлой тренировке была смена веса — по формуле `next_weight_kg`.

#### Экран «План»
Состояние: `WorkoutStates.waiting_for_block_a`
Текст: `WORKOUT_PLAN` (подстановки `{target_a}`, `{target_b}`)
Кнопок нет — ждёт свободный текстовый ввод.

#### Экран «Ввод блока A»
Состояние: `WorkoutStates.waiting_for_block_a`
Промпт, который видит пользователь, на самом деле встроен прямо в `WORKOUT_PLAN` (см. выше) — отдельного `BLOCK_A_PROMPT` в этой ветке **не отправляется** (в отличие от редактирования и бэкдейта, где `BLOCK_A_PROMPT` шлётся отдельным сообщением).
- Невалидный ввод (через `app/bot/parsing.py`) → одно из трёх сообщений об ошибке разбора (см. раздел 2), состояние не меняется.
- Валидный ввод → `WorkoutStates.waiting_for_block_b`, шлёт `BLOCK_B_PROMPT`.

#### Экран «Ввод блока B»
Состояние: `WorkoutStates.waiting_for_block_b`
- Невалидный ввод → как выше, ошибка разбора.
- Валидный ввод → `WorkoutStates.waiting_for_comment`, шлёт `COMMENT_PROMPT` + `skip_comment_keyboard()` (кнопка «Пропустить»).

#### Экран «Комментарий»
Состояние: `WorkoutStates.waiting_for_comment`
Два пути:
- Пользователь пишет текст → `handle_comment_text` → этот текст становится комментарием тренировки.
- Пользователь жмёт «Пропустить» (`callback_data=skip_comment`) → `handle_skip_comment` → комментарий `None`.

Оба пути ведут в `_finalize_workout`, который вызывает `WorkoutLogService.record_workout` и дальше — экран «Итог».

#### Экран «Итог»
Отправляется последовательно (до 4 сообщений):
1. `BLOCK_RESULT_SUMMARY` для блока A (подстановки `{max_reps}`, `{new_target}`)
2. **если** у блока A `equipment_changed=True` → `EQUIPMENT_CHANGED_BAND`
3. `BLOCK_RESULT_SUMMARY` для блока B
4. **если** у блока B `equipment_changed=True` → `EQUIPMENT_CHANGED_WEIGHT`

Затем:
5. `WORKOUT_DONE` + `workout_result_keyboard()` (кнопка «✏️ Изменить результат» → сценарий «Редактирование»)
6. `Что дальше?` 🔧 + `main_menu_keyboard()`

---

### История

**Точка входа:** кнопка «📖 История» (`show_history`) → `history.py::handle_show_history`
Не FSM-сценарий (нет состояний) — один хендлер, один ответ.

- Если тренировок нет → `HISTORY_EMPTY`
- Если есть → до 10 последних (`HISTORY_LIMIT`), одним сообщением, по одной строке на тренировку:
  `{ДД.ММ.ГГГГ}: A макс {N}→цель {N}, B макс {N}→цель {N}` 🔧
  Кнопок под списком нет — пользователь возвращается в меню только новой командой/кнопкой из предыдущего экрана.

---

### Редактирование

**Точка входа:** кнопка «✏️ Изменить результат» (`edit_last_workout`), появляется только сразу после записи тренировки → `workout_edit.py::handle_edit_last_workout`

- Если истории нет → `NOTHING_TO_EDIT` (как всплывающее уведомление, `show_alert=True`, а не сообщение в чат), сценарий обрывается.
- Если есть → берёт **последнюю** тренировку (не любую по выбору), состояние → `EditWorkoutStates.waiting_for_block_a`, шлёт `BLOCK_A_PROMPT` отдельным сообщением.

1. **`EditWorkoutStates.waiting_for_block_a`** — та же логика ошибок разбора, что и в тренировке. Валидно → `waiting_for_block_b`, шлёт `BLOCK_B_PROMPT`.
2. **`EditWorkoutStates.waiting_for_block_b`** — валидно → вызывает `WorkoutRepository.edit_workout` (пересчитывает саму тренировку и каскадом все последующие), шлёт `EDIT_DONE` (подстановки `{a_max}`, `{a_target}`, `{b_max}`, `{b_target}`), затем `Что дальше?` 🔧 + `main_menu_keyboard()`.

Комментарий в редактировании не запрашивается (в отличие от первичного ввода тренировки).

---

### Бэкдейт

**Точка входа:** кнопка «🔁 Внести пропущенную тренировку» (`backdate_workout`) → `backdate.py::handle_backdate_start`
Состояние → `BackdateStates.waiting_for_date`, шлёт `BACKDATE_DATE_PROMPT`.

1. **`BackdateStates.waiting_for_date`** (`handle_backdate_date`) — ждёт дату в формате `ДД.ММ.ГГГГ`.
   - Не парсится → `BACKDATE_DATE_INVALID`
   - Парсится, но глубже 7 дней (или в будущем) → `BACKDATE_TOO_OLD`
   - Валидна → `waiting_for_block_a`, шлёт `BLOCK_A_PROMPT`
2. **`BackdateStates.waiting_for_block_a`** — как обычно, ошибки разбора; валидно → `waiting_for_block_b`, `BLOCK_B_PROMPT`.
3. **`BackdateStates.waiting_for_block_b`** —
   - Если нет активного сета → `BACKDATE_NO_ACTIVE_SET`, состояние сбрасывается, сценарий обрывается.
   - Иначе — снаряд берётся «последний известный» (без отдельного вопроса, см. комментарий в коде), вызывает `WorkoutLogService.record_workout` с датой из шага 1, шлёт `BACKDATE_DONE`, затем `Что дальше?` 🔧 + `main_menu_keyboard()`.

Комментарий не запрашивается. Кнопка «Изменить результат» после бэкдейта не показывается (в отличие от обычной записи тренировки).

---

### Пейволл

**Точка входа:** автоматически, если при попытке начать тренировку `SubscriptionService.has_access()` вернул `False` → `subscription.py::send_paywall`.
Не FSM-сценарий — вызывается напрямую как функция из `workout.py`.

Показывает `TRIAL_ENDED` (подстановки `{price}` = `SUBSCRIPTION_PRICE_RUB` из `tribute.py`, `{days}` = `SUBSCRIPTION_DAYS`) + `paywall_keyboard()` (2 кнопки).

**Ветка «⭐ Оплатить Stars»** (`pay_stars`) → `payments_stars.py::handle_pay_stars`
- Создаёт инвойс-ссылку через `bot.create_invoice_link` (валюта `XTR`, `STARS_PRICE` 🟡 = 200 — черновое число, `subscription_period` = 30 дней)
- Шлёт литерал 🔧 `Оплата через Telegram Stars:` + `payment_link_keyboard(url)` (кнопка «Перейти к оплате», открывает `url`)
- Дальше — платёжный флоу Telegram (вне бота): `pre_checkout_query` подтверждается автоматически (`ok=True`), после реальной оплаты приходит `successful_payment` → `SubscriptionService.extend(source=STARS)` → литерал 🔧 `Подписка активирована — можно тренироваться!`

**Ветка «💳 Оплатить картой»** (`pay_tribute`) → `subscription.py::handle_pay_tribute`
- Создаёт заказ через `TributeService.create_payment_link` (990₽/30 дней — константы `tribute.py`)
- Шлёт `PAYMENT_LINK_SENT` + `payment_link_keyboard(url)` (`order.payment_url` либо `order.webapp_payment_url`)
- Дальше подтверждение приходит не сразу от бота, а через фоновый опрос `app/workers/tribute_sync.py` (раз в 5 минут) — пользователь не получает отдельного сообщения «подписка активирована» для Tribute-оплаты (в отличие от Stars-ветки, где такое сообщение есть).

### Ошибки валидации — сводная таблица

| Где | Триггер | Текст |
|---|---|---|
| Замер, ввод повторений | не цифры или `>100` | `BASELINE_INVALID` |
| Замер, толщина резины | не парсится как число | `BAND_THICKNESS_INVALID` |
| Тренировка/начало, новая резина после смены | не парсится как число | `BAND_THICKNESS_INVALID` |
| Анкета: вес/рост/возраст | не парсится, `≤0`, не цифры | `QUESTIONNAIRE_INVALID_NUMBER` (один и тот же текст на все три поля) |
| Ввод блока A/B (тренировка, редактирование, бэкдейт) — неверное число значений | `len(parts) != work_sets + 1` | см. раздел 2, `parsing.py`, сообщение №1 |
| Ввод блока A/B — нечисловой токен | любой элемент не `.isdigit()` | см. раздел 2, сообщение №2 |
| Ввод блока A/B — число вне диапазона | `<0` или `>100` | см. раздел 2, сообщение №3 |
| Бэкдейт, дата | не парсится как `ДД.ММ.ГГГГ` | `BACKDATE_DATE_INVALID` |
| Бэкдейт, дата | глубже 7 дней или в будущем | `BACKDATE_TOO_OLD` |
