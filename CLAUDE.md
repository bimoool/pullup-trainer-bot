# pullup-trainer-bot

Telegram-бот-тренер по подтягиваниям. Python 3.12, aiogram 3, PostgreSQL 16,
SQLAlchemy 2 (async), Alembic, APScheduler, Redis (FSM-хранилище), gspread,
openpyxl. Long polling, без вебхука. Хостится на VPS `<VPS_HOST>`
(root SSH, `/root/pullup-trainer-bot`, GitHub `bimoool/pullup-trainer-bot`).

**VPS общий с другим проектом** (`reeltrack-bot`/`reeltrack-postgres`,
контейнеры `reeltrack-*`, отдельная директория `/root/reeltrack-bot`) —
все `docker compose`-команды выполнять из `/root/pullup-trainer-bot`, без
`-p`/глобальных флагов, которые могли бы задеть чужие контейнеры. Порт `db`
на хосте — эфемерный (`127.0.0.1::5432`, `docker compose port db 5432`
чтобы узнать) именно для того, чтобы не конфликтовать с другими локальными
проектами.

## Архитектура

- **`app/domain/`** — чистая бизнес-логика (прогрессия, аномалии,
  ачивки, правила готовности к тренировке, отчёты). Ни одного импорта
  aiogram или SQLAlchemy — проверяется буквально (`grep -rl
  "aiogram\|sqlalchemy" app/domain/` должен быть пуст). Функции чистые,
  датаклассы `frozen=True`, деньги/вес — `Decimal`, не `float`. Домен
  покрыт unit-тестами в `tests/test_*.py` (корень `tests/`), без Postgres.
- **`app/db/repositories/`** — один репозиторий на агрегат
  (`WorkoutRepository`, `UserRepository`, ...), только они трогают
  SQLAlchemy-сессию и конвертируют ORM ↔ доменные датаклассы
  (`app/domain/session.py: WorkoutRecord/BlockAssignment` и т.п.).
  Интеграционные тесты — `tests/test_repositories/`, на реальном Postgres.
- **`app/services/`** — оркестрация поверх репозиториев: пишет через
  репозиторий, шлёт событие в `EventRepository`, начисляет монеты
  (`GamificationService`), проверяет ачивки. Тесты — `tests/test_services/`,
  реальный Postgres.
- **`app/bot/handlers/`** — тонкий слой aiogram поверх `services`/`domain`.
  Не должен содержать бизнес-логику прогрессии/начислений — только сбор
  ввода, FSM-состояние, вызов сервиса, форматирование ответа. Тесты —
  `tests/test_bot/`, реальный aiogram `Dispatcher.feed_update` со стаб-сессией
  бота (`tests/test_bot/conftest.py`), не моки хендлеров.
- **`app/workers/`** — фоновые задачи через APScheduler (синк Google
  Sheets, опрос Robokassa OpState, еженедельные отчёты) — polling-архитектура,
  не вебхуки: без домена/HTTPS у бота негде принимать входящие колбэки.
  Если воркеру нужно программно привязать следующее сообщение пользователя
  к событию таймера (не к колбэку — входящего Update у таймера нет) —
  `dispatcher.fsm.get_context(bot=bot, chat_id=..., user_id=...)`
  выставляет FSM-состояние напрямую (см. `weekly_digest.py`); для этого
  `register()` воркера должен получить `dispatcher`, не только `bot`
  (`main.py::build_scheduler`). Тот же приём тесты уже используют для
  прямой проверки состояния (`tests/test_bot/conftest.py`), здесь —
  боевое применение, не только в тестах. Redis-хранилище FSM (не
  MemoryStorage) означает, что такая связка переживает рестарт/деплой
  между отправкой напоминания и ответом на него.

**Деплой-образ не содержит `.git` и не имеет `git`/`gh`** — `Dockerfile`
копирует только `app/`, `pyproject.toml`, `alembic.ini` (не `COPY . .`).
Проверено буквально: `docker run --rm <image> sh -c "test -d /app/.git"`
— пусто, `which git gh` — пусто. Любая функция, которой нужна история
коммитов или GitHub API (пример: автосбор "что раскатили"/"что в работе"
для `weekly_digest.py`) не может использовать локальный `git log` или
личный `gh`-доступ разработчика — только собственный GitHub-токен,
положенный в `.env` на сервере и прочитанный через `app.config.settings`,
как `ROBOKASSA_*`. Личный `gh auth` на dev-машине даёт доступ только для
исследования/прототипирования самим разработчиком (или Claude), не для
процесса бота, который сам, автономно, будит воркер по расписанию.

Тесты (`tests/conftest.py`) сами поднимают `db` из docker-compose и
создают отдельную БД `pullup_test` — миграции применяются автоматически
при первом запуске. Нужен только запущенный Docker:

```bash
pytest              # весь набор
ruff check app/ tests/
```

## Известный класс бага: `callback.message.from_user` — это бот, не человек

В реальном Telegram сообщение, к которому прикреплена inline-кнопка,
отправлено ботом — `callback.message.from_user` всегда бот. Нажавшего
кнопку видно только через `callback.from_user`. Баг: `_finalize_workout`
брал `telegram_id` из `message.from_user.id` — для callback-варианта
(«Пропустить» у комментария) это ловило id бота, `get_by_telegram_id`
возвращал `None`, `user.id` падал `AttributeError` **после** `state.clear()`
— тренировка терялась молча, без сообщения об ошибке (aiogram глотает
необработанное исключение в хендлере). Подтверждено трассировкой из
логов прод-бота. Тот же паттерн жил ещё в трёх местах (`backdate.py`,
`menu.py::render_profile`, `profile_edit.py`) — везде заменено на явный
`telegram_id`, переданный от исходного callback/message, а не выведенный
из `message.from_user.id` задним числом.

Тестовая фикстура `tests/test_bot/conftest.py::make_callback_update` —
единственный источник `Update` с `CallbackQuery` для `tests/test_bot/`,
специально ставит `message.from_user` = бот (не нажавший), как в реальном
Telegram. Не заводить локальных копий с обратной (неверной) семантикой —
именно неверная копия маскировала баг до его обнаружения.

**Правило**: в любом хендлере, где `message` может прийти из
`CallbackQuery`, брать `telegram_id` только из `callback.from_user.id`
(или явного параметра, прокинутого от него), никогда из
`message.from_user.id`.

## Процедура деплоя

Стандартный цикл (без миграции):

```bash
git push origin main
ssh root@<VPS_HOST> "cd /root/pullup-trainer-bot && git pull && docker compose build app"
ssh root@<VPS_HOST> "cd /root/pullup-trainer-bot && docker compose up -d app"
```

С миграцией — **сначала прогнать её локально** против непустых таблиц
(dev-БД `pullup` из docker-compose, не только чистую `pullup_test`),
прежде чем `alembic upgrade head` на проде:

```bash
ssh root@<VPS_HOST> "cd /root/pullup-trainer-bot && docker compose run --rm app alembic upgrade head"
```

Причина этого правила — реальный инцидент (ревизия формулы прогрессии
блока на объём, миграция `e2c7a4f19d3b`): миграция добавляла колонки в
`blocks`, но не в `blocks_archive_admin_reset` — постоянную архивную
таблицу под «🧪 Полный сброс» (см. ниже), созданную через
`CREATE TABLE ... (LIKE blocks)` (`b41882a0e3e8`). `LIKE` — это снимок
структуры на момент создания, он **не следит** за последующими
`ALTER TABLE` на исходной таблице. Баг («INSERT has more expressions than
target columns») проявился только на полном прогоне тестов против
непустой тестовой БД — на пустой `pullup_test`, будь она поднята с нуля
без предварительного прогона, баг остался бы незамечен до первого
реального вызова "Полного сброса" в проде.

**Если когда-нибудь снова меняешь схему `workouts`, `blocks`,
`workout_sets`, `baselines` или `equipment_items`** — проверь, нужно ли
то же самое изменение в соответствующей `*_archive_admin_reset` таблице
(все пять перечислены в `b41882a0e3e8_admin_reset_archive_tables.py`).

После деплоя — не полагаться только на «в логах нет ошибок». Логи чистого
старта показывают, что процесс не упал, но не что фича реально работает.
Проверять на реальных данных: прямой SQL-запрос к проду (`docker compose
exec -T db psql ...`) для схемных изменений, реальный проход хендлера
через бота или через прямой вызов сервисного слоя для логики.

## Изменение формулы прогрессии или схемы БД — план перед кодом

Для нетривиальных изменений домена прогрессии (шаг роста, пороги,
переходы снаряда) или новых колонок/таблиц — сначала план с конкретными
расчётами на реальных примерах (числа, не абстрактные формулы), явное
согласование, и только потом реализация. Не идти сразу в код. Тесты пишутся
на **каждый пример из плана**, с точными ожидаемыми значениями — это
почти всегда ловит расхождение между тем, что казалось очевидным на бумаге,
и тем, что реально считает код (см. следующий пункт).

## Google Sheets: новая колонка в инкрементальном листе требует бэкфилла

`app/services/sheets_export.py::SHEET_HEADERS` — единственный источник
состава колонок. Правило прямо у константы (не пропустить):
добавление колонки в один из инкрементальных листов (`events`, `workouts`,
`subscriptions`, `coins`, `achievements` — те, что растут через
`append_rows`, а не переписываются целиком как `users`/`equipment_items`)
чинит заголовок на существующем листе автоматически
(`ensure_sheet_structure`), но **не трогает уже записанные строки** —
они на одну колонку короче, и все данные правее точки вставки читаются
под чужими подписями. Не «не хватает данных» — вводящее в заблуждение
смещение. Зафиксировано после реального инцидента (username в заголовке,
старые строки остались короче). Обязателен разовый бэкфилл
(`scripts/backfill_sheets_username.py` — образец: регенерирует
затронутые листы целиком из БД тем же кодом синка, а не точечно патчит
старые строки), не только правка заголовка.

## Стиль тестирования: доказать, что тест реально ловит баг

Зелёный тест сразу после написания фикса ничего не доказывает — он мог
быть зелёным и без фикса (слабое условие, неверная фикстура и т.п., как в
случае с `callback.message.from_user` выше). Стандарт в этом проекте:
хотя бы для нетривиальных фиксов — временно откатить исправление, увидеть
падение именно этого теста, вернуть исправление. Тот же принцип действует
при написании теста ДО реализации: сначала руками посчитать ожидаемое
значение по плану, потом сверить с тем, что выдаёт код — расхождение
здесь и ловит реальные баги (пример: при ревизии формулы прогрессии
ручной расчёт для `recalculate_volume_block` поймал, что
`recalculate_target` подмешивал бы порог смены снаряда в цифру, которая
должна была остаться честной — пойман до, не после написания теста).

## `ADMIN_IDS`: обход лимитов для тестирования вживую

`settings.is_admin(telegram_id)` (по `ADMIN_IDS` из `.env`) — для
telegram_id из списка:

- минимальный отдых между тренировками (`MIN_REST_DAYS`) не блокирует
  повторный старт (`handle_start_workout`);
- провал перехода на новом снаряде не откатывает его молча —
  `bypass_transition_wait=True` в `resolve_next_targets`/
  `_resolve_next_state` сразу предлагает выбрать снаряд заново;
- «🧪 Полный сброс» (только видна админам, `admin_reset_prompt` →
  `admin_reset_confirm`) архивирует (не удаляет) прогресс аккаунта в
  `*_archive_admin_reset`-таблицы и возвращает его в состояние до
  онбординга — можно проходить весь путь заново сколько угодно раз;
- «🧪 Тестовый платёж 1₽» в `/admin` — та же ссылка Robokassa и тот же
  путь подтверждения (`sync_pending_payments`), что у обычной подписки,
  но на 1₽ вместо `SUBSCRIPTION_PRICE_RUB` — не тратить 990₽ на каждую
  проверку интеграции.

Домен (`app/domain/rules.py::check_training_readiness` и т.д.) обход не
знает и не меняется — обход только в вызывающем bot/repository-слое.

## Robokassa: подтверждена задержка опроса, не баг

Диагностический платёж 1₽ (см. выше) дал первое живое подтверждение
`OpStateExt`: `State/Code=100` (оплачен) — код и парсинг (`_STATE_CODE_PAID`
в `app/services/robokassa.py`) верны на реальных данных, не только по
документации. Отдельно подтверждён реальный сценарий задержки: платёж
завершился на стороне Робокассы сразу **после** ближайшего прогона
`sync_robokassa_payments` (интервал 5 минут) — пойман только следующим
прогоном, уведомление пришло с задержкой ~7 минут. Это не баг, а
арифметика опроса: интервал не выбирается точно под момент оплаты,
худший случай — почти два интервала подряд. Решение — не менять интервал
(тратить его нельзя, это упрётся в лимиты API), а честно предупредить
в `PAYMENT_LINK_SENT` («до 10 минут»), плюс `_notify` теперь логирует и
успешную доставку, не только неудачу (`logger.info`, не только
`logger.warning`) — раньше «нет warning» не было прямым доказательством
«сообщение дошло», приходилось вручную сверяться со своим чатом с ботом.

Диагностика этого случая — образец методики: не чинить вслепую по
жалобе «уведомление не пришло», а по порядку проверить (1) сам платёж и
прошёл ли цикл синка, (2) что реально вернул внешний API (прямой вызов
с прод-сервера, не по логам), (3) какой путь подтверждения реализован
(вызывается ли `extend()`, привязана ли нотификация к сумме платежа),
(4) и только если на всех трёх шагах всё чисто, а результата всё равно
нет — тогда это баг того самого класса (см. `callback.message.from_user`
выше), а не раньше.

## Mini App: Этап 0 (issue #15)

Домен `app.bimoool.com` подтверждён (2026-08-31) — A-запись резолвится в
`<VPS_HOST>`, этот VPS. Веб-слой: `app/web/` (FastAPI, тонкий слой
поверх тех же `repositories`/`services`/`domain`, что и бот — не дублирует
логику), `webapp-frontend/` (React + Vite, вне пакета `app`, собирается в
статику и отдаётся тем же FastAPI-процессом одним origin'ом, без CORS),
`Dockerfile.web` + сервис `web` в `docker-compose.yml` (свой контейнер,
свой образ, зависит только от `db`, порт публикуется только на
`127.0.0.1` — физически не может задеть `reeltrack-*` на этом же VPS, см.
шапку файла).

**Готовые библиотеки, не самописный HMAC** (issue #15, коммент от
2026-08-31, референс `taiga-labs/telegram-miniapp-template`):
- Бэкенд — `init-data-py` (`app/web/auth.py::get_validated_init_data`,
  FastAPI-зависимость): выбран, а не `telegram-webapps-authentication`,
  потому что не навязывает свою обвязку над Depends/Header — тонкий слой
  интеграции пишется по тому же принципу, что и остальной проект (бот не
  использует чужой HTTP-клиент для Robokassa как чёрный ящик, см.
  `app/services/robokassa.py`, — берёт готовую проверку подписи и
  оборачивает сам).
- Фронтенд — `@telegram-apps/sdk` (`retrieveLaunchParams().initDataRaw`
  для сырой initData, `init()` на старте) — не `@twa-dev/sdk` (устаревший)
  и не самописная обвязка над `window.Telegram.WebApp`.

**Важная оговорка о проверке.** Обе интеграции написаны без доступа к
npm/PyPI из песочницы Claude (сетевой доступ недоступен, тот же класс
ограничения, что SSH к серверу, см. ниже) — по памяти о публичном API
этих библиотек, не сверено установкой пакета. `tests/test_web/test_auth.py`
специально строит initData САМ, по официальному алгоритму Telegram
(HMAC-SHA256, независимо от внутреннего устройства `init-data-py`), и
подписывает реальным `bot_token` — если имена классов/методов
(`InitData.parse`/`.validate(token, lifetime=...)`/`.user.id`/
`.user.first_name`) в реальности отличаются от использованных здесь, эти
тесты первыми покажут расхождение при первом `pytest`/`docker compose
build web` с доступом к сети. Не мержить/деплоить, не прогнав их хотя бы
раз с реальными пакетами.

**Обновление (issue #23, 2026-09-01): доступ к npm из песочницы Claude
иногда всё же есть** — оговорка выше про полное отсутствие сетевого
доступа не универсальна, зависит от конкретного запуска/окружения.
Когда доступ есть — им стоит воспользоваться (`npm install` в
`webapp-frontend/`, закоммитить получившийся `package-lock.json`, если
его ещё нет, прогнать `npx tsc -b && npx vite build` перед выводами о
типах/сборке), не полагаться на память о публичном API по умолчанию.
Так был найден реальный баг: `@telegram-apps/sdk`'s `retrieveLaunchParams()`
(пакет `@telegram-apps/bridge` под капотом) читает launch params
**только из URL** (`location.href` → `performance` navigation entry →
`sessionStorage`), никогда не обращается к `window.Telegram.WebApp.initData`
(мост старого `telegram-web-app.js`, подключённого в `index.html`).
На живом Telegram Desktop `tgWebAppData` иногда не попадает в URL, хотя
кнопка Mini App правильная (`KeyboardButton(web_app=WebAppInfo(...))`,
не обычная `url=`-ссылка — тип кнопки был не при чём) — фронтенд получал
пустой `initDataRaw` и ошибочно писал "открыто не из Telegram?".
`webapp-frontend/src/App.tsx` теперь фолбэчится на
`window.Telegram.WebApp.initData`, если `retrieveLaunchParams()` пуст
или бросает исключение — тот же initData, другой источник, независимый
от URL-парсинга. Не проверено на живом Desktop-клиенте (сеть до npm ≠
доступ к реальному Telegram-клиенту, это два разных класса ограничения
песочницы) — если фолбэк не поможет, следующий кандидат — точка входа
через постоянную Menu Button (`set_chat_menu_button`/`MenuButtonWebApp`)
вместо `KeyboardButton`, у неё более стабильная кросс-клиентская
поддержка initData по опыту сообщества `@telegram-apps/sdk`.

**Обновление (issue #28, 2026-09-02): фикс #23 не помог, кнопка всё же
не при чём.** После деплоя фолбэка на `window.Telegram.WebApp.initData`
ошибка "initDataRaw is empty" повторилась и на Desktop, и (чёрный экран)
на мобильном. Автор issue заподозрил, что кнопка на самом деле обычная
`url=`-ссылка, а не `web_app=WebAppInfo(...)` — проверено буквально по
коду (`app/bot/keyboards.py`, `bottom_menu_keyboard`): это
`KeyboardButton(text=BOTTOM_MENU_MINI_APP, web_app=WebAppInfo(url=...))`,

**Обновление (issue #61): черновик живой тренировки на сервере —

Схема — отдельная таблица `WorkoutDraft`/`workout_drafts`
(`app/db/models.py`, миграция `f1a2b3c4d5e6`), не поле в `ActiveTimer`:
у них независимые жизненные циклы (черновик живёт весь поток тренировки,
таймер — только во время конкретного отдыха, и не всегда синхронно
удаляется при продолжении, см. докстринг `ActiveTimer`) — совмещать в
одной строке было бы источником рассинхрона. Один черновик на
пользователя (unique `user_id`), без snapshot плана (`target`/`work_sets`/
`equipment`) — при восстановлении план перезапрашивается тем же
`GET /api/workout/plan`, что и обычный старт (пока черновик не сдан,
прогрессия не менялась, план детерминирован). `step_index` — единственный
источник позиции в потоке шагов, сами шаги (`buildSteps` в
`LiveWorkoutScreen.tsx`) пересобираются на фронтенде из `work_sets_a/b`
плана, не хранятся в БД.

API — `PUT/GET/DELETE /api/workout/draft` (`app/web/routes.py`,
`WorkoutDraftRepository` — тот же CRUD-без-сервисного-слоя паттерн, что
`ActiveTimerRepository`). `PUT` апсертит целиком (весь накопленный массив
подходов, не один подход за раз) — вызывается после каждого завершённого
подхода (`LiveWorkoutScreen.tsx::handleStepDone`), с ожиданием ответа: если
сохранение не удалось, показывается ошибка и переход на следующий шаг не
происходит — иначе только что введённый подход потерялся бы молча при
следующем закрытии Telegram. `submit_workout` удаляет черновик сам при
успешной записи (`status == "ok"`), в той же обработке, что и запись
`blocks`/`workouts` — не полагается на отдельный `DELETE` с клиента после
успеха (сеть могла оборваться уже после успешного submit).

Восстановление на фронтенде (`LiveWorkoutScreen.tsx`) — при заходе на
экран, если черновик найден и согласуется с текущим планом (число рабочих
подходов не короче сохранённых массивов — иначе черновик отбрасывается,
обычный `intro`), состояние восстанавливается и экран сразу открывается
на сохранённом `step_index` (или на `review`, если все подходы уже были
введены), без демонстрации `intro`. Правки на экране `review` (вес/резина/
комментарий перед финальной отправкой) сознательно НЕ персистятся — только
факт "дошёл до review" уже зафиксирован последним `PUT` перед переходом;
согласовано в issue как разумная граница объёма (потеря самого последнего
экрана перед отправкой — намного меньшая потеря, чем вся тренировка).

вторым запросом. Ловушка на реальном Postgres, не только по документации:
bind-параметр, единственное употребление которого в запросе —
`IS NULL`/`IS NOT NULL` без соседнего типизированного операнда, asyncpg не
может типизировать при подготовке prepared statement
(`AmbiguousParameterError`) — каждый такой параметр (`gender`, `age_bucket`,
`requesting_user_id`, `limit`) обёрнут явным `CAST(:param AS ...)`, не
только для читаемости.

**Обновление (issue #82): график "Прогресс" — факт вместо плана,

Старый `GET /api/progress` строился по `BlockAssignment.target_after` —
плановой цели на СЛЕДУЮЩУЮ тренировку, не по тому, что человек реально
сделал (баг, найденный на реальном использовании). Эндпойнт теперь
принимает `metric: max_reps|volume|strength` (`app/web/routes.py::

  запись уже в памяти, агрегация по всем пользователям разом не нужна.
- `volume` — уже существующий `BlockLog.volume` (рабочие подходы + подход

  тренировкам во времени — переживает смену резины/веса как один
  непрерывный ряд, не разрывается на несравнимые сегменты. Не определена
  для AUSTRALIAN (угол корпуса, не кг) — такие тренировки отдаются с

  выдумывает число.

был `target_a/target_b`) ради `strength`; на фронтенде приходят строкой
(тот же паттерн, что `LeaderboardEntry.value`) и конвертируются в `number`
один раз при рендере. `tests/test_web/test_progress.py` — числа посчитаны
руками по плану, не выведены из тестируемого кода (см. "Стиль
тестирования" выше); по пути тест на `BlockLog.best_set`

`max(*working_reps, max_reps)` падал `TypeError` на пустом
`working_reps` (`max()` с одним нераспакованным int-аргументом требует
iterable), исправлено на `max((*working_reps, max_reps))` до коммита.

## Ежемесячный «тест на максимум» блока на объём (было «разгрузка», issue #89)

Реальные пользователи жаловались на два симптома одной и той же фичи
(`DELOAD_INTERVAL_DAYS`/`is_deload_a`, введена в `106ccfd`, пятая ревизия
формулы прогрессии, п.4): (1) текст просил «один рабочий подход, ориентир
50 повторений», что нереалистично для новичка (цель блока A может быть 10)
и занижено для того, кто уже у потолка (33); (2) после этого блока бот как
ни в чём не бывало продолжал блоком на силу, что читалось как баг стыковки
шагов, хотя это было задумано с самого начала (докстринг `complete_workout`
уже это фиксировал).

**Переосмысление сути (решение автора продукта, не техническое).** По
факту это никогда не было разгрузкой (снижением нагрузки) — это ежемесячная
проверка реального текущего максимума (один all-out подход в отказ), что
подтверждает и исходный докстринг («не влияет на прогресс, только в
статистику»). Формулировка в `VOLUME_DELOAD_PROMPT` (`app/bot/texts.py`)
теперь явно фреймит это как тест, не обязательную цель, и заранее
предупреждает, что блок Б дальше идёт как в обычной тренировке — тест
касается только блока на объём.

**Фиксированное число 50 сначала заменили на множитель, потом убрали
числа-ориентиры совсем (issue #105).** Первая ревизия (issue #89) заменила
50 на `VOLUME_MAX_TEST_REFERENCE_MULTIPLIER = 1.5` — ориентир в тексте
считался как `round(target_a_state.target * 1.5)`. Живое использование
(issue #105) показало тот же класс проблемы другим числом: у пользователя
с целью 26 подсказка «39» читалась как резкий обязательный скачок, даже с
оговоркой «необязательный ориентир». Константа убрана из
`app/domain/constants.py` полностью, `VOLUME_DELOAD_PROMPT`
(`app/bot/texts.py`) и его аналог в Mini App (`webapp-frontend/src/
WorkoutScreen.tsx::DELOAD_TEST_PROMPT`) теперь не называют вообще никакого
числа — только «подтянись столько раз, сколько реально сможешь».

**Идентификаторы в коде (`is_deload_a`, `is_deload` — колонка `blocks`,
`is_volume_deload_due`, `_exclude_deload_entries`, `VOLUME_DELOAD_PROMPT`/
`VOLUME_DELOAD_DONE_SUFFIX`) сознательно НЕ переименованы** — только
пользовательский текст и докстринги. Переименование `is_deload` потребовало
бы миграции колонки БД (тот же риск, что описан в разделе "Процедура
деплоя" про `*_archive_admin_reset`), переименование остальных —
мало-полезный масштабный рефакторинг без функциональной ценности. Если
терминология всё же будет переименована в коде — обновить эту запись и
имена одновременно, не оставлять описание с одними именами, а код с
другими.

**Обновление (issue #105): форма ввода теста перенесена в Mini App, не
только в боте.** До этого issue статус `deload_due` в `GET /api/workout/plan`
(`app/web/routes.py::_resolve_plan_context`) останавливал поток целиком —
Mini App показывала заглушку «эта форма пока доступна только в боте»
(`WorkoutScreen.tsx`, статус `deload_due` в `STATUS_MESSAGES`). Теперь
`is_volume_deload_due` сворачивается в тот же статус `"ready"`, что и

форсирует блок A на свой вес без переспроса (`target_a_state` подменяется

False`, до проверки `equipment_setup_required`). `target_a` в ответе

том же ответе — никакого отдельного экрана/эндпойнта для него не

Ввод — один вопрос вместо сетки рабочих подходов

`WorkoutSubmitRequest.block_a_working_reps` ослаблен с `min_length=1` до
`min_length=0` (`app/web/schemas.py`) ради этого — блок Б по-прежнему

обычных 3) сам по себе выглядел бы аномалией. Прогрессия не пересчитывается
(`is_deload_a` прокидывается в `record_workout`, та же логика заморозки

правило, только путь ввода другой.

Другие статусы Mini App Этапа 1, которые по-прежнему ведут в бота

будущее): `first_workout` (первая тренировка — замер и выбор снаряда),
`gap_retest_required` (повторный замер после долгого перерыва),
`equipment_setup_required` (переспрос снаряда при пороге перехода). Три

## Свободный формат блока Б бэкдейта (issue #88)

**Баг:** «➕ Внести свободные подтягивания» (`app/bot/handlers/free_workout.py`)
уже решал эту проблему для блока A (объёмного) — но не для блока Б.
Бэкдейт (`app/bot/handlers/backdate.py`, `WorkoutRepository.
record_backdated_workout`) требовал полную раскладку по подходам для
ОБОИХ блоков через `parse_reps` на свободный текст; если пользователь, не
помня раскладку, присылал одно число (например «60»), `parse_reps`
парсило его как `working_reps=(), max_reps=60` — то есть как честный
максимум за ОДИН подход. Это число реально уходило в
`recalculate_target(STRENGTH_BLOCK, ...)` (искажая решение
рост/застой/откат — «60» против цели читалось как явный перевыполненный
максимум, хотя на самом деле это была сумма нескольких подходов) и в
`best_set`/лидерборд (`MAX_REPS`/`MAX_WEIGHT` читают `max_reps`/
`working_reps` блока напрямую) как будто это реальный личный рекорд за
подход — оба искажения задокументированы в самом issue.

**Решение (согласовано с Кириллом, упрощённый вариант):** бэкдейт блока Б
**всегда** вне пересчёта цели — `record_backdated_workout` для блока Б
больше не вызывает `recalculate_target` вообще, `target_after_b` всегда
равен `target_before_b`, `equipment_changed_b` всегда `False`, вне
зависимости от того, введена честная раскладка по подходам или только
итог без неё. Единственный вариант «входит в каскад, если указан
максимум» explicitly отклонён — пересчёт цели блока Б происходит ТОЛЬКО
при результате основной программы (`complete_workout`, живая
тренировка). Это поведенческое изменение и для УЖЕ существовавшего
полного бэкдейта по подходам, не только для нового режима — раньше он
пересчитывал цель как обычно. Блок A бэкдейта этим не затронут (форма
ввода и `recalculate_volume_block` остались прежними, issue не просил
их трогать).

**Новое понятие в домене — `BlockLog.reported_volume`
(`app/domain/session.py`) / `Block.reported_volume`
(`app/db/models.py` + `blocks_archive_admin_reset`, миграция
`d1e5f9a3c7b8`).** Новый режим ввода блока Б бэкдейта («🔢 Не помню по
подходам — только итог», клавиатура выбора формата перед `BLOCK_B_PROMPT`)
просит итог за тренировку (обязательно) и опционально лучший подход
(максимум). Итог **не** втискивается в `max_reps`/`working_reps` — это
воспроизвело бы тот же баг другим способом (`best_set`/лидерборд снова
приняли бы сумму за один подход). Вместо этого: `working_reps=()` всегда,
`max_reps` — 0 (максимум не зафиксирован) либо реально введённое число,
`reported_volume` — итог. `BlockLog.volume` возвращает `reported_volume`,
если он задан, ИНАЧЕ обычный `sum(working_reps) + max_reps` — тот же
приоритет зеркалится в `LeaderboardRepository._METRIC_EXPR[TOTAL_VOLUME]`
(`COALESCE(b.reported_volume, ...)`) и в `sheets_export.workout_to_rows`
(колонка `volume`). `best_set`/`MAX_REPS`/`MAX_WEIGHT` его никогда не
читают — они видят только `max_reps`/`working_reps`, которые либо 0
(нет данных), либо честно введённый максимум.

**Осознанно вне scope этого issue:** «редактироваться и удаляться как
обычные тренировки» из формулировки issue — в проекте на момент issue
#88 НЕТ удаления ни одной тренировки вообще (только полный админский
сброс аккаунта, см. «🧪 Полный сброс» ниже), поэтому паритет с «обычными»
тренировками здесь означает только редактируемость. Полноценное
редактирование бэкдейт/свободных записей требует ОТДЕЛЬНОГО механизма
пересчёта: `edit_workout`/`recalculate_cascade` работают только для
записей с `sequence_number`/`participates_in_cascade=True`, а у
бэкдейта/свободных записей их нет и не будет (Кирилл явно подтвердил
«всегда вне каскада»). Спроектировать это — самостоятельная задача уровня
«план перед кодом» (см. ниже), не реализовано в issue #88.

Mini App-форма бэкдейта (`webapp-frontend/src/BackdateForm.tsx`) не
тронута — она вводит блок Б через `SetInputGrid`, отдельную числовую
ячейку на каждый подход, не свободным текстом, поэтому физически не может
воспроизвести баг «одно число вместо раскладки» (`BackdateSubmitRequest`
на веб-слое по-прежнему требует `block_b_working_reps` минимум из одного
элемента). Если тот же UX «итог + опциональный максимум» когда-нибудь
понадобится и там — это отдельная задача на фронтенд, не часть issue #88.

## Проактивный статус «сегодня отдых» + факультатив в Mini App (issue #94)

**Лимит факультативов: 1 → 2 в неделю.** `ELECTIVE_MAX_PER_WEEK`
(`app/domain/electives.py`) — единственное место, откуда `is_elective_allowed`
берёт порог; то же скользящее 7-дневное окно (`ELECTIVE_WEEK_WINDOW_DAYS`),
что и раньше, не календарная неделя — тот же принцип, что `period="week"`
у лидерборда (issue #74). Тексты, называвшие лимит буквально ("не чаще раза
в неделю"), обновлены на "не более двух раз в неделю"
(`texts.ELECTIVE_MENU_INTRO`/`ELECTIVE_LIMIT_REACHED_TOAST`) — не только
константа, иначе бот противоречил бы сам себе.

**Бот: статус стал проактивным, не только реактивным.** Раньше день отдыха
(`TrainingReadiness.TOO_EARLY`) был виден только после нажатия "Начать
тренировку" (`handle_start_workout`) — открыть раздел "Тренировка" и просто
посмотреть статус было нельзя, ничего не показывалось, пока не наткнёшься
на отказ. `app/bot/handlers/workout.py::resolve_rest_day_notice` — общая
функция (не копия правила), которую теперь вызывают оба места:
`handle_start_workout` (реактивно, как раньше) и `handle_workout_section`
(`app/bot/handlers/menu.py`, проактивно — сразу при открытии раздела, ДО
любого нажатия). Обычное меню раздела показывается следом в любом случае —
статус не прячет остальные пункты (план/бэкдейт/факультатив/редактирование),
только добавляет заметное сообщение первым. Явный текст при исчерпанном
недельном лимите (`texts.TOO_EARLY_ELECTIVE_LIMIT_REACHED`) — тот же
принцип, что и у "🧪 Полный сброс"/остальных мест: не молчаливое скрытие
кнопки, а прямое объяснение почему её нет.

**Mini App: полноценный ввод факультатива, не заглушка "делай в боте".**
Уточнение в issue прямо потребовало реального экрана, не переноса на потом.
`GET /api/elective/plan` + `POST /api/elective/submit` (`app/web/routes.py`)
— тот же путь, что `handle_electives_start`/`_finalize_elective` бота
(`app/bot/handlers/electives.py`), не отдельная копия правил: та же ротация
без повтора (`available_elective_types`) и тот же недельный лимит
(`is_elective_allowed`). Сознательно **нет** статуса `"no_access"` — бот не
проверяет подписку для факультатива (`handle_electives_start` не вызывает
`SubscriptionService`), факультатив не за паивеллом ни в одном из двух
интерфейсов; заводить в вебе гейт, которого нет в боте, значило бы разойтись
с реальным поведением, а не защитить лишний раз. Сервер пересчитывает
`total_reps` из присланного `reps_sequence` сам (не доверяет клиентской
сумме) — тот же принцип, что и у остальных Submit-эндпойнтов проекта.

`webapp-frontend/src/ElectiveScreen.tsx` — новый экран, переиспользует
`SetInputGrid`/`parseSetValue`/`parseSetValues` из `WorkoutScreen.tsx` (та
же раскладка по подходам, что и обычный ввод тренировки), с +/- кнопками
для форматов с переменной длиной последовательности (лесенка W, 3 минуты —
`min_count`/`max_count` из ответа сервера), без них для `max_reps_ladder`
(там `min_count == max_count == 4`, фиксированная сетка). Два входа в один
и тот же экран: кнопка "🎯 Факультатив" в обычном ряду режимов
`WorkoutScreen.tsx` (доступна всегда, симметрично боту) и отдельная кнопка
"🎯 Сделать факультатив" на статусе `too_early` (`state.phase === "not_ready"`)
— тот же экран в обоих случаях, `plan.is_rest_day` только меняет
поясняющий текст внутри, не саму форму.

Не проверено на живом клиенте (тот же класс ограничения песочницы, что и в
остальном разделе Mini App выше) — в этом запуске, в отличие от более
ранних записей о непостоянном доступе, и `docker compose`/Postgres, и
npm-реестр были доступны: весь бэкенд-набор (`pytest`, 912 тестов, включая
новые `tests/test_web/test_elective.py` и
`tests/test_bot/test_workout_section_rest_status.py`) и `ruff check`
реально прогнаны, не только прочитаны, и `npm run build` (`tsc -b && vite
build`) прошёл чисто. Реальное поведение внутри Telegram-клиента всё равно
не подтверждено — это отдельный класс ограничения (сеть до пакетов ≠
доступ к живому Telegram-клиенту).

## Визуализация прогресса: формула Эпли для блока Б (issue #96)

**Резина принципиально не приводится к общей шкале нагрузки, в отличие от
метрики `strength` (issue #82).** Первое предложение (обобщить через
`to_signed_load`, ту же знаковую шкалу, что уже использует `recalculate_target`
и метрика `strength`) было явно отклонено автором продукта: реальное
сопротивление резины физически неизвестно (стёртая маркировка в зале, резина
растягивается и меняет характеристики со временем) — это не "сравниваем
только внутри одной резины", а жёстче: формула Эпли (`нагрузка = (вес тела +
отягощение) × (1 + повторения/30)`) применяется ТОЛЬКО там, где вес надёжно
известен в кг — `EquipmentType.WEIGHT` и `BODYWEIGHT` (свой вес без резины/
отягощения). `BAND` исключается из расчёта Эпли полностью, так же как
`AUSTRALIAN` (там кг вообще нет — только угол корпуса). Объём блока A в
рамках одной резины (`current_equipment_progress`/`EquipmentProgress`,
уже существовал до issue #96) остался отдельным, никогда не смешиваемым
измерением — фичи issue #96 его не трогают.

**`app.domain.reports.epley_progress`** — единственный источник расчёта,
используется и ботом, и Mini App (не дублируется). `_epley_eligible`
дополнительно отсекает записи с `best_set == 0` (бэкдейт-итог блока Б без
зафиксированного максимума, issue #88, `reported_volume` задан) — "0
повторений" исказило бы формулу до голого веса снаряда.

**"Прошлая"/"первая" тренировка блока Б для % — только `participates_in_
cascade=True`** (официальная программа), бэкдейт/свободные записи участвуют
как "текущее значение" (факт), но не как анкоры сравнения — тот же принцип
разделения "факт vs официальная программа", что уже применялся к каскаду
пересчёта цели (issue #88). Ради этого в `app.domain.session.WorkoutRecord`
добавлено поле `participates_in_cascade: bool = True` (дефолт `True`, чтобы
не ломать существующие конструкторы в тестах/коде, которым это различие
было безразлично) — раньше `WorkoutRecord` вообще не хранил этот флаг,
репозиторий терял информацию о происхождении записи по дороге.

Показ — строка в уже существующем "📊 Прогресс" бота (`app/bot/handlers/
reports.py`/`format_progress_report`) и расширение `GET /api/analytics`
(`epley_progress` поле, `app/web/routes.py`/`schemas.py`) — без нового
экрана/эндпоинта, по прямому согласованию в issue. Обязательная
сноска-пояснение формулы (`texts.EPLEY_PROGRESS_FOOTNOTE`) показывается
только когда есть что объяснять (сама оценка посчиталась) — иначе выглядела
бы как объяснение отсутствующего числа. `None` целиком (карточка не
показывается) — либо нет `weight_kg` в профиле, либо ни одна тренировка
блока Б не подошла под формулу.

**Обновление (issue #110): метрика "Сила" графика "Прогресс" (issue #82,
ДО issue #96) приведена к тому же принципу — резина исключена, не сведена
к минусу.** Старая реализация (`app/web/routes.py::_progress_value`) строила
метрику `strength` через `to_signed_load` на всех типах снаряда блока Б
кроме AUSTRALIAN — резина шла со знаком минус на одну шкалу с отягощением
в кг. Это буквально то, что issue #96 явно запретил для `epley_progress`
(реальное сопротивление резины физически неизвестно — стёртая маркировка,
растяжение — несравнимо с кг ни в каком виде, даже со знаком). Дефолтный
вариант из issue (не единственный предложенный, но выбранный им по
умолчанию при отсутствии явного решения автора продукта) — "оставить
вкладку, но исправить": `_STRENGTH_ELIGIBLE_TYPES = (WEIGHT, BODYWEIGHT)`
— резина теперь тоже даёт `null` на графике, как раньше только AUSTRALIAN.
`to_signed_load()` сама не изменена — она по-прежнему обслуживает резину
для сравнений "легче/тяжелее" внутри `recalculate_target`, где обе стороны
сравнения всегда один и тот же тип снаряда (не для этого графика).

**Эта метрика и `epley_progress` — разные расчёты на разных данных, не
дублирование одного и того же.** `strength` — это голый
`to_signed_load(equipment_type, equipment_value)`, без учёта числа
повторений; `epley_progress` — `(вес тела + отягощение) × (1 +
повторения/30)`, требует `weight_kg` в профиле. После этого фикса область
допустимых типов снаряда у них совпала (`WEIGHT`/`BODYWEIGHT`), но формулы
остались разными — объединять их в один расчёт issue прямо не поручал
("не решай сам в сторону полного объединения без подтверждения"), это
отдельная задача, если Кирилл захочет её после ревью этого фикса.

**Не проверено на реальном распределении пользователей по типам снаряда
блока Б** — нет доступа к проду из песочницы (тот же класс ограничения,
что и в остальном разделе Mini App выше), поэтому нельзя было заранее
оценить, у какой доли активных пользователей график "Сила" не опустеет
после исключения резины. Если после деплоя окажется, что график пустой у
большинства (блок Б у них ещё долго на резине) — следующий шаг не чинить
дальше эту метрику, а обсудить с Кириллом её замену/объединение с
`epley_progress` (%-прирост по Эпли уже показывает то же самое "как
меняется сила блока Б" без пустых точек на резине, просто в виде текста
аналитики, не графика).

## Чередующаяся тяжёлая тренировка блока Б (issue #97)

**Только когда блок Б уже на `EquipmentType.WEIGHT`.** Нечётная тренировка
блока Б в рамках сета из 12 — обычная прогрессия (как раньше), чётная —
фиксированные `HEAVY_BLOCK_FIXED_REPS` (3) повторения в каждом из 5
подходов (4 рабочих + подход на максимум, та же раскладка ввода 4+1, что и
обычно — парсинг не меняется вообще, меняется только текст приглашения) на
повышенном весе. Пока блок Б на резине/собственном весе (ещё не перешёл на
отягощение) — чередования нет вообще, каждая тренировка обычная: явное
решение автора продукта (тот же принцип, что и у `epley_progress`/issue
#96 — резина принципиально не приводится к шкале кг).

**Позиция в сете** — `WorkoutSet.workouts_completed` (счётчик ДО инкремента
следующей тренировки, тот же, что закрывает сет по `SET_LENGTH`): нечётное
значение здесь означает, что следующая тренировка чётная/тяжёлая.
`WorkoutRepository._resolve_next_state` вычисляет `NextBlockState.is_heavy`
только когда снаряд блока Б уже `WEIGHT` и `needs_new_equipment=False` —
первая тренировка сразу после перехода на отягощение (или после отката
неудачного перехода) никогда не тяжёлая, чередование стартует со следующей.

**`is_heavy` не хранится персистентно как отдельное "включено/выключено"
состояние — вычисляется заново при каждом резолве** (тот же принцип, что
`needs_new_equipment`/`is_retry_allowed` в этом же файле), но сам факт
"эта конкретная историческая тренировка была тяжёлой" хранится на
`Block.is_heavy` (миграция `b7f3a9c1e4d2` + синхронно в
`blocks_archive_admin_reset`, см. правило про пять архивных таблиц выше) —
без этого поля нельзя было бы восстановить, какой вес/цель считать
"нормальными" для следующей чётной/нечётной тренировки задним числом.

**Тяжёлая тренировка не участвует в пересчёте прогрессии силового блока** —
`target_before == target_after`, `equipment_changed=False` всегда, тем же
приёмом, что `is_deload` у блока A (`recalculate_cascade`,
`WorkoutRepository.complete_workout`/`edit_workout`). Из истории она
исключается тем же способом, что `is_deload` для блока A —
`_exclude_heavy_entries`/`_exclude_deload_entries` — везде, где блок Б
берёт "последнее состояние" статическим срезом истории (`_resolve_next_state`,
`_weak_streak`, `_preceding_chain_state`): без этого следующая ОБЫЧНАЯ
тренировка унаследовала бы повышенный вес или объём тяжёлой как базу для
сравнения "слабая/сильная" — несопоставимые шкалы (фикс. 3 повторения на
повышенном весе vs обычная прогрессия). Внутри `recalculate_cascade`
(последовательный проход, не статический срез) это устроено проще —
тяжёлая запись просто не обновляет бегущие `weak_streak_b`/`prev_volume_b`/
`target_b`, как и `is_deload` для блока A.

**Расчёт веса — переиспользует формулу Эпли (issue #96), не дублирует.**
`app.domain.constants.epley_multiplier` — общий множитель `(1 + reps/30)`,
вынесенный из `app.domain.reports._epley_load` в `constants.py` (единственное
место без риска циклического импорта между `reports.py`/`progression.py`).
`suggest_heavy_weight_kg` (`app/domain/progression.py`) — только для ПЕРВОЙ
тяжёлой тренировки (когда предыдущей тяжёлой ещё не было в истории): медиана
`HEAVY_BLOCK_MEDIAN_REPS` (5) повторений обычного блока → эквивалент 1ПМ →
обратно вес на `HEAVY_BLOCK_FIXED_REPS` (3) повторения — множитель 35/33
(≈+6%), округление вверх до `HEAVY_WEIGHT_ROUND_TO_KG`. Дальше подсказка
несёт сама история тяжёлых тренировок (`resolve_heavy_weight_growth`,
вызывается из `_resolve_next_state`, ищет последний `Block.is_heavy=True`
по всей истории, не только среди соседних записей) — нет отдельного
персистентного поля "текущая тяжёлая цель": оно и не нужно, та же
экономия, что уже применена к `target_b` (просто читается из
`target_after` последнего блока, не хранится отдельно).

**`HEAVY_WEIGHT_ROUND_TO_KG = 0.5` — НЕ `WEIGHT_ROUND_TO_KG` (1.25, шаг
блинов обычного силового блока).** Подтверждено явно автором продукта
отдельным сообщением в issue (изначально в тексте issue ошибочно
предполагалось 2.5 кг) — при фиксе всего 3 повторений шаг 1.25 кг слишком
грубый для регулярного мелкого прогресса.

**Триггер роста веса — единичный порог по 5-му подходу, не стрик.** Если
`max_reps` (5-й, "на максимум" подход тяжёлой тренировки) `>=
HEAVY_GROWTH_MAX_REPS_THRESHOLD` (5) — следующая тяжёлая предлагается на
`+HEAVY_WEIGHT_ROUND_TO_KG` тяжелее, иначе вес остаётся прежним. Явно
согласовано с автором продукта (буквальные примеры: "3 3 3 3 5" → рост,
"3 3 3 3 4" → без роста) — **без отката** при провале, в отличие от
обычного силового блока (`WEAK_STREAK_ROLLBACK_THRESHOLD`, стрик из 3
подряд слабых). Первая версия плана (стрик из 2 подряд успешных тяжёлых
тренировок для варианта "5×3 без отдельного максимума") была отменена
автором продукта в процессе ревизии — итоговая структура ввода осталась
4+1 (как у обычного блока Б), не чистые 5×3.

**Бот** (`app/bot/handlers/workout.py`/`equipment.py`) — план/приглашение
блока Б показывают другой текст на тяжёлой тренировке
(`WORKOUT_PLAN_BLOCK_B_LINE_HEAVY`/`BLOCK_B_PROMPT_HEAVY`), подсказка веса
(`heavy_equipment_value`) подставляется в `equipment_results["b"]` вместо
обычного унаследованного веса в `_begin_equipment_setup` — это работает
только потому, что тяжёлая тренировка гарантированно `needs_new_equipment=
False` (см. выше), то есть никогда не попадает в очередь `equipment_queue`
с вопросом о типе снаряда; пользователь может поправить подсказку тем же
"✏️ Изменить вес", что и у обычного веса. **Mini App** (`GET /api/workout/plan`,
`app/web/routes.py::_resolve_plan_context`) — тот же приём: `equipment_b.value`
уже содержит `heavy_equipment_value`, `WorkoutPlanResponse.is_heavy_b`
(`app/web/schemas.py`) говорит фронтенду показать другой заголовок/подпись
блока Б (`webapp-frontend/src/WorkoutScreen.tsx::BlockForm`, проп `isHeavy`)
— раскладка полей ввода та же (4 рабочих + подход на максимум), сервер
(`submit_workout`) не меняется вовсе: `is_heavy` для записываемой
тренировки вычисляется внутри `WorkoutRepository.complete_workout`
заново, тем же кодом, что и для бота, не передаётся с клиента.

**Обновление (issue #117): график "Прогресс → Сила" помечает тяжёлые точки,
не только план блока Б.** Легитимный периодический скачок веса (чередование
issue #97) на графике факта (issue #82) читался пользователем как аномалия
данных — там нет заголовка блока, который объяснял бы это, в отличие от

(`app/web/routes.py::get_progress`) — прямой проброс уже существующего

линии, плюс отметка в hover-тултипе и легенде графика, когда среди видимых
точек есть хотя бы одна тяжёлая. Текст-пояснение под графиком
(`CHART_METRIC_HINTS.strength`) — обязательный минимум по формулировке
issue — обновлён отдельно от маркеров, не вместо них.

## Push-уведомление о тренировочном дне (issue #100)

**Отдельный воркер, не CronTrigger на фиксированный UTC-час.** Все
остальные периодические рассылки (`send_weekly_reports`,
`send_weekly_digest_reminder`) шлют всем в один и тот же момент UTC —
здесь так нельзя: уведомление должно прийти в выбранный ПОЛЬЗОВАТЕЛЕМ
локальный час (`users.training_reminder_hour`, `app/db/models.py`), а у
пользователей разные часовые пояса (`users.timezone`). `app/workers/
training_reminder.py::send_training_reminders` — `IntervalTrigger` каждые
`POLL_INTERVAL_MINUTES` (15) минут, опрашивает всех `list_onboarded()`,
для каждого сравнивает текущий локальный час (`ZoneInfo(user.timezone)`) с
его `training_reminder_hour` (`NULL` → `DEFAULT_TRAINING_REMINDER_HOUR`,
9 — тот же принцип NULL-значит-дефолт, что у `timer_preferences`, issue
#59/#90). Именно этот кейс раньше был отмечен как "ещё не реализованная
задача" в комментарии `app/workers/weekly_report.py::register` — теперь
реализована, комментарий обновлён.

**`users.training_reminder_last_sent_date` (локальная дата, не UTC) —
обязательная защита от дублей.** Без неё опрос каждые 15 минут отправил бы
одно и то же уведомление 4 раза подряд, пока текущий локальный час
совпадает с выбранным. Условие отправки — `check_training_readiness` (тот
же домен, что использует `resolve_rest_day_notice`, issue #94) даёт
статус, отличный от `TOO_EARLY`, на UTC-дату "сегодня" — намеренно та же
точка отсчёта, что и везде в проекте (`resolve_rest_day_notice`,
`handle_start_workout`), готовность к тренировке нигде не считается по
локальному часовому поясу пользователя; `local_now` в воркере участвует
только в выборе часа отправки и в анти-дублировании. У пользователей без
единой тренировки в истории уведомление не отправляется вообще (нечего
сравнивать, первая тренировка — не "по расписанию", а разовый замер).

**Гранулярность — час, не HH:MM.** Issue допускал упрощение ("выбор
времени, если это не сильно усложняет") — выбор с точностью до часа
(`training_reminder_hour: SmallInteger`, кнопки `−1 ч`/`+1 ч`) даёт
пользователю контроль без отдельного экрана ввода произвольного времени;
достаточно для "утреннее/дневное/вечернее напоминание", не событие с
точностью до минуты.

**Тумблер — единственная персистентная настройка бота с явным дефолтом
"выключено"** (`training_reminder_enabled: Boolean, server_default=
'false'`), в отличие от `timer_preferences`/`sound_volume_percent` (там
сама механика всегда активна, настраивается только число) — молчаливая
подписка на push-рассылку без явного согласия недопустима, тот же принцип,
что `leaderboard_display_name IS NULL` = "анонимно по умолчанию" (issue
#67), только тут дефолт — "выключено", а не "не показывать имя".

**Экран — `app/bot/handlers/training_reminder.py`, отдельный от
`profile_edit.py`, доступен кнопкой "🔔 Напоминание о тренировке" из
"Профиля".** Не переиспользует FSM-паттерн анкеты (там правится факт о
пользователе — вес/рост/пол/дата рождения/часовой пояс), это настройка
поведения бота — тумблер и час пишутся сразу по нажатию кнопки, экран
перерисовывается in-place (`edit_text`), без промежуточного состояния
ожидания ввода. Явное предупреждение прямо на экране, если часовой пояс
не указан (уведомление в этом случае технически не отправится — `not
user.timezone` в воркере), а не молчаливое "ничего не произойдёт" — тот
же принцип, что у "🧪 Полный сброс"/лимита факультативов (issue #94).

**Mini App-аналога настройки нет** — issue не уточнял вторую площадку
явно, а сама механика (push от бота, не статус экрана) не имеет смысла
внутри веб-интерфейса, открытого только пока Mini App активна. Если
понадобится синхронный переключатель и там — отдельная задача (та же
логика, что `GET/PUT /api/timer/preferences`, просто новые поля).

## Прочие устоявшиеся решения

- **Архивировать, не удалять.** Любой «сброс»/«убрать» исторических
  данных — перенос в `*_archive_v1`/`*_archive_admin_reset`-таблицу, не
  `DELETE`. Перед удалением enum-значения из БД (см. пример с Tribute,
  `8a1f4c6e9b2d`) — сначала вручную проверить, нет ли исторических строк
  с этим значением; если есть — не удалять значение, оставить как
  «исторический, не используется», задокументировав это в комментарии
  рядом с определением enum.
- **Одна причина падения = один хендлер, не общий `try/except` в проде
  молча.** `cd0eefa` завёл глобальный обработчик необработанных
  исключений на уровне диспетчера — он логирует и уведомляет админа
  (`ADMIN_UNHANDLED_EXCEPTION_NOTIFICATION`), не проглатывает молча.
  Если пишешь код, который может упасть предсказуемо — лови и обрабатывай
  сам, не полагайся на этот catch-all как на способ скрыть баг.
  `state.clear()` — до записи в БД в `_finalize_workout`, не после
  (гонка двойного тапа: см. `2b92942`).
- **`app.bot.parsing.MAX_REPS = 999`** — единственный источник верхнего
  предела на число повторений (`parse_reps`/`parse_int_sequence`,
  `onboarding.py`). Не заводить локальных копий лимита в отдельных
  хендлерах (баг, `673bf65`: старый `MAX_REASONABLE_REPS=100` в
  `onboarding.py` отклонял обычные трёхзначные результаты вроде 102).
- **Числовые константы продуктовых решений, не научных фактов** —
  фиксировать явно в докстринге при вводе (пример: потолок 30 повторений,
  откат до 20/30, старт веса 5 кг, шаг 5% в `app/domain/progression.py` —
  докстринг `recalculate_volume_block` явно отделяет, что построено на
  принципах прогрессивной перегрузки, а что — собственный выбор чисел).

## Известный класс бага: `message.text` — `None` у сообщения с картинкой

Прод-инцидент (issue #69): рассылка "📢 Рассылка всем" и еженедельный
дайджест (`handle_weekly_digest_reply`) брали текст из `message.text`
напрямую и передавали его в `bot.send_message`. Когда админ присылает
сообщение с картинкой, Telegram кладёт подпись в `message.caption`, а
`message.text` остаётся `None` — `aiogram`/pydantic отклоняет
`SendMessage(text=None)` валидацией (`1 validation error for SendMessage:
text — Input should be a valid string`), рассылка падала целиком, ни один
пользователь не получал сообщение. Тот же провал ждал
`WeeklyDigestRepository.record` (колонка `text` — `NOT NULL`).

Фикс — `app/bot/handlers/admin.py::_broadcast_source_text` (`message.text
or message.caption`) как единственный источник текста для рассылки, и
ветвление на `bot.send_photo(..., caption=...)`, если в сообщении есть
`message.photo` — иначе картинка терялась бы молча, а подпись ушла бы как
обычный текст без неё. Тот же паттерн (`message.text` без учёта
`message.photo`/`message.caption`) правился заодно и в `handle_admin_dm_text`
(личное сообщение пользователю из карточки в `/admin`) — тот же класс
бага, тот же вызывающий код мог получить картинку так же легко.

**Правило**: в любом хендлере, принимающем свободный текст от админа для
пересылки другому пользователю, не читать `message.text` напрямую, если
сообщение может прийти с вложением — проверять `message.photo` и
использовать `message.caption` как текст в этом случае.

## Известный класс бага: альбом (несколько фото) — Telegram шлёт его как
## несколько Update, не один

Прод-инцидент (issue #72), найден сразу после фикса issue #69 выше: админ
прикрепил к рассылке НЕСКОЛЬКО фото — ушло одно фото с подписью, остальные
отдельными сообщениями без текста. Причина не в `_broadcast_to_onboarded_
users` самой по себе (она уже брала `message.photo`/`message.caption`
правильно), а в том, что Telegram доставляет альбом не одним сообщением с
несколькими фото, а несколькими отдельными Update с общим
`media_group_id` — по одному Update на каждое фото. `aiogram`-диспетчер в
реальном polling обрабатывает Update конкурентными asyncio-задачами
(`Dispatcher._polling`, `handle_as_tasks=True` по умолчанию), не дожидаясь
хендлера предыдущего Update — каждое фото альбома по отдельности ловило
`waiting_for_broadcast_text` и самостоятельно запускало полную рассылку.

Фикс — `app/bot/middlewares.py::MediaGroupMiddleware`, outer-middleware,
подключенный только на `admin_router.message`
(`app/bot/handlers/admin.py`, не глобально на весь `Dispatcher`, чтобы не
трогать альбомы вне админских сценариев). Буферизует части одного альбома
по `media_group_id`: первая часть ждёт `ALBUM_DEBOUNCE_SECONDS`, копит
остальные части (обычно приходят с разницей в десятки-сотни мс) в общий
список и передаёт их все хендлеру одним вызовом через `data["album"]`;
остальные части сами добавляют себя в буфер и завершаются без вызова
хендлера — иначе он запустился бы ещё раз на каждую из них.
`_broadcast_to_onboarded_users`, `handle_admin_broadcast_text`,
`handle_weekly_digest_reply` и `handle_admin_dm_text` при непустом `album`
шлют `bot.send_media_group` с `InputMediaPhoto(caption=...)` на одном
элементе массива вместо `send_photo` на каждое фото по отдельности; caption
ищется по ВСЕМ частям альбома (`_album_caption`), не только по первой
пришедшей — Telegram не гарантирует, что подпись окажется именно на
дошедшей до буфера первой.

**Правило**: любой хендлер, ожидающий «одно сообщение = один Update» (в
частности — рассылки/пересылка от админа), не может просто проверять
`message.photo` для случая с несколькими фото — Telegram гарантированно
разобьёт такое сообщение на несколько Update с общим `media_group_id`.
Нужна буферизация по `media_group_id` до хендлера (см.
`MediaGroupMiddleware`), не точечная правка внутри самого хендлера.

## Нормативы WSF (стритлифтинг) — вторая система оценки рядом с ГТО (issue #104)

**Данные — `app/domain/data/wsf_multirep_norms.json` (коммит `7fa0f60`),

## Удаление тренировок (issue #146) — бэкдейт/свободные, потом и каскадные

**Пробел issue #106 закрыт частично, по дизайну, не по недосмотру.** Issue
#146 явно просил решить и описать, должно ли удаление ОБЫЧНОЙ (каскадной)
тренировки запускать `recalculate_cascade`, а не решать это молча — вопрос
остаётся открытым, ждёт ответа Кирилла. Реализовано только удаление
записей с `participates_in_cascade=False` (бэкдейт, `record_backdated_workout`,
и свободные подтягивания, `record_free_workout`) — `DELETE
/api/history/{workout_id}` (`app/web/routes.py::delete_history_workout`)
для тренировки цепочки каскада отвечает 400, не 200/204: не реализовано, не
запрещено навсегда.

**Архивирует, не удаляет молча — переиспользует существующие
`workouts_archive_admin_reset`/`blocks_archive_admin_reset`** (миграция
`b41882a0e3e8`, "🧪 Полный сброс"), не заводит третий парный набор архивных
таблиц под ещё один сценарий "не терять удалённые строки". Компромисс,
принятый сознательно (`app/services/workout_deletion.py`, докстринг): имя
таблиц ("...admin_reset") теперь чуть шире своего первоначального смысла
(не только полный сброс аккаунта админом, но и штатное удаление одной
записи самим пользователем), но повторно использует уже поддерживаемый в
актуальном состоянии слепок схемы `workouts`/`blocks` вместо дублирования
обязательства синхронизации при каждом `ALTER TABLE` (см. правило про пять
`*_archive_admin_reset` таблиц в разделе "Процедура деплоя" выше — оно
теперь тоже относится и к этому пути, не только к `admin_reset.py`).

**Найдена и обработана реальная скрытая связь схемы, не упомянутая в самом
issue: `record_backdated_workout` (в отличие от `record_free_workout`) сам
инкрементирует `workout_sets.workouts_completed` при создании** (тот же
счётчик, что закрывает сет по `SET_LENGTH` и определяет чётность `is_heavy`
чередующейся тяжёлой тренировки блока Б, issue #97) — без обратного
decrement при удалении такой записи счётчик навсегда остался бы завышенным
на 1, перманентно сдвигая чётность `is_heavy` для ВСЕХ последующих
тренировок блока Б, не только в редком граничном случае. `delete_
noncascade_workout` декрементирует счётчик для бэкдейт-записей (не для
свободных — те его не трогали и при создании). Сознательно НЕ реализовано:
откат `WorkoutSetStatus.COMPLETED → ACTIVE`, если удаляемая запись была
именно той, что закрыла сет ровно на `SET_LENGTH`, — `ensure_active_
workout_set` уже мог успеть открыть СЛЕДУЮЩИЙ сет к моменту удаления по
любому обращению к плану между записью и удалением (не только при явном
старте тренировки), реоткрытие старого тогда означало бы два `ACTIVE` сета
одновременно у одного пользователя. Узкий и непроверяемый без реального
инцидента граничный случай — не решён молча, задокументирован здесь как
известное ограничение на будущее, а не тихо проигнорирован.

**UX** — кнопка "🗑 Удалить" рядом с "✏️ Изменить" в `HistoryScreen.tsx`,
показывается только при `HistoryEntry.is_deletable`
(`HistoryEntryResponse.is_deletable` в `app/web/schemas.py` — на момент
issue #146 совпадает с `is_backdated`, но это два разных поля с бэкенда, не
выведенное на фронтенде переиспользование одного и того же факта).
Подтверждение — `window.confirm`, тот же паттерн, что уже применяется в
`App.tsx` для потери прогресса живой тренировки при уходе с экрана — в
проекте нет отдельного кастомного confirm-компонента, заводить его ради
одной кнопки не стали.

**Обновление: удаление ОБЫЧНЫХ (каскадных) тренировок — решение Кирилла,
вариант A (пересчитывать каскад).** Реальный кейс из ответа на открытый
вопрос выше: тренировка задублирована по ошибке — без пересчёта каскада
дубль продолжал бы искажать прогрессию целей задним числом у всех
последующих тренировок цепочки, само удаление не решало бы проблему дубля.
`is_deletable` теперь всегда `True` (поле не убрано — оставлено на случай
будущего сужения набора удаляемых записей); `DELETE
/api/history/{workout_id}` для каскадной тренировки больше не 400, а
`delete_cascade_workout` (`app/services/workout_deletion.py`).

Пересчёт — `WorkoutRepository.recalculate_cascade_on_delete`, механика
идентична каскадной части `edit_workout` (тот же `_preceding_chain_state`/
`recalculate_cascade`, тот же принцип "`equipment_type`/`is_deload`/
`is_heavy` каждой последующей записи — факт, не пересчитывается"), с одной
разницей: `edit_workout` сначала пересчитывает саму отредактированную
запись и стартует каскад от её НОВОГО `target_after`, а здесь редактируемой
записи больше нет вообще — каскад для `chain[position + 1:]` стартует
прямо от состояния ДО удаляемой записи (`_preceding_chain_state(chain,
position)` и weak/stall-стрики по `chain[:position]`, без "+1 за саму
запись"). Работает единообразно независимо от того, была ли удаляемая
запись сама `is_deload`/`is_heavy` — `_preceding_chain_state` смотрит
только на `chain[:position]`, саму удаляемую запись не читает вовсе.

**Смены снаряда между удаляемой и последующими тренировками — тот же
риск, что уже несёт `edit_workout`, не новый, привнесённый именно
удалением.** Каждая последующая запись пересчитывается по формуле
(потолок цели в `recalculate_volume_block`/`recalculate_target`) заново
решает, должен ли был случиться переход на новый снаряд, не читая
исторический `equipment_type` записи как признак перехода — пересчитанная
траектория теоретически может разойтись с тем, что реально было записано
на конкретном снаряде исторически. Тот же механизм уже год как используется
в проекте для `edit_workout`, отдельно для удаления не переосмыслен —
согласовано с автором issue именно в этих границах (см. его уточнение про
"опиши риски и подожди подтверждения по конкретному пункту").

`sequence_number` всех последующих записей цепочки сдвигается на -1, чтобы
не оставить дыру — `complete_workout` вычисляет `sequence_number` новой
тренировки как `len(cascade_chain) + 1` (количество, не `max + 1`), дыра
привела бы к коллизии с уже существующим номером при следующей живой
тренировке. Безопасно в пределах одной транзакции благодаря
`UNIQUE(user_id, sequence_number) DEFERRABLE INITIALLY DEFERRED`
(`app/db/models.py::Workout`, уже существовало до этого issue ради NULL у
STARTED-тренировок) — проверяется в Postgres только при COMMIT, не после
каждого отдельного UPDATE, поэтому временное совпадение номеров
(удаляемая запись ещё не удалена, а следующая уже переномерована на её
место) внутри транзакции не конфликтует.

Декремент `workout_set.workouts_completed` — тот же побочный эффект issue
#97 (чётность `is_heavy`), что уже обрабатывался для бэкдейта выше, теперь
и для каскадных: `complete_workout` инкрементирует этот счётчик всегда, без
отката чётность тяжёлой тренировки блока Б сдвинулась бы навсегда. Общий
код архивирования (`_archive_and_delete` в `workout_deletion.py`) вынесен
в отдельную функцию, переиспользуемую `delete_cascade_workout` и
`delete_noncascade_workout` — не дублирует один и тот же raw SQL под двумя
разными докстрингами.

Гейт STARTED-тренировки (`_history_is_editable`, тот же, что уже
использует правка) добавлен на удаление отдельно от прежней проверки
`participates_in_cascade`: живая тренировка в процессе (`sequence_number`
ещё `None`) физически не находится в `_cascade_chain`, попытка удалить её
до этого гейта падала бы `StopIteration` внутри
`recalculate_cascade_on_delete` вместо понятной 400-ошибки.

Причина — `webapp-frontend/index.html` грузит настоящий
`https://telegram.org/js/telegram-web-app.js` блокирующим `<script>` в
`<head>`, БЕЗ `async`/`defer`. `page.addInitScript`
(`fixtures/telegramMock.ts`) гарантированно выполняется раньше ЛЮБОГО
скрипта страницы — но это не помогает, потому что "раньше" не то же
самое, что "последний": сам `telegram-web-app.js`, выполняясь ПОСЛЕ
addInitScript вне настоящего Telegram-клиента, тоже пишет в
`window.Telegram.WebApp` — своим собственным объектом с пустым `initData`
— целиком ПЕРЕЗАПИСЫВАЯ то, что только что положил мок, а не дополняя
его. `App.tsx` в фолбэке (issue #23) получает `telegramWebApp.initData ===
""` и уходит в ветку "initDataRaw is empty" ещё до первого запроса к
`/api/hello` — одинаково на каждом сценарии, независимо от того, что
сидировал `scripts/e2e_seed.py` под конкретный `telegram_id`. Это
объясняет и то, почему падение выглядело "как будто зависло" (тест ждёт
текст, специфичный для успешного статуса, которого never будет, пока
initData считается пустой) — не флуктуацию по времени сети, хотя реальный
внешний запрос к `telegram.org` из блокирующего тега сам по себе тоже был
не идеальным решением независимо от этой находки.

Фикс — `fixtures/telegramMock.ts::mockTelegramWebApp` теперь СНАЧАЛА
регистрирует `page.route("https://telegram.org/js/telegram-web-app.js",
...)`, отдающий пустой файл вместо реального скрипта, и только потом
кладёт мок в `window.Telegram.WebApp` через `addInitScript` — реальный
скрипт больше не выполняется вообще, значит и не может перезаписать мок,
независимо от порядка тегов в `<head>`. `index.html` (продакшен-код) не
тронут — реальный Telegram-клиент никогда не подгружает эту библиотеку
сам (мост уже встроен в клиент), поведение файла для реальных
пользователей не меняется.

Проверено чтением исходника `init-data-py==0.2.7` (`InitData.calculate_hash`/
`Object.to_json`/`types/user.py`) — установлен через `pip install --target`
(в этой сессии `unzip`/`python3 -c` были заблокированы политикой песочницы,
как и `npm`/`npx`/`playwright`, тот же класс ограничения, что и в предыдущих
попытках этого issue, но `pip install --target` сработал и дал читаемые
`.py`-файлы без необходимости распаковывать архив руками) — алгоритм подписи
в `fixtures/initData.ts` совпадает с тем, что реально проверяет библиотека
байт-в-байт (порядок полей, `separators=(",", ":")`, `ensure_ascii=False`,
`replace("/", "\\/")`), это НЕ было причиной падения. Не проверено вживую
Playwright-прогоном в этой сессии — тот же класс ограничения песочницы, что
и во всех предыдущих попытках этого issue. Следующий прогон в GitHub Actions
— первое реальное подтверждение того, что перехват сетевого запроса
действительно устраняет падение.

## Редактирование/удаление личных резин в Mini App (issue #148)

**До этого issue список резин (`EquipmentItem`) был только `POST`/`GET`
(issue #124, PR 3) — ни переименовать, ни удалить ошибочно заведённую
резину было нельзя ни в одном интерфейсе.** `PATCH`/`DELETE
/api/equipment/band-items/{id}` (`app/web/routes.py`) закрывают это;
`EquipmentItemRepository.rename`/`.delete` — ownership-проверка (404, не
403, тем же принципом, что и остальные проверки в этом файле).

**Удаление — настоящий `DELETE`, не архивация.** Резина — личный
справочник пользователя, не история тренировок (в отличие от
`workouts`/`blocks`, которые архивируются при "🧪 Полный сбросе") — прямое
удаление здесь корректно и ожидаемо.

**Схема была устроена так, что удаление сломало бы историю — это
поправлено как часть issue, не оставлено.** `blocks.equipment_item_id`/
`elective_workouts.equipment_item_id` были FK без `ON DELETE` (то есть
Postgres по умолчанию `RESTRICT`) — `DELETE` на уже использованную резину
падал бы `IntegrityError`. Миграция `e7c2a4f9d1b3` меняет обе FK на
`ON DELETE SET NULL` и добавляет `Block.equipment_item_name`/
`ElectiveWorkout.equipment_item_name` (+ `blocks_archive_admin_reset`, по
правилу "пяти архивных таблиц" из раздела "Процедура деплоя" выше) —
снапшот названия резины НА МОМЕНТ этой конкретной тренировки, заполняется
`WorkoutRepository`/`ElectiveWorkoutRepository` при записи блока (не
задним числом при удалении — переименование резины после тренировки не
должно менять то, что показывает уже записанная история). Бэкфилл в той
же миграции — до этого issue резину нельзя было переименовать, значит
текущее `equipment_items.name` совпадает с названием на момент любой уже
существующей записи. `WorkoutDraft.block_*_actual_band_item_id` — не FK
(черновик не хранит снапшот плана вообще, issue #61), `EquipmentItemRepository.delete`
обнуляет их вручную, чтобы черновик не указывал на исчезнувший id.

**Побочный найденный баг (не потребовал доступа к проду, поймано чтением
кода `current_equipment_progress`/`_same_equipment`, `app/domain/reports.py`
+ идентичный предикат в `app/domain/recommendations.py`) — две РАЗНЫЕ

**Обновление: реальный прогон интеграционных тестов автором продукта нашёл

остальное в identity map) expired, включая PK-атрибут. Синхронное чтение
`user_row.id` при вычислении аргумента для

ДО того, как этот `await` реально запускается (Python вычисляет аргументы
вызова раньше, чем передаёт управление корутине) — то есть вне

## Известный класс бага: `Input`/`Select` из `@telegram-apps/telegram-ui` без `Section` — визуально невидимы (issue #170)

`AppRoot` (`webapp-frontend/src/main.tsx`) задаёт CSS-переменные темы
(`--tgui--bg_color`/`--tgui--section_bg_color`/`--tgui--outline` и т.п.) на
весь поддерево, но сам не даёт `Input`/`Select` контрастного фона — их
собственный фон (`background: var(--tgui--bg_color)`) совпадает с фоном
страницы, а рамка (`box-shadow` с `--tgui--outline`, ~5% непрозрачности)
почти не видна. Именно `<Section>` (свой `background:
var(--tgui--section_bg_color)`, обычно серый на светлой теме) даёт полю
видимый контраст — без неё поле технически в DOM, принимает фокус/ввод, но
выглядит пустым местом, ни подписи `header`, ни рамки не разглядеть.
`OnboardingScreen.tsx` был единственным местом в проекте, где `Input`/
`Select` рендерились не через `<Section>` (везде — `ProfileEditForm.tsx`/
`BackdateForm.tsx`/`HistoryEditForm.tsx` — уже оборачивали); исправлено
обёрткой `<Section className="block-section">` вокруг полей на каждой фазе
(`baseline_input` и все 5 шагов анкеты), тем же паттерном, что и в
остальных формах.

**Правило**: `Input`/`Select` из этого кита всегда оборачивать в
`<Section>` (или `<List>`), не рендерить напрямую в `<div>` — сам компонент
не подскажет об этом ни ошибкой, ни визуальным сигналом сильнее, чем
"как будто светлый на светлом".

## Graphify — карта кода для расследований

`graphifyy` (пакет на PyPI, команда `graphify`) уже в `[project.optional-
dependencies].dev` — доступен после обычного `pip install -e ".[dev]"`. Это
граф вызовов/импортов/комментариев по AST (никакого LLM, детерминированно,
~10-20с на весь репозиторий) — не продуктовая зависимость, только
инструмент расследования для агента.

**Когда использовать:** issue требует понять, как связаны несколько файлов/
функций, которые не лежат рядом друг с другом (пример из практики: `is_heavy`
блока Б → `suggest_heavy_weight_kg`/`resolve_heavy_weight_growth`
(`app/domain/progression.py`) → `_exclude_heavy_entries`/`recalculate_cascade`
(`app/db/repositories/workouts.py`) → `epley_progress`
(`app/domain/reports.py`) — раньше на такое уходила серия отдельных `grep`).
Не нужен для простых точечных правок в одном файле.

**Как использовать:**
```
graphify update .                          # построить/обновить граф (без LLM)
graphify query "вопрос своими словами"     # BFS по графу, находит релевантные узлы
graphify explain "имя_функции_или_файла"   # что это и с чем связано
graphify path "A" "B" --undirected         # как A и B связаны между собой
```
`graphify-out/` — сгенерированное, не коммитить (в `.gitignore`), пересобирается
командой `update` за секунды при повторных запусках (инкрементально, по
`manifest.json`).

Ограничение: `graphify explain`/`query` ищут по совпадению имени узла — для
неоднозначных общих слов (например, ровно как называется файл миграции)
может зацепиться не за то, что имелось в виду; формулируйте запрос ближе к
доменному термину/имени функции, а не к общему слову.
