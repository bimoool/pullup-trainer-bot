# pullup-trainer-bot

Telegram-бот-тренер по подтягиваниям. Python 3.12, aiogram 3, PostgreSQL 16,
SQLAlchemy 2 (async), Alembic, APScheduler, Redis (FSM-хранилище), gspread,
openpyxl. Long polling, без вебхука. Хостится на VPS `192.241.141.47`
(root SSH, `/root/pullup-trainer-bot`, GitHub `bimoool/pullup-trainer-bot`).

**VPS общий с другим проектом** (`reeltrack-bot`/`reeltrack-postgres`,
контейнеры `reeltrack-*`, отдельная директория `/root/reeltrack-bot`) —
все `docker compose`-команды выполнять из `/root/pullup-trainer-bot`, без
`-p`/глобальных флагов, которые могли бы задеть чужие контейнеры. Порт `db`
на хосте — эфемерный (`127.0.0.1::5432`, `docker compose port db 5432`
чтобы узнать) именно для того, чтобы не конфликтовать с другими локальными
проектами.

## Архитектура

- **`app/domain/`** — чистая бизнес-логика (прогрессия, аномалии,
  ачивки, правила готовности к тренировке, отчёты). Ни одного импорта
  aiogram или SQLAlchemy — проверяется буквально (`grep -rl
  "aiogram\|sqlalchemy" app/domain/` должен быть пуст). Функции чистые,
  датаклассы `frozen=True`, деньги/вес — `Decimal`, не `float`. Домен
  покрыт unit-тестами в `tests/test_*.py` (корень `tests/`), без Postgres.
- **`app/db/repositories/`** — один репозиторий на агрегат
  (`WorkoutRepository`, `UserRepository`, ...), только они трогают
  SQLAlchemy-сессию и конвертируют ORM ↔ доменные датаклассы
  (`app/domain/session.py: WorkoutRecord/BlockAssignment` и т.п.).
  Интеграционные тесты — `tests/test_repositories/`, на реальном Postgres.
- **`app/services/`** — оркестрация поверх репозиториев: пишет через
  репозиторий, шлёт событие в `EventRepository`, начисляет монеты
  (`GamificationService`), проверяет ачивки. Тесты — `tests/test_services/`,
  реальный Postgres.
- **`app/bot/handlers/`** — тонкий слой aiogram поверх `services`/`domain`.
  Не должен содержать бизнес-логику прогрессии/начислений — только сбор
  ввода, FSM-состояние, вызов сервиса, форматирование ответа. Тесты —
  `tests/test_bot/`, реальный aiogram `Dispatcher.feed_update` со стаб-сессией
  бота (`tests/test_bot/conftest.py`), не моки хендлеров.
- **`app/workers/`** — фоновые задачи через APScheduler (синк Google
  Sheets, опрос Robokassa OpState, еженедельные отчёты) — polling-архитектура,
  не вебхуки: без домена/HTTPS у бота негде принимать входящие колбэки.
  Если воркеру нужно программно привязать следующее сообщение пользователя
  к событию таймера (не к колбэку — входящего Update у таймера нет) —
  `dispatcher.fsm.get_context(bot=bot, chat_id=..., user_id=...)`
  выставляет FSM-состояние напрямую (см. `weekly_digest.py`); для этого
  `register()` воркера должен получить `dispatcher`, не только `bot`
  (`main.py::build_scheduler`). Тот же приём тесты уже используют для
  прямой проверки состояния (`tests/test_bot/conftest.py`), здесь —
  боевое применение, не только в тестах. Redis-хранилище FSM (не
  MemoryStorage) означает, что такая связка переживает рестарт/деплой
  между отправкой напоминания и ответом на него.

**Деплой-образ не содержит `.git` и не имеет `git`/`gh`** — `Dockerfile`
копирует только `app/`, `pyproject.toml`, `alembic.ini` (не `COPY . .`).
Проверено буквально: `docker run --rm <image> sh -c "test -d /app/.git"`
— пусто, `which git gh` — пусто. Любая функция, которой нужна история
коммитов или GitHub API (пример: автосбор "что раскатили"/"что в работе"
для `weekly_digest.py`) не может использовать локальный `git log` или
личный `gh`-доступ разработчика — только собственный GitHub-токен,
положенный в `.env` на сервере и прочитанный через `app.config.settings`,
как `ROBOKASSA_*`. Личный `gh auth` на dev-машине даёт доступ только для
исследования/прототипирования самим разработчиком (или Claude), не для
процесса бота, который сам, автономно, будит воркер по расписанию.

Тесты (`tests/conftest.py`) сами поднимают `db` из docker-compose и
создают отдельную БД `pullup_test` — миграции применяются автоматически
при первом запуске. Нужен только запущенный Docker:

```bash
pytest              # весь набор
ruff check app/ tests/
```

## Известный класс бага: `callback.message.from_user` — это бот, не человек

В реальном Telegram сообщение, к которому прикреплена inline-кнопка,
отправлено ботом — `callback.message.from_user` всегда бот. Нажавшего
кнопку видно только через `callback.from_user`. Баг: `_finalize_workout`
брал `telegram_id` из `message.from_user.id` — для callback-варианта
(«Пропустить» у комментария) это ловило id бота, `get_by_telegram_id`
возвращал `None`, `user.id` падал `AttributeError` **после** `state.clear()`
— тренировка терялась молча, без сообщения об ошибке (aiogram глотает
необработанное исключение в хендлере). Подтверждено трассировкой из
логов прод-бота. Тот же паттерн жил ещё в трёх местах (`backdate.py`,
`menu.py::render_profile`, `profile_edit.py`) — везде заменено на явный
`telegram_id`, переданный от исходного callback/message, а не выведенный
из `message.from_user.id` задним числом.

Тестовая фикстура `tests/test_bot/conftest.py::make_callback_update` —
единственный источник `Update` с `CallbackQuery` для `tests/test_bot/`,
специально ставит `message.from_user` = бот (не нажавший), как в реальном
Telegram. Не заводить локальных копий с обратной (неверной) семантикой —
именно неверная копия маскировала баг до его обнаружения.

**Правило**: в любом хендлере, где `message` может прийти из
`CallbackQuery`, брать `telegram_id` только из `callback.from_user.id`
(или явного параметра, прокинутого от него), никогда из
`message.from_user.id`.

## Процедура деплоя

Стандартный цикл (без миграции):

```bash
git push origin main
ssh root@192.241.141.47 "cd /root/pullup-trainer-bot && git pull && docker compose build app"
ssh root@192.241.141.47 "cd /root/pullup-trainer-bot && docker compose up -d app"
```

С миграцией — **сначала прогнать её локально** против непустых таблиц
(dev-БД `pullup` из docker-compose, не только чистую `pullup_test`),
прежде чем `alembic upgrade head` на проде:

```bash
ssh root@192.241.141.47 "cd /root/pullup-trainer-bot && docker compose run --rm app alembic upgrade head"
```

Причина этого правила — реальный инцидент (ревизия формулы прогрессии
блока на объём, миграция `e2c7a4f19d3b`): миграция добавляла колонки в
`blocks`, но не в `blocks_archive_admin_reset` — постоянную архивную
таблицу под «🧪 Полный сброс» (см. ниже), созданную через
`CREATE TABLE ... (LIKE blocks)` (`b41882a0e3e8`). `LIKE` — это снимок
структуры на момент создания, он **не следит** за последующими
`ALTER TABLE` на исходной таблице. Баг («INSERT has more expressions than
target columns») проявился только на полном прогоне тестов против
непустой тестовой БД — на пустой `pullup_test`, будь она поднята с нуля
без предварительного прогона, баг остался бы незамечен до первого
реального вызова "Полного сброса" в проде.

**Если когда-нибудь снова меняешь схему `workouts`, `blocks`,
`workout_sets`, `baselines` или `equipment_items`** — проверь, нужно ли
то же самое изменение в соответствующей `*_archive_admin_reset` таблице
(все пять перечислены в `b41882a0e3e8_admin_reset_archive_tables.py`).

После деплоя — не полагаться только на «в логах нет ошибок». Логи чистого
старта показывают, что процесс не упал, но не что фича реально работает.
Проверять на реальных данных: прямой SQL-запрос к проду (`docker compose
exec -T db psql ...`) для схемных изменений, реальный проход хендлера
через бота или через прямой вызов сервисного слоя для логики.

## Изменение формулы прогрессии или схемы БД — план перед кодом

Для нетривиальных изменений домена прогрессии (шаг роста, пороги,
переходы снаряда) или новых колонок/таблиц — сначала план с конкретными
расчётами на реальных примерах (числа, не абстрактные формулы), явное
согласование, и только потом реализация. Не идти сразу в код. Тесты пишутся
на **каждый пример из плана**, с точными ожидаемыми значениями — это
почти всегда ловит расхождение между тем, что казалось очевидным на бумаге,
и тем, что реально считает код (см. следующий пункт).

## Google Sheets: новая колонка в инкрементальном листе требует бэкфилла

`app/services/sheets_export.py::SHEET_HEADERS` — единственный источник
состава колонок. Правило прямо у константы (не пропустить):
добавление колонки в один из инкрементальных листов (`events`, `workouts`,
`subscriptions`, `coins`, `achievements` — те, что растут через
`append_rows`, а не переписываются целиком как `users`/`equipment_items`)
чинит заголовок на существующем листе автоматически
(`ensure_sheet_structure`), но **не трогает уже записанные строки** —
они на одну колонку короче, и все данные правее точки вставки читаются
под чужими подписями. Не «не хватает данных» — вводящее в заблуждение
смещение. Зафиксировано после реального инцидента (username в заголовке,
старые строки остались короче). Обязателен разовый бэкфилл
(`scripts/backfill_sheets_username.py` — образец: регенерирует
затронутые листы целиком из БД тем же кодом синка, а не точечно патчит
старые строки), не только правка заголовка.

## Стиль тестирования: доказать, что тест реально ловит баг

Зелёный тест сразу после написания фикса ничего не доказывает — он мог
быть зелёным и без фикса (слабое условие, неверная фикстура и т.п., как в
случае с `callback.message.from_user` выше). Стандарт в этом проекте:
хотя бы для нетривиальных фиксов — временно откатить исправление, увидеть
падение именно этого теста, вернуть исправление. Тот же принцип действует
при написании теста ДО реализации: сначала руками посчитать ожидаемое
значение по плану, потом сверить с тем, что выдаёт код — расхождение
здесь и ловит реальные баги (пример: при ревизии формулы прогрессии
ручной расчёт для `recalculate_volume_block` поймал, что
`recalculate_target` подмешивал бы порог смены снаряда в цифру, которая
должна была остаться честной — пойман до, не после написания теста).

## `ADMIN_IDS`: обход лимитов для тестирования вживую

`settings.is_admin(telegram_id)` (по `ADMIN_IDS` из `.env`) — для
telegram_id из списка:

- минимальный отдых между тренировками (`MIN_REST_DAYS`) не блокирует
  повторный старт (`handle_start_workout`);
- провал перехода на новом снаряде не откатывает его молча —
  `bypass_transition_wait=True` в `resolve_next_targets`/
  `_resolve_next_state` сразу предлагает выбрать снаряд заново;
- «🧪 Полный сброс» (только видна админам, `admin_reset_prompt` →
  `admin_reset_confirm`) архивирует (не удаляет) прогресс аккаунта в
  `*_archive_admin_reset`-таблицы и возвращает его в состояние до
  онбординга — можно проходить весь путь заново сколько угодно раз;
- «🧪 Тестовый платёж 1₽» в `/admin` — та же ссылка Robokassa и тот же
  путь подтверждения (`sync_pending_payments`), что у обычной подписки,
  но на 1₽ вместо `SUBSCRIPTION_PRICE_RUB` — не тратить 990₽ на каждую
  проверку интеграции.

Домен (`app/domain/rules.py::check_training_readiness` и т.д.) обход не
знает и не меняется — обход только в вызывающем bot/repository-слое.

## Robokassa: подтверждена задержка опроса, не баг

Диагностический платёж 1₽ (см. выше) дал первое живое подтверждение
`OpStateExt`: `State/Code=100` (оплачен) — код и парсинг (`_STATE_CODE_PAID`
в `app/services/robokassa.py`) верны на реальных данных, не только по
документации. Отдельно подтверждён реальный сценарий задержки: платёж
завершился на стороне Робокассы сразу **после** ближайшего прогона
`sync_robokassa_payments` (интервал 5 минут) — пойман только следующим
прогоном, уведомление пришло с задержкой ~7 минут. Это не баг, а
арифметика опроса: интервал не выбирается точно под момент оплаты,
худший случай — почти два интервала подряд. Решение — не менять интервал
(тратить его нельзя, это упрётся в лимиты API), а честно предупредить
в `PAYMENT_LINK_SENT` («до 10 минут»), плюс `_notify` теперь логирует и
успешную доставку, не только неудачу (`logger.info`, не только
`logger.warning`) — раньше «нет warning» не было прямым доказательством
«сообщение дошло», приходилось вручную сверяться со своим чатом с ботом.

Диагностика этого случая — образец методики: не чинить вслепую по
жалобе «уведомление не пришло», а по порядку проверить (1) сам платёж и
прошёл ли цикл синка, (2) что реально вернул внешний API (прямой вызов
с прод-сервера, не по логам), (3) какой путь подтверждения реализован
(вызывается ли `extend()`, привязана ли нотификация к сумме платежа),
(4) и только если на всех трёх шагах всё чисто, а результата всё равно
нет — тогда это баг того самого класса (см. `callback.message.from_user`
выше), а не раньше.

## Mini App: Этап 0 (issue #15)

Домен `app.bimoool.com` подтверждён (2026-08-31) — A-запись резолвится в
`192.241.141.47`, этот VPS. Веб-слой: `app/web/` (FastAPI, тонкий слой
поверх тех же `repositories`/`services`/`domain`, что и бот — не дублирует
логику), `webapp-frontend/` (React + Vite, вне пакета `app`, собирается в
статику и отдаётся тем же FastAPI-процессом одним origin'ом, без CORS),
`Dockerfile.web` + сервис `web` в `docker-compose.yml` (свой контейнер,
свой образ, зависит только от `db`, порт публикуется только на
`127.0.0.1` — физически не может задеть `reeltrack-*` на этом же VPS, см.
шапку файла).

**Готовые библиотеки, не самописный HMAC** (issue #15, коммент от
2026-08-31, референс `taiga-labs/telegram-miniapp-template`):
- Бэкенд — `init-data-py` (`app/web/auth.py::get_validated_init_data`,
  FastAPI-зависимость): выбран, а не `telegram-webapps-authentication`,
  потому что не навязывает свою обвязку над Depends/Header — тонкий слой
  интеграции пишется по тому же принципу, что и остальной проект (бот не
  использует чужой HTTP-клиент для Robokassa как чёрный ящик, см.
  `app/services/robokassa.py`, — берёт готовую проверку подписи и
  оборачивает сам).
- Фронтенд — `@telegram-apps/sdk` (`retrieveLaunchParams().initDataRaw`
  для сырой initData, `init()` на старте) — не `@twa-dev/sdk` (устаревший)
  и не самописная обвязка над `window.Telegram.WebApp`.

**Важная оговорка о проверке.** Обе интеграции написаны без доступа к
npm/PyPI из песочницы Claude (сетевой доступ недоступен, тот же класс
ограничения, что SSH к серверу, см. ниже) — по памяти о публичном API
этих библиотек, не сверено установкой пакета. `tests/test_web/test_auth.py`
специально строит initData САМ, по официальному алгоритму Telegram
(HMAC-SHA256, независимо от внутреннего устройства `init-data-py`), и
подписывает реальным `bot_token` — если имена классов/методов
(`InitData.parse`/`.validate(token, lifetime=...)`/`.user.id`/
`.user.first_name`) в реальности отличаются от использованных здесь, эти
тесты первыми покажут расхождение при первом `pytest`/`docker compose
build web` с доступом к сети. Не мержить/деплоить, не прогнав их хотя бы
раз с реальными пакетами.

**Обновление (issue #23, 2026-09-01): доступ к npm из песочницы Claude
иногда всё же есть** — оговорка выше про полное отсутствие сетевого
доступа не универсальна, зависит от конкретного запуска/окружения.
Когда доступ есть — им стоит воспользоваться (`npm install` в
`webapp-frontend/`, закоммитить получившийся `package-lock.json`, если
его ещё нет, прогнать `npx tsc -b && npx vite build` перед выводами о
типах/сборке), не полагаться на память о публичном API по умолчанию.
Так был найден реальный баг: `@telegram-apps/sdk`'s `retrieveLaunchParams()`
(пакет `@telegram-apps/bridge` под капотом) читает launch params
**только из URL** (`location.href` → `performance` navigation entry →
`sessionStorage`), никогда не обращается к `window.Telegram.WebApp.initData`
(мост старого `telegram-web-app.js`, подключённого в `index.html`).
На живом Telegram Desktop `tgWebAppData` иногда не попадает в URL, хотя
кнопка Mini App правильная (`KeyboardButton(web_app=WebAppInfo(...))`,
не обычная `url=`-ссылка — тип кнопки был не при чём) — фронтенд получал
пустой `initDataRaw` и ошибочно писал "открыто не из Telegram?".
`webapp-frontend/src/App.tsx` теперь фолбэчится на
`window.Telegram.WebApp.initData`, если `retrieveLaunchParams()` пуст
или бросает исключение — тот же initData, другой источник, независимый
от URL-парсинга. Не проверено на живом Desktop-клиенте (сеть до npm ≠
доступ к реальному Telegram-клиенту, это два разных класса ограничения
песочницы) — если фолбэк не поможет, следующий кандидат — точка входа
через постоянную Menu Button (`set_chat_menu_button`/`MenuButtonWebApp`)
вместо `KeyboardButton`, у неё более стабильная кросс-клиентская
поддержка initData по опыту сообщества `@telegram-apps/sdk`.

**Обновление (issue #28, 2026-09-02): фикс #23 не помог, кнопка всё же
не при чём.** После деплоя фолбэка на `window.Telegram.WebApp.initData`
ошибка "initDataRaw is empty" повторилась и на Desktop, и (чёрный экран)
на мобильном. Автор issue заподозрил, что кнопка на самом деле обычная

**Обновление (issue #30, 2026-09-02): найдена настоящая первопричина —

initData гарантированно пустая, если Mini App запущена через keyboard

(`window.Telegram.WebApp` существует, `retrieveLaunchParams()` не бросает

способ запуска, для которого Telegram официально гарантирует непустую

сохранять документированно сломанную точку входа. Не проверено на живом
клиенте (тот же класс ограничения песочницы) — если чёрный экран на

button, это отдельный баг ErrorBoundary/загрузки скрипта, не initData.

**Обновление (issue #61): черновик живой тренировки на сервере —
исправление принятого в issue #59 решения держать промежуточные подходы

Схема — отдельная таблица `WorkoutDraft`/`workout_drafts`
(`app/db/models.py`, миграция `f1a2b3c4d5e6`), не поле в `ActiveTimer`:
у них независимые жизненные циклы (черновик живёт весь поток тренировки,
таймер — только во время конкретного отдыха, и не всегда синхронно
удаляется при продолжении, см. докстринг `ActiveTimer`) — совмещать в
одной строке было бы источником рассинхрона. Один черновик на
пользователя (unique `user_id`), без snapshot плана (`target`/`work_sets`/
`equipment`) — при восстановлении план перезапрашивается тем же
`GET /api/workout/plan`, что и обычный старт (пока черновик не сдан,
прогрессия не менялась, план детерминирован). `step_index` — единственный
источник позиции в потоке шагов, сами шаги (`buildSteps` в
`LiveWorkoutScreen.tsx`) пересобираются на фронтенде из `work_sets_a/b`
плана, не хранятся в БД.

API — `PUT/GET/DELETE /api/workout/draft` (`app/web/routes.py`,
`WorkoutDraftRepository` — тот же CRUD-без-сервисного-слоя паттерн, что
`ActiveTimerRepository`). `PUT` апсертит целиком (весь накопленный массив
подходов, не один подход за раз) — вызывается после каждого завершённого
подхода (`LiveWorkoutScreen.tsx::handleStepDone`), с ожиданием ответа: если
сохранение не удалось, показывается ошибка и переход на следующий шаг не
происходит — иначе только что введённый подход потерялся бы молча при
следующем закрытии Telegram. `submit_workout` удаляет черновик сам при
успешной записи (`status == "ok"`), в той же обработке, что и запись
`blocks`/`workouts` — не полагается на отдельный `DELETE` с клиента после
успеха (сеть могла оборваться уже после успешного submit).

Восстановление на фронтенде (`LiveWorkoutScreen.tsx`) — при заходе на
экран, если черновик найден и согласуется с текущим планом (число рабочих
подходов не короче сохранённых массивов — иначе черновик отбрасывается,
обычный `intro`), состояние восстанавливается и экран сразу открывается
на сохранённом `step_index` (или на `review`, если все подходы уже были
введены), без демонстрации `intro`. Правки на экране `review` (вес/резина/
комментарий перед финальной отправкой) сознательно НЕ персистятся — только
факт "дошёл до review" уже зафиксирован последним `PUT` перед переходом;
согласовано в issue как разумная граница объёма (потеря самого последнего
экрана перед отправкой — намного меньшая потеря, чем вся тренировка).

же самое `NULL` (`PUT /api/leaderboard/display-name`, `UserRepository.
set_leaderboard_display_name` — в отличие от `update_profile`, здесь
`None` валидное значение, не «пропустить поле»).

Три метрики (макс. повторений за подход, макс. вес отягощения, макс.
суммарный объём — когда-либо) — переключаемые табы одного экрана
(`LeaderboardScreen.tsx`), не три отдельных вкладки, с фильтром по полу
(`users.gender`) и возрастной категории поверх любой из них. Возрастные
категории — ступени ГТО для взрослых (18-29/30-39/40-49/50-59/60-69/70+,
`app/domain/leaderboard.py::AGE_BUCKETS`/`age_bucket`), взятые как готовый
ориентир по просьбе автора, не потому что это официальный стандарт для
самого лидерборда; посчитаны на лету от `birth_date` (тот же принцип, что
`app.bot.formatting.calculate_age`, продублирован как чистая функция без
импорта — `app/domain/` не должен зависеть от `app/bot/`), не хранятся
отдельно. Пользователи без даты рождения или младше 18 — только в общем
зачёте («все»), без своей ступени.

`app/db/repositories/leaderboard.py::LeaderboardRepository.top()` —
единственный репозиторий проекта на `sqlalchemy.text()` (raw SQL), не
ORM `select()`: `MAX`/`SUM` по элементам JSONB-массива `working_reps`
(`jsonb_array_elements_text`) и `RANK() OVER` сразу по всем пользователям
не выражаются штатным ORM без raw-фрагментов, а обычный паттерн проекта
(грузить полные ORM-объекты и агрегировать в Python, см.
`WorkoutRepository`) здесь означал бы тянуть блоки ВСЕХ пользователей в
память при каждом открытии лидерборда — денормализация/кэш сознательно не
заведены (тот же риск рассинхрона схемы, что уже один раз укусил проект,
см. `*_archive_admin_reset` выше), обычные Postgres-таблицы с индексом по
`user_id` и `LIMIT` достаточно быстры на реальном объёме без этого. Топ-N
плюс своя строка (даже если пользователь вне топа) — одним запросом через
`WHERE rnk <= :limit OR user_id = :requesting_user_id`, не отдельным
вторым запросом. Ловушка на реальном Postgres, не только по документации:
bind-параметр, единственное употребление которого в запросе —
`IS NULL`/`IS NOT NULL` без соседнего типизированного операнда, asyncpg не
может типизировать при подготовке prepared statement
(`AmbiguousParameterError`) — каждый такой параметр (`gender`, `age_bucket`,
`requesting_user_id`, `limit`) обёрнут явным `CAST(:param AS ...)`, не
только для читаемости.

**Обновление (issue #82): график "Прогресс" — факт вместо плана,
переключатель метрик, "сила" — знаковая шкала нагрузки, не повторения.**
Старый `GET /api/progress` строился по `BlockAssignment.target_after` —
плановой цели на СЛЕДУЮЩУЮ тренировку, не по тому, что человек реально
сделал (баг, найденный на реальном использовании). Эндпойнт теперь
принимает `metric: max_reps|volume|strength` (`app/web/routes.py::
get_progress`/`_progress_value`) и отдаёт факт:

- `max_reps` — лучший фактический подход блока (рабочий или на максимум).
  Новое свойство `BlockLog.best_set` (`app/domain/session.py`) — тот же
  смысл, что `_BEST_SET_EXPR` в `LeaderboardRepository` (issue #67/#74), но
  в Python поверх уже загруженных `WorkoutRecord`, не raw SQL — здесь
  запись уже в памяти, агрегация по всем пользователям разом не нужна.
- `volume` — уже существующий `BlockLog.volume` (рабочие подходы + подход
  на максимум), просто читается вместо `target_after`.
- `strength` — единственная метрика с одной линией, не двумя (`value_a`
  всегда `null`), скоуплена на блок Б. Решение (согласовано в плане перед
  реализацией, не выбрано вслепую) — НЕ повторения на блоке Б: там факт
  растёт медленно и **сбрасывается** при каждой смене снаряда (новый
  снаряд — новый отсчёт от 3 повторений), график выглядел бы как пила, а
  не как рост силы. Вместо этого — `app.domain.constants.to_signed_load`,
  уже существующая доменная функция единой знаковой шкалы нагрузки (резина
  — минус, свой вес — 0, отягощение — плюс), которую `recalculate_target`
  уже использует для сравнения "тяжелее/легче" при смене снаряда: та же
  переменная, что определяет прогрессию, просто показанная по
  тренировкам во времени — переживает смену резины/веса как один
  непрерывный ряд, не разрывается на несравнимые сегменты. Не определена
  для AUSTRALIAN (угол корпуса, не кг) — такие тренировки отдаются с
  `value_b=null`, фронтенд пропускает эти точки при построении линии
  (`ProgressScreen.tsx::seriesKeysForMetric`/фильтр в `ProgressScreen`), не
  выдумывает число.

`ProgressPointResponse.value_a/value_b` — `Decimal | None` (не `int`, как
был `target_a/target_b`) ради `strength`; на фронтенде приходят строкой
(тот же паттерн, что `LeaderboardEntry.value`) и конвертируются в `number`
один раз при рендере. `tests/test_web/test_progress.py` — числа посчитаны
руками по плану, не выведены из тестируемого кода (см. "Стиль
тестирования" выше); по пути тест на `BlockLog.best_set`
(`tests/test_session.py`) поймал реальный баг первой реализации —
`max(*working_reps, max_reps)` падал `TypeError` на пустом
`working_reps` (`max()` с одним нераспакованным int-аргументом требует
iterable), исправлено на `max((*working_reps, max_reps))` до коммита.

## Еженедельный дайджест: нормализация коммитов, черновик, охват (issue #84)

**Автосбор "что раскатили" теперь читаем.** Git-история этого репозитория
почти целиком состоит из merge-коммитов кнопки "Merge pull request" на
GitHub (`Merge pull request #83 from bimoool/claude/issue-82-...`) —
первая строка технична и нечитаема, а `_parse_commits`
(`app/services/github.py`) раньше брал только её (`.splitlines()[0]`).
Настоящий заголовок смёрженного PR GitHub кладёт второй непустой строкой
того же сообщения коммита — `_normalize_commit_message` теперь достаёт
именно её для merge-коммитов, плюс для всех коммитов убирает префиксы
Conventional Commits (`fix:`, `feat(scope)!:` и т.п.) с капитализацией
первой буквы остатка. Полноценная группировка по смыслу — отдельная и
существенно более сложная NLP-задача, сознательно не делалась; базовой
нормализации достаточно, потому что автосбор — не финальный текст
рассылки (см. следующий пункт), а материал для написания дайджеста.

его. Пользователи никогда не видят сырой автосбор напрямую.

## Прочие устоявшиеся решения

- **Архивировать, не удалять.** Любой «сброс»/«убрать» исторических
  данных — перенос в `*_archive_v1`/`*_archive_admin_reset`-таблицу, не
  `DELETE`. Перед удалением enum-значения из БД (см. пример с Tribute,
  `8a1f4c6e9b2d`) — сначала вручную проверить, нет ли исторических строк
  с этим значением; если есть — не удалять значение, оставить как
  «исторический, не используется», задокументировав это в комментарии
  рядом с определением enum.
- **Одна причина падения = один хендлер, не общий `try/except` в проде
  молча.** `cd0eefa` завёл глобальный обработчик необработанных
  исключений на уровне диспетчера — он логирует и уведомляет админа
  (`ADMIN_UNHANDLED_EXCEPTION_NOTIFICATION`), не проглатывает молча.
  Если пишешь код, который может упасть предсказуемо — лови и обрабатывай
  сам, не полагайся на этот catch-all как на способ скрыть баг.
  `state.clear()` — до записи в БД в `_finalize_workout`, не после
  (гонка двойного тапа: см. `2b92942`).
- **`app.bot.parsing.MAX_REPS = 999`** — единственный источник верхнего
  предела на число повторений (`parse_reps`/`parse_int_sequence`,
  `onboarding.py`). Не заводить локальных копий лимита в отдельных
  хендлерах (баг, `673bf65`: старый `MAX_REASONABLE_REPS=100` в
  `onboarding.py` отклонял обычные трёхзначные результаты вроде 102).
- **Числовые константы продуктовых решений, не научных фактов** —
  фиксировать явно в докстринге при вводе (пример: потолок 30 повторений,
  откат до 20/30, старт веса 5 кг, шаг 5% в `app/domain/progression.py` —
  докстринг `recalculate_volume_block` явно отделяет, что построено на
  принципах прогрессивной перегрузки, а что — собственный выбор чисел).

## Известный класс бага: `message.text` — `None` у сообщения с картинкой

Прод-инцидент (issue #69): рассылка "📢 Рассылка всем" и еженедельный
дайджест (`handle_weekly_digest_reply`) брали текст из `message.text`
напрямую и передавали его в `bot.send_message`. Когда админ присылает
сообщение с картинкой, Telegram кладёт подпись в `message.caption`, а
`message.text` остаётся `None` — `aiogram`/pydantic отклоняет
`SendMessage(text=None)` валидацией (`1 validation error for SendMessage:
text — Input should be a valid string`), рассылка падала целиком, ни один
пользователь не получал сообщение. Тот же провал ждал
`WeeklyDigestRepository.record` (колонка `text` — `NOT NULL`).

Фикс — `app/bot/handlers/admin.py::_broadcast_source_text` (`message.text
or message.caption`) как единственный источник текста для рассылки, и
ветвление на `bot.send_photo(..., caption=...)`, если в сообщении есть
`message.photo` — иначе картинка терялась бы молча, а подпись ушла бы как
обычный текст без неё. Тот же паттерн (`message.text` без учёта
`message.photo`/`message.caption`) правился заодно и в `handle_admin_dm_text`
(личное сообщение пользователю из карточки в `/admin`) — тот же класс
бага, тот же вызывающий код мог получить картинку так же легко.

**Правило**: в любом хендлере, принимающем свободный текст от админа для
пересылки другому пользователю, не читать `message.text` напрямую, если
сообщение может прийти с вложением — проверять `message.photo` и
использовать `message.caption` как текст в этом случае.

## Известный класс бага: альбом (несколько фото) — Telegram шлёт его как
## несколько Update, не один

Прод-инцидент (issue #72), найден сразу после фикса issue #69 выше: админ
прикрепил к рассылке НЕСКОЛЬКО фото — ушло одно фото с подписью, остальные
отдельными сообщениями без текста. Причина не в `_broadcast_to_onboarded_
users` самой по себе (она уже брала `message.photo`/`message.caption`
правильно), а в том, что Telegram доставляет альбом не одним сообщением с
несколькими фото, а несколькими отдельными Update с общим
`media_group_id` — по одному Update на каждое фото. `aiogram`-диспетчер в
реальном polling обрабатывает Update конкурентными asyncio-задачами
(`Dispatcher._polling`, `handle_as_tasks=True` по умолчанию), не дожидаясь
хендлера предыдущего Update — каждое фото альбома по отдельности ловило
`waiting_for_broadcast_text` и самостоятельно запускало полную рассылку.

Фикс — `app/bot/middlewares.py::MediaGroupMiddleware`, outer-middleware,
подключенный только на `admin_router.message`
(`app/bot/handlers/admin.py`, не глобально на весь `Dispatcher`, чтобы не
трогать альбомы вне админских сценариев). Буферизует части одного альбома
по `media_group_id`: первая часть ждёт `ALBUM_DEBOUNCE_SECONDS`, копит
остальные части (обычно приходят с разницей в десятки-сотни мс) в общий
список и передаёт их все хендлеру одним вызовом через `data["album"]`;
остальные части сами добавляют себя в буфер и завершаются без вызова
хендлера — иначе он запустился бы ещё раз на каждую из них.
`_broadcast_to_onboarded_users`, `handle_admin_broadcast_text`,
`handle_weekly_digest_reply` и `handle_admin_dm_text` при непустом `album`
шлют `bot.send_media_group` с `InputMediaPhoto(caption=...)` на одном
элементе массива вместо `send_photo` на каждое фото по отдельности; caption
ищется по ВСЕМ частям альбома (`_album_caption`), не только по первой
пришедшей — Telegram не гарантирует, что подпись окажется именно на
дошедшей до буфера первой.

**Правило**: любой хендлер, ожидающий «одно сообщение = один Update» (в
частности — рассылки/пересылка от админа), не может просто проверять
`message.photo` для случая с несколькими фото — Telegram гарантированно
разобьёт такое сообщение на несколько Update с общим `media_group_id`.
Нужна буферизация по `media_group_id` до хендлера (см.
`MediaGroupMiddleware`), не точечная правка внутри самого хендлера.
